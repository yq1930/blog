# 前端调试技巧

调试效率的差距不在工具，而在方法。看到 bug 就开始改代码试，往往改了十次还没定位；先观察、再假设、最后验证，可能三分钟就找到根因。本篇讲断点调试、网络面板、性能分析、移动端远程调试，以及一套通用的 bug 排查思路。把调试当作有章法的流程，而不是碰运气。

## 先建立排查思路

面对一个 bug，别急着改代码。按这个顺序走：

```text
1. 复现  → 稳定复现的 bug 才好定位
2. 隔离  → 二分法缩小范围（注释、回滚、最小复现）
3. 观察  → 看实际值，而不是猜值
4. 假设  → 提出"可能是什么导致了这个"
5. 验证  → 改一处，看现象是否变化
```

| 反模式 | 问题 |
| --- | --- |
| 改代码看现象，反复试 | 每次改动引入新变量，越来越乱 |
| 只看代码不运行 | 脑内执行不可靠，尤其是异步 |
| 假设"应该是这样" | 实际值和假设值常常不一样 |

> 最容易卡住的时刻，往往是"我确定这里没问题"。放下假设，去打印实际值。

## 断点调试：比 console.log 强得多

`console.log` 适合快速看一眼值，但复杂问题（异步、闭包、状态变化）断点调试更高效。断点能让你**暂停在某个时刻，查看所有变量的真实值，并逐步执行**。

| 调试方式 | 用途 |
| --- | --- |
| 普通断点 | 暂停在某行 |
| 条件断点 | 表达式为真才暂停（如 `i === 100`） |
| 日志断点 | 不暂停，只打印（替代临时 console.log） |
| DOM 断点 | 元素被修改/删除时暂停 |
| XHR/Fetch 断点 | 某个请求发出时暂停 |

```text
// 在 Sources 面板：
// 1. 点行号加断点
// 2. 右键断点 → Edit breakpoint → 加条件
// 3. 用 Step over / Step into / Step out 逐步执行
// 4. 右侧 Scope 查看所有变量真实值
```

条件断点特别有用——循环里某次迭代出问题，设 `i === 9527` 直接停在出错那次，不用手动跳过前 9526 次。

DOM 断点定位"谁改了 DOM"：在元素上右键 → Break on → attribute modifications / subtree modifications / node removal，DOM 被改时自动暂停到改它的代码。

## Sources 面板的小技巧

```text
- Call Stack：查看调用栈，点哪一层跳到哪层代码
- Watch：监视表达式，断点暂停时看它的值
- Scope：当前作用域所有变量（闭包也能看到）
- 黑盒脚本（Blackbox）：把库代码标记为不进入，单步时跳过
```

把 Vue/React 源码、第三方库加入黑盒，单步执行时不会陷进库内部，只在自己的业务代码里走。

## 网络面板：API 问题先看这里

很多"前端 bug"其实是接口问题。Network 面板能看清每个请求的全过程：

| 检查项 | 看什么 |
| --- | --- |
| 请求 URL 和方法 | 对不对？参数有没有错？ |
| 请求头 | Authorization、Content-Type 对吗？ |
| 请求体 | 发出去的数据对吗？ |
| 状态码 | 200/400/401/404/500 各意味什么 |
| 响应体 | 后端返回了什么？是错误信息还是空？ |
| Timing | 是慢在 DNS、连接还是服务端处理？ |

```text
常见误判：
- "数据没显示" → 其实是接口返回了空数组，不是前端渲染问题
- "登录失败" → 看响应是 401（凭证错）还是 400（参数错）
- "页面慢" → Timing 显示 TTFB 很高，是后端慢，不是前端
```

> 复现问题时勾选 **Preserve log**，页面跳转后网络记录不丢失。勾选 **Disable cache**，避免缓存干扰调试。

## 性能分析：找到慢在哪里

"感觉卡"不是定位问题的说法。用 Performance 面板录制一段交互，看时间花在哪：

```text
1. 打开 Performance 面板
2. 点 Record → 操作页面（如滚动、点击）
3. Stop → 看 Flame Chart 和 Summary
```

| 火焰图颜色 | 含义 |
| --- | --- |
| 黄色 | 脚本执行（JS） |
| 紫色 | 布局和样式计算 |
| 绿色 | 绘制和合成 |
| 灰色 | 空闲 |

| 问题信号 | 可能原因 |
| --- | --- |
| 长黄色块（>50ms） | JS 计算太重，需要拆分 |
| 大块紫色 | 频繁重排（改了布局属性） |
| 强制同步布局警告 | 读布局属性后又立刻写布局 |

> 别只看"总时长"。找到最长的那一段函数调用，针对性优化。优化后再录制对比，确认真的变快了。

## 移动端远程调试

手机上的问题没法直接用电脑 DevTools。用远程调试把手机连到电脑：

| 平台 | 方法 |
| --- | --- |
| Android + Chrome | `chrome://inspect`，USB 连接 |
| iOS + Safari | Safari → 开发 → 设备名 |
| 微信/小程序 | 各自的开发者工具远程调试 |

```text
// Android 调试步骤：
// 1. 手机开启开发者模式 + USB 调试
// 2. USB 连电脑
// 3. 电脑 Chrome 打开 chrome://inspect
// 4. 看到设备后点 Inspect
```

移动端远程调试能看断点、网络、控制台，和桌面端几乎一样。无法远程调试时（如线上问题），用 `vConsole` 或 `eruda` 这类注入工具在页面内显示一个简易调试面板。

## 日志策略：留有用的信息

线上问题靠日志复盘。但日志不是越多越好——关键在于**留有用的信息**：

| 原则 | 说明 |
| --- | --- |
| 记上下文 | `submit failed` 没用，`submit failed: form=login, error=network` 有用 |
| 分级别 | error/warn/info，不要全是 log |
| 避免敏感信息 | 密码、token 不要打日志 |
| 生产环境收敛 | 大量 console.log 影响性能，生产构建移除或降级 |

```js
// 差：看不出上下文
console.log('error', err)

// 好：带上下文
console.error('[login] submit failed', { email, code: err.code, msg: err.message })
```

## 常见 bug 排查清单

| 现象 | 先查什么 |
| --- | --- |
| 数据没显示 | Network 响应体是否为空或报错 |
| 样式没生效 | DevTools Elements 看 computed style，是否被覆盖 |
| 点击没反应 | 控制台是否有 JS 报错，元素是否被遮挡 |
| 偶发崩溃 | 是否有未处理的 Promise rejection |
| 内存增长 | Performance Memory 录制，看是否有泄漏 |

## 务实的检查清单

- 是否先稳定复现 bug，再开始排查？
- 复杂问题是否用断点而非一堆 console.log？
- 条件断点是否用上，定位循环里的特定迭代？
- 接口问题是否先看 Network 面板的请求和响应？
- "页面卡"是否用 Performance 录制找到具体慢的函数？
- 移动端问题是否用远程调试，而不是猜？
- 日志是否带上下文且不泄露敏感信息？

调试的本质是"缩小搜索范围"。每一步操作（复现、隔离、断点、看网络）都应该让可能的原因变少。如果改了十次还没定位，说明方法错了——停下来，重新观察，而不是继续乱试。
