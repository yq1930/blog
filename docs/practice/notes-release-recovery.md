# 发布后旧页面打不开：懒加载资源与恢复设计

用户上午打开应用，下午发布新版本。已打开的页面看起来一切正常，点击一个从未访问过的页面时，导航突然停住了。

旧页面仍在引用旧版本的懒加载文件。如果发布过程已经删除它们，浏览器就找不到下一页所需的代码。这个问题需要发布端和客户端共同处理。

本文来自[笔记应用实践](/practice/notes-architecture)的构建、发布脚本和路由恢复实现。这里只总结源码所体现的机制，不代表核验过线上缓存头、服务器状态或部署结果。

**2026-10-23 更新：**补充固定提交发布、后端依赖恢复和开发环境隔离；界面版本号的描述也按近期改动修正。

## 为什么首页正常，下一页却失败

当前 PC 应用使用路由懒加载，编辑器和其他页面按需下载。它改善首屏加载，但也让一次浏览器会话跨越多个发布版本。

```text
旧入口 → 已加载的首页代码
                  │ 用户稍后进入编辑页
                  ▼
             旧编辑页 chunk
                  │
          发布时删除了旧文件 → 导入失败
```

Vite 官方说明了这个场景，并提供 `vite:preloadError` 事件供应用处理动态导入失败。网络中断也可能导致类似错误，不能把每次导入失败都解释为发布版本不一致。[Vite Load Error Handling](https://vite.dev/guide/build.html#load-error-handling)

## 先发布资源，最后切换入口

当前发布脚本采用如下顺序：

1. 在独立临时目录构建，构建期间继续提供旧产物。
2. 检查临时产物中是否存在有效入口文件及其 JavaScript 资源。
3. 发布新资源，每个文件先写同目录临时文件，再通过重命名替换。
4. 更新资源清单，最后替换 HTML 入口。
5. 清理超过保留期、且不属于当前版本的旧资源。

关键约束是：**新 HTML 出现时，它引用的资源应已可读取；旧 HTML 还在使用时，旧资源也应有过渡期。**

这属于按文件发布和入口切换机制，不等于整个目录具有数据库式事务。切换入口后的进程重启或探活若失败，仍需单独处理；不能宣称任何发布失败都会自动回滚所有状态。

## 保留期从资源退役开始计算

假设一个版本已经稳定运行很久，某个 chunk 的修改时间也很早。发布新版时，若直接删除“修改时间早于保留期”的文件，它可能刚被替换就遭到清理。

当前脚本为上一版退出使用的资源记录退役时点，并保存当前版本的资源清单：

| 文件类型 | 处理方式 |
| --- | --- |
| 新版本仍引用的文件 | 无论文件时间多早，都不能清理 |
| 刚被新版本替换的文件 | 从本次退役起计算保留期 |
| 更早退役的文件 | 保留原退役时间，避免每次发布无限续期 |
| 旧清单缺失或与入口不匹配 | 保守保留现有资源，重新建立基线 |

脚本还校验清单中的路径，防止错误条目越出资源目录。清理策略应由明确清单约束，不能仅靠目录中所有文件的修改时间猜测。

有限保留期仍无法服务无限长的旧会话，所以客户端恢复入口不可省略。

## 恢复应该回到用户想去的页面

当前应用在 Vue Router 的错误入口识别动态导入和 CSS chunk 失败，保留失败导航的目标地址，并显示“重新加载并打开”或“留在当前页”的选择。

它没有把 Vite 官方事件示例原样当成项目实现。路由错误入口的优势是能拿到来源与目标，便于说明“重新加载以后去哪里”。

```text
导航失败
  │
  ├─ 旧导航的迟到错误 → 忽略
  │
  └─ 当前导航的资源错误 → 显示一次恢复提示
                             │
                     留下保存 / 确认重新加载
                                      │
                       核对仍处于同一失败上下文
                                      │
                             打开原目标页面
```

如果用户先点 A，再点 B，A 的失败响应最后才到，不能把恢复目标改回 A。弹窗期间已经成功进入其他页面时，也不能在点击确认后跳回旧目标。

这与[编辑会话](/practice/notes-save-lifecycle)是同一条原则：异步结果必须核对自己是否还属于当前上下文。

## 不要用刷新掩盖未保存内容

下面是常见但不适合编辑器的处理思路：

```text
捕获加载错误 → 立即刷新
刷新后再次失败 → 再次刷新
```

它可能丢失内存中的修改，也可能在断网时形成刷新循环。当前实现让用户明确选择，提示先保存未完成编辑，并保留浏览器的离开保护。

进一步改进可以记录一次恢复尝试的版本与目标，失败后展示离线说明或手动重试入口。但不能把这种增强写成当前已经具备的能力。

## HTML 和哈希资源需要不同的缓存策略

官方建议为 HTML 配置 `Cache-Control: no-cache`，避免刷新后继续获得引用旧资源的入口。[Vite 构建说明](https://vite.dev/guide/build.html#load-error-handling)

`no-cache` 的含义是复用前需要重新验证，并非完全不存储。带内容哈希的不可变资源通常可以长期缓存，前提是同一 URL 不覆盖成另一份内容。[MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control#no-cache)

实际配置还要核对 CDN、反向代理和静态服务器，源码里的 Vite 配置无法证明线上响应头正确。

对本项目的总结应写成“已经保留旧资源并提供恢复提示；部署层缓存头仍需要按环境核验”。

## 让用户能说清自己打开的是哪一版

早期实现将包版本和 Git 短提交号一起展示，近期改动把界面改为只显示正式包版本号。当前不能再写成“用户在关于页可以直接看到构建提交”。

界面版本号与运维追踪身份可以分开：用户界面保持简洁，发布记录保留精确提交、资源清单和构建标识。若多个提交共用一个包版本，只看界面版本就不能区分它们。

当前发布脚本不只检查 HTTP 成功状态，还检查返回的 HTML 是否引用本次构建入口。但这只是入口级验证，不能替代编辑、保存和恢复等业务回归。

## 固定本次要发布的提交

近期前后端发布脚本要求使用确定的提交 SHA，并校验取回的提交与目标一致，避免排队期间分支已变化而实际发布了另一版。

它们还通过部署锁防止并发切换，并检查目标是否为当前版本的后续提交。旧作业晚到时不能悄悄把新版本覆盖回去；有意回滚需要独立、显式的控制。

这些保护回答的是“发布哪一份代码、谁能同时切换”，不是数据库事务或业务回滚能力。工作区出现本地改动时拒绝覆盖，也比自动清空现场更利于排障。

## 后端要同时恢复代码与依赖

后端近期改为先将目标提交准备到临时目录，按锁文件安装依赖并构建；通过后再切换代码和必要依赖，随后重启进程。

发生切换后的失败时，恢复逻辑尝试回到原提交与原依赖；无法恢复会保留现场并报告错误。不能把“有恢复分支”写成“恢复必定成功”。

当前后端脚本核对的是 PM2 进程状态、启动时间及短时间内是否再次重启。它没有调用业务接口或数据库，因此只能证明进程层面的状态，不应称为已经通过业务健康检查。

前端与后端的验收信号不同：前端检查入口资源，后端检查进程稳定性；用户操作是否正确，仍需受控环境中的业务验证。

## 本地页面也要约束后端目标

近期共享请求层移除了缺配置时默认访问某个线上地址的行为，改为显式声明接口环境并校验来源；生产构建在不匹配的页面来源运行时，会在请求前拒绝。

这能减少本地预览误连生产的机会，但配置校验不是网络隔离：别名、代理和环境误标仍需由环境清单及网络访问控制处理。原生端也不能被假定具有与浏览器完全相同的来源检查能力。

部署前应确认构建目标与运行环境一起匹配。把同一套静态产物复制到本机，并不自动把其中的服务目标变成测试环境。

## 在隔离静态环境验证

以下场景可用两套构建产物和本地静态服务器复现，不需要连接业务后端：

- [ ] 打开旧版本，切换产物后进入尚未加载的路由。
- [ ] 保留期内旧 chunk 可读取；当前清单资源不会因时间较早被删除。
- [ ] 删除某个旧 chunk 后出现恢复提示，来源页面仍保留。
- [ ] 连续导航 A、B，A 迟到的失败不会覆盖 B 的恢复目标。
- [ ] 有未保存内容时可以选择留下，确认重新加载时进入原目标。
- [ ] 断网时不会无限刷新；恢复网络后可再次尝试。
- [ ] 构建失败或资源发布失败且入口尚未切换时，旧入口仍可读取。

如果本地页面来自真实业务应用，测试前还要替换或阻断业务请求；页面运行在本机，并不代表它调用的服务也在本机。
