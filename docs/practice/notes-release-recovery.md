# 发布后旧页面打不开：懒加载资源与恢复设计

一个很典型的线上问题：

用户上午打开了应用，下午团队发布了新版本。用户已打开的页面看起来一切正常，可当他点击一个**之前从没访问过的页面**时，导航突然停住了，控制台报 `Failed to fetch dynamically imported module`。

原因是：旧页面仍然在引用旧版本的懒加载文件，而发布过程已经把这些文件删掉了，浏览器找不到下一页所需的代码。这个问题需要**发布端和客户端一起**处理。

本文来自 [笔记应用实践](/practice/notes-architecture) 的构建、发布脚本和路由恢复实现，只总结源码所体现的机制，不代表核验过线上的缓存头、服务器状态或部署结果。

## 1. 原理：展览换展，老访客手里还拿着旧地图

想象一座博物馆在开放期间更换展品。上午入馆的游客，手里拿着一份旧的导览地图（**旧的 HTML 入口**），地图上标着各个展厅的位置（**懒加载的 chunk 文件**）。

如果换展时立刻把旧展品全部撤走，拿着旧地图的游客走到某个展厅时，就会发现里面空空如也。

合理的做法是：

- 先把新展品布置好，再印新地图（**先发布资源，最后切换入口**）；
- 旧展品保留一段时间，让拿着旧地图的游客还能看完（**旧资源保留期**）；
- 在展厅门口贴一张告示：“展览已更新，请到前台换一份新地图”（**客户端恢复提示**）。

当前的 PC 应用使用路由懒加载，编辑器和其他页面按需下载。这改善了首屏的加载速度，但也让一次浏览器会话可能跨越多个发布版本：

```text
旧入口 → 已加载的首页代码
                  │ 用户稍后进入编辑页
                  ▼
             旧编辑页 chunk
                  │
          发布时删除了旧文件 → 导入失败
```

Vite 官方文档说明了这个场景，并提供了 `vite:preloadError` 事件供应用处理动态导入失败。注意：网络中断也可能导致类似的错误，不能把每一次导入失败都解释为“发布了新版本”。[Vite Load Error Handling](https://vite.dev/guide/build.html#load-error-handling)

## 2. 发布端：先发布资源，最后切换入口

当前的发布脚本采用这样的顺序：

1. 在独立的临时目录里构建，构建期间继续提供旧的产物；
2. 检查临时产物中是否有有效的入口文件及其 JavaScript 资源；
3. 发布新资源：每个文件先写到同目录下的临时文件，再通过重命名替换；
4. 更新资源清单，**最后**替换 HTML 入口；
5. 清理超过保留期、且不属于当前版本的旧资源。

关键约束是：**新的 HTML 出现时，它引用的资源必须已经可以读取；旧的 HTML 还在使用时，旧资源也要有一段过渡期。**

这是一种按文件发布、最后切换入口的机制，不等于整个目录具有数据库那样的事务性。切换入口之后，如果进程重启或探活失败，仍需要单独处理；不能说任何发布失败都会自动回滚所有状态。

## 3. 坑一：按文件修改时间清理，误删了刚退役的资源

**现象**：设置了“删除 7 天前的旧文件”，结果发布后旧页面还是马上就打不开了。

**原因**：假设某个版本已经稳定运行了一个月，它的某个 chunk 文件修改时间也是一个月前。发布新版本时，这个文件刚刚被替换掉，可它的修改时间早就超过了 7 天，于是立刻被清理了。

**修复**：保留期应该**从资源退役的那一刻开始计算**。当前脚本为上一版本中退出使用的资源记录退役时间，并保存当前版本的资源清单：

| 文件类型 | 处理方式 |
| --- | --- |
| 新版本仍在引用的文件 | 无论文件时间多早，都不能清理 |
| 刚被新版本替换的文件 | 从本次退役起计算保留期 |
| 更早就已退役的文件 | 保留原来的退役时间，避免每次发布都无限续期 |
| 旧清单缺失或与入口不匹配 | 保守地保留现有资源，重新建立基线 |

脚本还会校验清单中的路径，防止错误的条目越出资源目录。清理策略应该由明确的清单来约束，而不能只靠目录里所有文件的修改时间来猜。

即便如此，有限的保留期也无法服务无限长的旧会话，所以**客户端的恢复入口不可省略**。

## 4. 客户端：恢复到用户想去的页面

当前应用在 Vue Router 的错误处理入口识别动态导入和 CSS chunk 的加载失败，记住这次失败导航的目标地址，然后显示两个选项：“重新加载并打开”或“留在当前页”。

它没有原样照搬 Vite 官方事件的示例。在路由的错误入口处理的好处是，能拿到“从哪里来、要到哪里去”，便于实现“重新加载之后打开原本要去的页面”。

```text
导航失败
  │
  ├─ 旧导航的迟到错误 → 忽略
  │
  └─ 当前导航的资源错误 → 显示一次恢复提示
                             │
                     留下保存 / 确认重新加载
                                      │
                       核对仍处于同一失败上下文
                                      │
                             打开原目标页面
```

### 坑二：恢复的目标页面错乱

**现象**：用户先点了 A，又马上点了 B。A 的加载失败最后才返回，弹出的恢复提示却要带用户去 A；或者弹窗期间用户已经成功进入了其他页面，点击确认后又被拉回了旧的目标。

**修复**：和 [编辑会话](/practice/notes-save-lifecycle) 是同一条原则——**异步的结果必须核对自己是否还属于当前的上下文**。只处理当前导航的失败；用户确认时，再次核对仍处于同一个失败的上下文。

## 5. 坑三：捕获到加载错误就立即刷新

**现象**：常见的“修复”方式是这样的：

```text
捕获加载错误 → 立即刷新
刷新后再次失败 → 再次刷新
```

对编辑器来说，这会造成两个问题：内存中还没保存的修改直接丢失；如果失败是因为断网，页面会陷入无限刷新的循环。

**修复**：当前实现让用户**明确选择**，提示先保存未完成的编辑，并保留浏览器的离开保护。进一步的改进可以记录一次恢复尝试的版本和目标，失败后显示离线说明或手动重试的入口——但这还不是当前已经具备的能力。

## 6. 坑四：刷新之后，拿到的还是旧的 HTML

**现象**：用户按照提示重新加载了页面，问题依旧，因为浏览器（或 CDN）缓存了旧的 `index.html`，它引用的仍然是已经被删除的旧资源。

**修复**：Vite 官方建议为 HTML 配置 `Cache-Control: no-cache`，避免刷新后继续拿到引用旧资源的入口。[Vite 构建说明](https://vite.dev/guide/build.html#load-error-handling)

`no-cache` 的意思是“复用之前必须重新向服务器确认”，并不是“完全不缓存”。带内容哈希的文件可以长期缓存，前提是同一个 URL 永远不会被覆盖成另一份内容。[MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control#no-cache)

实际配置还要逐一核对 CDN、反向代理和静态服务器，源码里的 Vite 配置无法证明线上的响应头是正确的。对本项目准确的说法是：**已经保留旧资源并提供恢复提示；部署层的缓存头仍需要按环境核验。**

## 7. 让用户能说清自己打开的是哪一版

早期实现在界面上同时展示包版本号和 Git 短提交号，近期的改动把界面改为只显示正式的包版本号，所以不能再说“用户在关于页能直接看到构建提交”。

界面上的版本号和运维追踪用的身份可以分开：界面保持简洁，发布记录里保留精确的提交、资源清单和构建标识。注意：如果多个提交共用同一个包版本号，只看界面上的版本号就无法区分它们。

当前的发布脚本不只检查 HTTP 状态是否成功，还会检查返回的 HTML 是否引用了本次构建的入口。但这只是入口级别的验证，不能代替编辑、保存、恢复等业务回归测试。

## 8. 坑五：发布的不是你以为的那一版

**现象**：发布任务在排队期间，分支上又合入了新的提交，实际发布的代码和测试过的不是同一份；或者一个晚到的旧发布任务把新版本覆盖回了旧版本。

**修复**：近期前后端的发布脚本要求使用**确定的提交 SHA**，并校验取回的提交与目标一致。它们还通过**部署锁**防止并发切换，并检查目标是否是当前版本的后续提交——晚到的旧任务不能悄悄把新版本覆盖回去；有意的回滚需要独立、显式的控制。

这些保护回答的是“发布哪一份代码、谁能同时切换”，不是数据库事务或业务回滚的能力。工作区里出现本地改动时拒绝覆盖，也比自动清空现场更利于排查。

## 9. 坑六：后端只换了代码，没换依赖

**现象**：后端新版本依赖了一个新的包，发布时只更新了代码，重启后进程起不来；回滚时又只回滚了代码，依赖还是新的。

**修复**：后端近期改为先把目标提交准备到临时目录，按锁文件安装依赖并构建；通过后再**同时切换代码和必要的依赖**，然后重启进程。切换后如果失败，恢复逻辑会尝试回到原来的提交和原来的依赖；无法恢复时保留现场并报告错误。不能把“有恢复分支”说成“恢复一定成功”。

当前后端脚本检查的是 PM2 的进程状态、启动时间，以及短时间内是否又重启了。它没有调用业务接口或数据库，所以只能证明**进程层面**的状态，不能称为已经通过了业务健康检查。前端和后端的验收信号不同：前端检查入口资源，后端检查进程是否稳定；用户的操作是否正确，仍然需要在受控环境中做业务验证。

## 10. 坑七：本地预览的页面连到了生产后端

**现象**：在本地预览构建产物，以为是测试环境，实际请求全部发到了线上服务。

**原因**：过去的共享请求层在缺少配置时，会默认访问某个线上地址。

**修复**：近期共享请求层移除了这个默认值，改为显式声明接口环境并校验页面来源；生产构建如果在不匹配的页面来源中运行，会在发出请求之前就拒绝。

这能减少本地预览误连生产的机会，但**配置校验不等于网络隔离**：别名、代理、环境标错仍然需要通过环境清单和网络访问控制来处理。原生端也不能假定具有与浏览器完全相同的来源检查能力。把同一套静态产物复制到本机，并不会自动让其中配置的服务目标变成测试环境。

## 在隔离的静态环境中验证

以下场景可以用两套构建产物和本地静态服务器复现，不需要连接业务后端：

- [ ] 打开旧版本，切换产物后进入一个尚未加载过的路由
- [ ] 保留期内旧 chunk 可以读取；当前清单里的资源不会因为时间较早被删除
- [ ] 删除某个旧 chunk 后出现恢复提示，来源页面仍然保留
- [ ] 连续导航 A、B，A 的迟到失败不会覆盖 B 的恢复目标
- [ ] 有未保存内容时可以选择留下，确认重新加载时进入原目标
- [ ] 断网时不会无限刷新，恢复网络后可以再次尝试
- [ ] 构建失败或资源发布失败且入口尚未切换时，旧入口仍然可以读取

如果本地页面来自真实的业务应用，测试前还要替换或阻断业务请求：**页面运行在本机，并不代表它调用的服务也在本机。**

## 检查清单

- [ ] 发布顺序是先资源、后入口
- [ ] 旧资源的保留期从退役时间开始计算，并由清单约束
- [ ] 资源加载失败时显示恢复提示，不自动刷新、不丢失未保存的内容
- [ ] 恢复目标只属于当前的失败导航
- [ ] HTML 配置了 `no-cache`，哈希资源长期缓存，并在各部署层核验
- [ ] 发布使用确定的提交，有部署锁，旧任务不能覆盖新版本
- [ ] 后端同时切换和恢复代码与依赖
- [ ] 请求层显式声明接口环境，不默认访问线上地址
