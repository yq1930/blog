# 页面跳转规则会变化：缓存候选范围，确认时重读规则

某个入口需要临时跳到新页面，最容易的写法是判断一个固定业务 ID，再拼一个新地址。入口变多、规则有生效日期、页面长时间不关闭之后，这些判断就会开始互相矛盾。

本文来自一个原生微信小程序近期的导航改造，核对日期为 **2026-10-23**。业务对象、编号、地址和接口均省略，只保留可复用的控制流程。本次没有启动小程序或调用业务接口。

## 把“需要检查”与“现在生效”拆开

当前实现把规则分成两层：

| 数据 | 用途 | 缓存策略 |
| --- | --- | --- |
| 候选对象列表 | 哪些对象可能需要特殊处理 | 可缓存并后台更新 |
| 当前生效配置 | 此刻是否启用、目标是什么 | 点击时读取，确认时再次读取 |

这让普通入口无需每次等待规则请求，同时避免把有时效性的最终决定长期缓存。

```text
页面显示 → 预取候选列表
    ↓
用户点击 → 是否属于候选范围
    ├─ 否 → 原流程
    └─ 是 → 读取当前配置 → 显示提示
                               ↓
                         用户确认时再读取
                               ↓
                         按新规则或原流程继续
```

页面可能跨过日期边界，弹窗也可能停留很久。确认时重读配置，解决的是“用户看到提示时的规则”和“真正执行时的规则”可能不同。

## 缓存提高速度，也留下短暂遗漏窗口

当前候选请求使用同一个在途 Promise 合并并发请求；缓存过期时后台更新；初次没有缓存时只等待有限时间，失败则沿用原流程。

但使用旧候选列表也有明确代价：如果服务端刚加入一个新对象，旧列表中没有它，刷新完成前可能仍走原流程。候选缓存不是毫无影响的性能优化。

适合的策略取决于规则性质：

- 只是改善体验的跳转，可以接受短暂沿用原流程；
- 涉及权限、支付资格或必须执行的业务限制，应由服务端最终动作再次校验；
- 规则变化要求立刻生效时，需要额外的版本、失效通知或更严格读取策略。

这些增强是建议，不是当前客户端代码已经提供的保障。

## 保存用户意图，不只保存一个 URL

当前实现记录原对象、可选上下文和原流程回调。用户确认后，再依据最新规则构造目标地址。存在原有上下文时会带过去，而不是无条件回到一个空白入口。

通用意图模型可以表达为：

```ts
type NavigationIntent = {
  sourceId: string;
  selectedResourceId?: string;
  resumeOriginal: () => void;
};
```

模型比提前拼好的 URL 更容易重新解释。规则失效时可以继续原流程；规则更新时可以换目标，同时保留用户已经做出的选择。

当前代码还校验配置是否启用、来源是否一致、目标格式是否合法，以及目标是否等于来源。字符串编码用于构造地址，但不能代替这些业务条件检查。

## 弹窗属于某一页、某一次操作

异步请求返回时，用户可能已经离开当前页面；确认请求返回时，弹窗也可能已关闭或替换。

当前实现检查页面是否仍处于页面栈顶部，并在确认阶段检查保存的上下文是否仍是同一个对象。旧请求不能重新弹出属于上一轮操作的提示。

“页面仍存在”与“页面仍是当前操作目标”不同。只判断对象不为空，无法排除已经被隐藏的旧页面。

## 失败回退要说明自己的适用范围

当前规则接口不可用或配置无效时沿用原流程，跳转失败则在上下文仍有效时恢复提示并允许重试。按钮锁用于避免重复进入检查流程。

这是一种偏可用性的选择，不适合直接套在安全授权上。若原流程已经无法完成业务，静默回退也会把问题推迟到下一步；此时应展示明确的不可用状态。

客户端提示只负责导航体验，不应成为业务规则的唯一执行点。旧客户端、缓存和直接进入目标页，都需要服务端最终行为保持一致。

## 建议验证

| 场景 | 应核对的结果 |
| --- | --- |
| 普通对象不在候选范围 | 不被额外请求长期阻塞 |
| 候选列表过期且新增了对象 | 记录可接受的短暂遗漏，不能当作实时保证 |
| 弹窗停留跨过生效边界 | 确认时按新配置处理 |
| 加载过程中离开页面 | 旧响应不重开弹窗 |
| 连续点击与关闭后重开 | 提交锁和上下文分别管理 |
| 跳转失败或规则接口失败 | 保留必要意图，回退行为符合业务约定 |
