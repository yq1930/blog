# 保存成功，为什么还会丢输入：编辑会话与本地草稿

一个真实会发生的场景：

用户点击保存时，正文是 A。请求还没返回，用户又输入了 B。随后 A 保存成功，页面把“有未保存修改”的标记清除了。用户放心地关掉页面——B 就丢了。

服务端没有出错。错的是客户端把“**某一次快照已保存**”理解成了“**当前表单已保存**”。**保存状态必须属于一份确定的内容。**

本文延续 [笔记应用实践](/practice/notes-architecture)，根据当前前端实现总结编辑会话、保存队列和本地草稿的边界。示例为通用的教学代码，文末是建议的回归测试场景。

## 1. 原理：银行回执只证明你存的那一笔

去银行存钱：你把 100 元交给柜员，在等回执的时候，又往钱包里放了 50 元。回执上写着“已存入 100 元”——它只证明这 100 元存进去了，**不代表钱包里现在的 150 元都存进去了**。

保存也是这样：

- 点击保存那一刻的内容，是交给柜员的 100 元（**提交的快照**）；
- 等待响应时用户新输入的内容，是后来放进钱包的 50 元；
- 保存成功的响应，就是那张回执。

所以正确的做法是：响应回来后，**比较“当前表单”和“提交的快照”是否相同**。相同，才能标记为已保存；不同，说明还有新的修改没存。

## 2. 先分清三条保存路径

当前应用中，普通笔记和知识库文档用的不是同一种交互：

| 路径 | 怎么触发 | 保存到哪里 | 页面应该怎样描述 |
| --- | --- | --- | --- |
| 普通笔记自动同步 | 本地修改进入同步队列 | 本机缓存和服务端 | 区分“待同步”“同步失败”“已同步” |
| 知识库手动保存 | 点击保存或使用保存快捷键 | 服务端 | 本次提交成功后才确认 |
| 知识库本地草稿 | 输入后防抖写入 | 当前浏览器 | 用于恢复，不能说成“已上传” |

本地草稿不能替代手动保存：浏览器存储配额满了、隐私模式、用户清理了站点数据、写入前页面崩溃，都可能让草稿不可用。

## 3. 把一次编辑当作一个“会话”

当前实现把表单、加载序号、保存队列、本地草稿和已读取的版本，放进同一个**编辑会话**里。页面调用会话提供的能力，并负责询问用户是否离开、是否恢复草稿、是否覆盖。

```text
打开内容 → 读取服务端基线 → 检查本地草稿
                                  │ 用户选择恢复
                                  ▼
                              当前表单
                         ┌────────┴────────┐
                         ▼                 ▼
                    本地草稿兜底       手动提交快照
                                           │
                            失败：保留       │ 成功
                                           ▼
                              当前表单仍等于该快照？
                                是：已保存 / 否：仍有修改
```

初始化数据、恢复草稿和用户输入，是三种不同的变化。如果只用一个无条件的 `watch` 监听表单，很容易把“初始化”误判为“用户编辑”，或者把服务端回填的数据再上传一次。

## 4. 坑一：旧的提交替新的输入宣布了“保存成功”

**现象**：就是开头的场景，保存期间新输入的内容被标记成了已保存，关闭页面后丢失。

**修复**：保存时记下提交的快照，响应回来后和当前表单比较。当前实现会保存提交时的标题、正文和用户主动修改过的父级；请求期间如果出现了新的输入，就继续保持“未保存”状态，并基于新确认的版本保留后续的草稿。

下面只演示“快照确认”这一点，假定调用方已经串行提交，并且 `readForm()` 返回的字段和提交的载荷一致：

```ts
async function saveSnapshot() {
  const owner = currentSession();
  const submitted = structuredClone(readForm());

  const result = await persist(submitted);
  if (owner !== currentSession()) return;

  rememberConfirmedVersion(result.version);
  if (sameEditableFields(readForm(), submitted)) {
    markSaved();
    clearLocalDraft();
  } else {
    markUnsaved();
    keepLocalDraft(result.version);
  }
}
```

这个片段省略了错误处理、服务端版本冲突和队列的实现，不能单独当作完整的保存器使用。它要表达的约束是：**旧的提交不能替后来的输入宣告成功。**

## 5. 坑二：加了防抖，保存顺序还是乱了

**现象**：快速连续修改时，偶尔出现“后保存的内容被先保存的内容覆盖”。

**原因**：防抖只是**推迟**任务的启动。第一个请求发出去以后，第二个请求仍然可能同时发出，而后发的请求，响应也可能先到。

**修复**：当前保存队列采用“**一个进行中的任务 + 一份最新的待提交快照**”：

1. 收到保存请求时，把当时的快照设为“最新待提交内容”。普通笔记可以由输入触发自动同步；知识库的输入本身只更新表单和本地草稿；
2. 如果有正在进行的任务，就等待，避免多个写入同时进行；
3. 成功后，继续处理等待中的最新快照；
4. 失败后，保留待提交的内容，退出本轮，允许用户重试；
5. 切换会话时推进队列的代次，清理还没开始的任务，并让旧的回调失效。

“合并中间快照、只保留最新一份”适合“最终正文是什么”这类状态保存。如果业务要求保留每一次操作（比如记账流水、逐条审计），就不能这样合并。

另外，**取消队列不等于撤销了已经到达服务端的写入**。浏览器的 `AbortController` 可以终止请求或响应的读取，但不能据此推断服务端的事务已经回滚，这是前后端职责的边界。[MDN AbortController.abort](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort)

## 6. 坑三：迟到的响应回填到了别的文档

**现象**：打开文档 A，加载很慢，用户切到了文档 B；过了一会儿 A 的数据返回，把 B 的编辑区内容替换成了 A 的。

**原因**：异步操作返回时，没有检查“这个结果还属于当前的页面吗”。当前的加载流程会同时检查加载序号、会话代次、知识库和条目标识，并在等待用户确认草稿之后再检查一次。为什么需要这么多检查？

| 交错场景 | 为什么只检查条目 ID 不够 | 需要的检查 |
| --- | --- | --- |
| A 加载很慢，切到 B 后 A 才返回 | A 不该回填到 B | 当前目标 ID |
| A → B → A，第一次 A 最晚返回 | ID 又变回了 A，但这个请求已经过期 | 加载序号 |
| 退出账号后登录了另一个账号 | 旧的响应可能还在网络中 | 会话代次 |
| 恢复草稿的弹窗打开时切换了目标 | 用户点击的是旧上下文里的确认 | 弹窗结束后再次校验 |

**这些检查不能只写在发起请求之前**；每一个可能让出执行权的 `await` 之后，都要确认结果仍然属于当前的上下文。

用 watcher 驱动异步加载时，可以利用 Vue 的清理机制作废旧任务。`onWatcherCleanup` 在 Vue 3.5 以上才可用，而且要在同步阶段注册；取消之后仍然要检查结果的归属。[Vue watcher 副作用清理](https://vuejs.org/guide/essentials/watchers.html#side-effect-cleanup)

## 7. 坑四：草稿串了账号，或者不知道是基于哪个版本改的

**现象**：换了一个账号登录，打开同一个位置的文档，却弹出了“恢复草稿”，内容是上一个账号写的；或者恢复了一份草稿，保存时把别人后来的修改覆盖了。

**修复**：草稿必须记住**账号、内容和编辑基线**。当前知识库草稿按账号和内容范围隔离，保存标题、正文、父级、内容类型、草稿时间，以及开始编辑时的服务端版本。新建内容的范围还包含容器和内容类型，避免同一位置的新文档和新看板互相覆盖。

通用的模型可以写成：

```ts
type LocalDraft = {
  owner: string;
  scope: string;
  contentKind: string;
  baseVersion: string | null;
  fields: { title: string; body: string };
  savedLocallyAt: number;
};
```

只保存正文、不保存基线，恢复后就无法区分“这是在最新内容上的编辑”还是“这是在几天前的版本上的编辑”。当前实现会保留旧的基线，让之后的提交继续触发正常的冲突处理。

草稿恢复也不是自动覆盖：先读取服务端的内容，再和草稿比较，由用户选择是否恢复。等待选择期间如果账号或文档发生了变化，旧的选择不能作用于新的页面。

### 草稿迁移：先写新的，再删旧的

旧草稿没有类型信息时，当前实现会根据内容结构判断它适用的类型；类型不匹配就留在原处，不强行当作富文本恢复。用户确认后，先写入新的草稿范围，**写入成功才清理旧的副本**。

清理前还会比较旧副本是否已经被另一个标签页修改，避免删掉对方刚写入的内容。这是在 `localStorage` 上做的尽力保护，不是跨标签页的原子事务，不能说已经彻底消除了并发问题。

## 8. 结构校验和版本检查是两道不同的关卡

服务端近期为看板的新建、内容或类型变化、复制和历史恢复加入了结构检查，包括对象形状、字段类型、数量限制和已提供 ID 的重复判断。它兼容空正文和部分旧格式，并不要求所有旧记录都具备新的字段。

只修改标题或目录时，不应该顺便重写旧看板的正文。当前补丁把正文校验放在了相关的写入路径上：结构变化受到约束，没有改动的旧记录仍然可以正常操作。

- **版本检查**回答：“你是不是基于过期的状态在修改？”
- **结构检查**回答：“这份内容能不能被正确解析和保存？”

通过其中一道，并不能代替另一道。

历史对比也要区分“展示的文本”和“比较的依据”：同名的附件换了 ID、同名的图片换了来源，展示的名称可能一样，但内容仍然应该被判断为发生了变化。当前的预览读取文字和附件名称，不会主动加载历史附件的内容。

## 9. 坑五：保存正文时，把目录位置搬了回去

**现象**：一个标签页打开着文档，另一个标签页把它移动到了别的目录。第一个标签页保存正文后，文档又回到了原来的目录。

**原因**：第一个页面保存时，把所有旧字段（包括旧的父级目录）原样发了过去，覆盖了新的目录位置。

**修复**：当前编辑会话**只在用户主动修改了父级时**，才把这个字段放进提交的载荷里。目录刷新可以同步用户没有主动修改的字段，但不能覆盖表单里用户已经选择、尚未提交的目录。

“只提交本次修改的字段”减少了无意的覆盖；服务端的状态版本检查仍然必不可少，两者缺一不可。详见 [快照同步与并发冲突](/practice/notes-sync-consistency)。

## 10. 坑六：本地草稿写入失败了，界面却显示“已安全保存”

当前页面有站内路由离开和参数切换的保护，浏览器刷新或关闭前也有提示，并处理了保存快捷键。普通笔记的同步层还能区分“有待同步的内容”和“待同步的内容没能写入本机缓存”。

但知识库草稿的底层存储虽然会返回写入失败，当前的调用链并没有把所有失败都转成明确的提示。所以**不能说“每次输入都有可靠的备份”**。建议补充“本地草稿不可用”的状态，并在重要的离开操作前明确提示。

`beforeunload` 也不能保证在每一次崩溃或系统强制关闭时都会触发。可靠的设计应该在编辑过程中持续保留恢复信息，而不是把最后一次保存寄托在关闭页面的那一刻。

## 建议优先验证的交错顺序

- [ ] A 保存中继续输入 B：A 成功后，B 仍然显示未保存
- [ ] 连续提交多次：同一内容的写入按顺序执行，最终保留最新的快照
- [ ] 请求失败后重试：不会无限循环，不丢失较新的待提交内容
- [ ] A → B → A 快速切换：第一次 A 的迟到响应不会回填
- [ ] 草稿恢复弹窗期间换号或换页：旧的选择无效
- [ ] 另一个窗口修改了正文或移动了目录：基于旧基线的提交进入冲突流程
- [ ] 本地存储写入失败：不能显示“已安全保存在本机”
