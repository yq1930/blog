# 旧系统怎么改：不推倒重来的渐进式路线

一个项目能稳定运行很多年，说明它解决了大量真实的问题。技术栈旧并不等于必须重写。真正需要解决的问题是：**每次修改，都不确定会影响到哪里**。

本文根据一个同时存在 PHP/Yaf、Vue 2、Webpack 3/4、原生小程序和 Vue 3/Vite 子项目的真实工程环境整理，示例已经删除内部名称和业务实现。

::: tip 读完这篇你会
- 判断一个旧项目应该重构、升级还是局部重写
- 在几乎没有测试的情况下，先建立第一层保护
- 先统一请求、错误和身份这些“边缘”，再逐步整理内部
- 让旧技术和新技术共存，而不是互相拖累
:::

## 1. 原理：边通车边修路

城市里改造一座老桥，通常不会把桥封掉、拆了重建，而是**一边保持通车，一边分段施工**：先搭好临时车道，再改造一半桥面，验证没问题后把车流切过去，再改造另一半。任何时候出了问题，都能把车流切回原来的路线。

旧系统的改造也一样：

```text
阶段 1：固定现有行为      ← 先知道“现在是什么样”
      ↓
阶段 2：统一系统边缘      ← 搭好“临时车道”：请求层、入口、身份、第三方调用
      ↓
阶段 3：迁移一条完整流程  ← 先改一段桥面，能随时切回
      ↓
阶段 4：再升级框架和工具  ← 最后才动“地基”
```

“边缘”指的是客户端的请求层、服务端的入口、身份处理和第三方调用。这些位置最容易隔离变化，也最适合作为第一步。

## 2. 先别急着重写

下面这些现象在旧项目里很常见：

- 控制器很长，SQL 和业务判断混在一起；
- Vue 入口里注册了很多全局组件；
- 一个路由文件有几千行；
- 请求方法挂在 `Vue.prototype` 上；
- 旧构建只能在特定的 Node 版本下运行；
- 多个小程序复制了相似的登录和请求代码。

它们说明系统需要治理，但不代表“重新做一套”一定更快。重写要重新发现所有隐藏的业务规则，还要处理新旧数据、双写、灰度和回滚。**在没有可靠的行为测试时，重写只是把已知的问题换成了未知的问题。**

| 现状 | 优先做法 |
| --- | --- |
| 业务规则经常变，没人说得清完整行为 | 先补日志和特征测试 |
| 某个模块输入输出清楚，数据也独立 | 可以局部重写 |
| 只是构建工具太旧 | 先固定可用环境，再逐项升级 |
| 多个客户端对接口的理解不一样 | 先统一请求适配和错误结构 |
| 核心写流程经常重复或状态不明 | 先处理幂等、事务和状态流转 |
| 模块之间随意修改同一批表 | 先明确数据的所有者，不急着拆微服务 |

## 3. 阶段一：固定现有行为

### 让旧项目能重复构建

先记录并固定：

- PHP、扩展和操作系统的要求；
- Node 与 npm 的版本；
- 依赖锁文件；
- 构建命令和产物目录；
- 环境变量的名称（不记录真实值）；
- 发布顺序和回滚方式。

旧项目常被 `node-sass`、旧 Webpack 插件或原生模块卡住。**先让 CI 能稳定复现当前的构建，再谈升级。**

### 补一小组高价值的测试

不用一开始就追求高覆盖率，先保护最重要的几条路径：

```text
登录 → 查询列表 → 查看详情
创建 → 提交 → 再次查询
同一操作提交两次 → 只产生一个结果
登录失效 → 只恢复一次
外部调用超时 → 本地状态仍能查询
```

还可以给旧接口写**特征测试**：它不评价旧行为好不好，只是把当前的真实表现记录下来，确保重构前后没有意外的变化。

```js
it('keeps the legacy empty-list shape', async () => {
  const result = await legacyClient.fetchList()
  expect(result).toEqual({ items: [], total: 0 })
})
```

发现旧行为本身有问题时，单独修复，不要悄悄夹在重构里。

## 4. 阶段二：统一系统边缘

### 统一客户端请求层

大型 Vue 2 项目里常见三种请求方式：独立的 API 模块、全局原型方法、自己封装的 XHR。不用一次全部替换，先在外面包一层稳定的接口：

```js
export async function request(options) {
  try {
    const raw = await legacyTransport.send(options)
    return normalizeSuccess(raw)
  } catch (error) {
    throw normalizeError(error)
  }
}
```

新页面只调用 `request`，旧页面继续工作。等调用点逐步迁移完，再删除旧的入口。统一后的结构见 [跨端 API 契约](/practice/cross-client-api-contract)。

### 让服务端入口只做四件事

```text
1. 解析输入
2. 建立当前用户上下文
3. 调用一个业务用例
4. 返回统一结果
```

简化后的 PHP 写法：

```php
final class SubmitController
{
    public function __invoke(HttpRequest $request): HttpResponse
    {
        $context = $this->contexts->fromRequest($request);
        $command = SubmitCommand::fromArray($request->body());
        $result = $this->submit->execute($command, $context);

        return $this->responses->success($result);
    }
}
```

一开始，`$this->submit` 内部仍然可以调用旧的模型。重要的是，入口和页面先依赖一个稳定的边界，内部才能安全地替换。

## 5. 阶段三：选一条业务流程做试点

不要从“整理所有目录”开始。选一条完整的、风险适中的业务流程：

```text
页面提交
  → API
  → 权限检查
  → 业务规则
  → 数据写入
  → 外部通知
  → 页面查询最终结果
```

适合做试点的流程：输入输出清楚；有真实价值，但不是风险最高的核心；可以用功能开关只开放给少量用户；有明确的验证指标；能快速切回旧路径。

### 用功能开关切换新旧路径

```php
if ($flags->enabled('new_submit_flow', $context->tenantId)) {
    return $this->newFlow->execute($command, $context);
}

return $this->legacyFlow->execute($command, $context);
```

功能开关需要有：默认状态、修改权限和审计、新旧路径的指标对比、关闭后的回退结果、计划删除的日期。迁移完成后要及时清理，开关越多，系统的状态越复杂。

### 数据结构怎样安全迁移

使用“先加、再迁、后删”的顺序：

```text
增加新字段或新结构
  ↓
新旧代码都能读
  ↓
由一个写入适配层同时维护新旧结构
  ↓
小批量回填历史数据
  ↓
持续校验新旧结果
  ↓
切换读路径并观察
  ↓
停止写旧结构
  ↓
确认稳定后删除旧结构
```

迁移期间仍会有新的请求写入，所以双写必须集中在一个适配层，并有差异监控，不要让每个控制器各写一份。回填任务要能重复执行、保存进度、限制对数据库的压力，不要用一个超大的事务一次搬完。

## 6. 阶段四：最后才升级框架和工具

满足下面这些条件后，升级会安全很多：

- 构建环境已经固定；
- 核心流程有冒烟测试；
- 请求和错误有统一的适配层；
- 页面不再直接依赖大量全局方法；
- 新旧路径可以切换；
- 出问题时知道该看哪些指标。

## 7. Vue 2 和小程序项目先整理什么

**让 `main.js` 只负责启动**：根入口注册路由、Store、监控和少量全局样式；业务弹窗和页面专用的组件，在模块内部引入。

**把大路由按业务区域拆开**，先拆文件、不改 URL：

```js
import accountRoutes from './modules/account'
import reportRoutes from './modules/report'

export default new Router({
  routes: [...accountRoutes, ...reportRoutes]
})
```

每个路由使用统一的元信息（标题、权限、是否缓存）。路由守卫只处理登录和权限，不负责所有页面的数据加载。

**一端只选一个主要的 UI 库**：历史页面继续使用已有的组件库，新页面明确默认选择。确实要混用时，通过业务组件包一层，不让每个页面直接调用三种不同的弹窗 API。

**多个小程序减少复制**，可以把代码分成三类：

```text
纯逻辑：金额、日期、校验、状态转换
运行时适配：request、storage、login、upload
具体页面：主题、导航、内容和交互
```

优先共享纯逻辑和协议定义，品牌页面和平台生命周期不必强行共用。工作区里已经出现了 Vue 3、Vite 或 uni-app 子项目，也不代表旧的原生项目必须立刻迁移：先让新旧项目遵守同一套接口和错误语义，再判断哪些功能值得迁移。

## 8. 常见错误

### 坑一：一次升级所有依赖

**现象**：在一次提交里同时升级了 Node、Webpack、Vue、UI 组件库和样式工具，构建失败或页面行为异常，却无法判断是哪一层引起的。

**修复**：每次只升级一个层次，并保留可以对比的旧产物。升级前后用同一组冒烟测试验证。

### 坑二：只移动了文件，依赖关系没变

**现象**：把控制器的内容原样复制到了 `service` 目录，看起来分层了，但新的服务依然读取全局的请求对象、随意修改其他模块的数据。

**修复**：分层的标志不是目录名，而是依赖方向：服务不读取 HTTP 请求对象，只接收明确的参数；每张表有明确的所有者模块。

### 坑三：用微服务解决代码混乱

**现象**：为了解决代码混乱，把一个模块拆成了独立服务，结果多出了超时、重试、分布式一致性等一堆新问题，原来的混乱一点没少。

**修复**：先在单体内部把边界理清楚，拆服务是边界清晰之后的事，见 [服务边界与业务编排](/backend/service-design)。

### 坑四：新旧代码永久双写，兼容层变成了永久代码

**现象**：为了平滑迁移加的兼容层和双写逻辑，两年后还在，每次改规则都要改两套。

**修复**：兼容层和双写在创建时就要有**使用量统计和删除条件**（比如“旧入口调用量连续 30 天为零后删除”），并写进任务清单。

## 9. 参考节奏

下面是一个可以参考的节奏，实际进度根据团队规模和业务压力调整，不必照搬：

| 阶段 | 主要工作 |
| --- | --- |
| 起步 | 固定构建环境；画客户端—业务能力表；加 `requestId` 和错误分类；选 5 条核心冒烟流程；选定一个试点 |
| 推进 | 统一客户端请求适配；让服务端入口变薄；包装第三方 SDK；为试点补特征测试和契约测试；在功能开关后运行新路径 |
| 收尾 | 对比新旧路径的指标；演练回滚；清理没有流量的兼容代码；把方法复制到第二个功能；单独制定工具链升级计划 |

## 排查思路：改造后出了问题

1. **先切回旧路径**：关闭功能开关，确认问题是否消失，先止血再排查。
2. **对比新旧路径**：用同一份输入分别走新旧路径，比较返回结果、写入的数据和外部调用。
3. **看特征测试**：哪一条特征测试失败了，就是哪一处行为发生了变化。
4. **数据迁移问题**：查看差异监控，定位是回填、双写还是读路径切换出的问题。

## 检查清单

- [ ] 重构前后的行为有测试对比
- [ ] 新路径有日志、指标和错误分类
- [ ] 可以按小范围逐步开启，关闭开关能安全返回旧路径
- [ ] 数据迁移可以暂停和继续
- [ ] 兼容逻辑有使用量统计和删除日期
- [ ] 每次只升级一个层次的依赖
- [ ] 生产配置和凭据没有写进仓库
- [ ] 团队能用同样的方法处理下一个功能
