# 遗留系统渐进式治理：不推倒重来的现代化路线

遗留系统通常不是“旧技术写成的坏系统”，而是已经承载真实业务、积累大量例外规则、又必须持续交付的系统。它的问题往往不是某个框架版本低，而是变化成本不可预测：改一处会影响哪些端不清楚，失败后在哪里恢复不清楚，重复实现之间谁是准则也不清楚。

现代化的首要目标不是换技术，而是让改动变得可理解、可验证、可回滚。只有做到这一点，框架和运行时升级才会从赌博变成普通工程工作。

> 文中目录、模块、接口与代码均为独立示例，不映射任何具体项目。

## 先判断：系统真的需要重写吗

下面几种信号经常让团队产生“重写会更快”的冲动：

- 控制器很长，业务逻辑和 SQL 混在一起；
- 多个客户端有相似页面，却各自维护请求和状态；
- 旧构建工具只能在特定 Node 版本运行；
- 全局组件、插件和工具函数越来越多；
- 接口依靠特殊参数、文本错误和历史兼容分支；
- 自动化测试很少，发布依靠人工回归。

这些信号说明需要治理，却不直接证明需要重写。重写项目必须重新发现所有隐含规则，并在新旧系统并行期间处理双写、数据迁移和渠道切换。除非边界足够独立、行为已有可靠测试、数据迁移可演练，否则风险通常高于渐进式改造。

一个更实用的判断表：

| 情况 | 优先策略 |
| --- | --- |
| 业务仍频繁变化，规则没有稳定规格 | 先补观测与特征测试 |
| 局部模块边界清楚、数据独立 | 可抽取或重写该模块 |
| 只是构建链老旧 | 固化环境后分步升级工具链 |
| 多端协议不一致 | 先建适配层和契约测试 |
| 核心写流程不可回滚 | 先治理事务、幂等和审计 |
| 所有模块共享同一数据库且互相写表 | 先明确数据所有权，不直接拆服务 |

## 现代化的四个结果指标

不要用“迁移了多少文件”衡量进度。更有意义的是：

1. **定位时间**：从收到问题到确定责任模块需要多久；
2. **变更半径**：一个需求需要同时修改多少入口和重复实现；
3. **验证时间**：从提交代码到获得可信反馈需要多久；
4. **恢复时间**：上线异常后能否快速停用、回滚或补偿。

技术升级只有改善这些指标，才算真正完成现代化。

## 第零阶段：保护现场

在修改结构之前，先让现有系统可重复运行。

### 固化构建环境

记录并锁定：

- PHP、扩展、Web 服务器和操作系统约束；
- Node、npm、Python 等构建时运行时版本；
- 依赖锁文件和包源；
- 必需的环境变量名称，不记录真实值；
- 各端构建命令、产物目录和部署顺序。

旧前端常被 `node-sass`、旧 Webpack 插件或原生模块卡住。第一步不是一口气升级所有包，而是用版本管理和 CI 容器把“还能构建”固定下来。

### 建立最小冒烟基线

选择 5～10 条高价值流程，不追求覆盖全部页面：

```text
登录 → 查询列表 → 查看详情
创建草稿 → 提交 → 再次查询
重复提交同一操作 → 只产生一个结果
会话过期 → 回到登录且不丢失安全状态
外部服务超时 → 本地状态可解释、可恢复
```

这组基线是后续改造的安全绳。没有基线，重构前后即使都能运行，也无法证明行为没有变化。

### 加入最小观测

先统一 `requestId`、错误分类、关键动作日志和版本标识。不要等到新架构完成才做监控；迁移期间最需要知道请求落到了新路径还是旧路径。

## 第一阶段：先统一边缘，不动核心

“边缘”是变化频率高、又能隔离外部差异的位置：客户端请求层、服务端入口层、身份适配和第三方网关。

### 客户端请求适配层

将散落的基础地址、公共参数、会话恢复和错误提示收敛到一个传输层，再向页面暴露稳定方法：

```ts
interface Transport {
  send<T>(request: ApiRequest): Promise<ApiResult<T>>
}

interface ApiResult<T> {
  data: T
  requestId: string
}
```

旧接口可能使用查询参数会话、表单编码或不同成功字段。适配层可以暂时兼容，但对页面只提供统一结果。兼容逻辑应记录使用量和计划删除日期。

### 服务端入口适配层

让每个渠道入口只完成四件事：解析输入、建立身份上下文、调用用例、映射响应。即使业务逻辑暂时仍在旧类中，也先用一个应用服务包住它。

```php
final class SubmitController
{
    public function __invoke(HttpRequest $request): HttpResponse
    {
        $context = $this->contextResolver->resolve($request);
        $command = SubmitCommand::fromArray($request->body());
        $result = $this->submitUseCase->execute($command, $context);

        return $this->responses->success($result);
    }
}
```

这是“绞杀者”改造的起点：新旧实现都藏在稳定边界后，调用方不需要知道内部正在迁移。

### 第三方网关

支付、消息、文件、身份平台等 SDK 不应直接出现在业务用例中。先定义团队自己的窄接口：

```php
interface PaymentGateway
{
    public function request(string $operationId, Money $amount): PaymentResult;
    public function query(string $operationId): PaymentStatus;
}
```

接口使用业务需要的概念，而不是完整复制第三方 SDK。这样更换供应方、模拟失败和实现补偿都会更容易。

## 第二阶段：以业务切片提取用例

不要从“把所有控制器改薄”开始大规模机械搬运。选择一条有明确输入、结果和状态变化的业务切片，逐步提取。

### 提取顺序

```text
现有入口
  │
  ├─ 写特征测试固定现有行为
  ├─ 提取输入对象与结果对象
  ├─ 提取应用用例
  ├─ 把 SQL 包进仓储接口
  ├─ 把外部调用包进网关
  └─ 在开关后切换到新实现
```

“特征测试”不判断旧行为是否优雅，只记录当前对外可观察行为。发现明显缺陷时，先把缺陷作为独立变更处理，避免在重构中悄悄改变业务。

### 选择第一个切片

理想的试点应：

- 有实际价值，但不是最高风险的资金核心；
- 输入输出比较清楚；
- 可在单个租户、渠道或功能开关下灰度；
- 有明确成功指标和回滚路径；
- 能暴露真实的数据库与外部依赖模式。

不要选择纯展示页，因为它验证不了事务和副作用边界；也不要一上来选择系统最复杂的结算流程。

## 第三阶段：建立依赖方向

遗留系统的“共享库”容易变成所有模块都能引用、也能被所有模块反向引用的中心。治理重点不是移动目录，而是控制依赖方向。

```text
入口层 ─────▶ 应用层 ─────▶ 领域层
  │              │              ▲
  │              ▼              │
  └────────▶ 基础设施适配器 ──────┘
```

可执行规则包括：

- 控制器不能直接访问数据库连接；
- 领域对象不能读取全局请求和会话；
- 外部 SDK 只能在网关适配器中出现；
- 新模块不能引用旧模块的控制器；
- 跨模块写数据只能调用所有者提供的用例或端口。

一开始不必修复全部历史违规。对新增和修改代码执行“童子军规则”：碰到的边界至少不再恶化，并逐步加静态检查阻止新违规。

## 第四阶段：治理核心写流程

结构整洁不等于业务可靠。资金、库存、名额和状态流转需要单独治理。

### 明确状态机

用允许转换表替代散落的 `if`：

| 当前状态 | 动作 | 下一状态 | 操作者 | 副作用 |
| --- | --- | --- | --- | --- |
| draft | submit | pending | 创建者 | 记录待审核事件 |
| pending | approve | approved | 审核者 | 创建后续任务 |
| pending | reject | rejected | 审核者 | 通知创建者 |
| approved | cancel | cancelled | 授权角色 | 发起补偿 |

数据库更新必须同时约束当前状态，避免两个并发请求都以为自己有权转换。

### 分开本地事务和外部副作用

本地数据写入和 outbox 放在同一事务；第三方调用由可重试任务执行。每次外部操作使用业务幂等键，并保留请求摘要、响应摘要和最终状态，避免只记录“调用失败”。

### 为恢复而设计

每种中间状态都要回答：

- 谁会继续推进它？
- 多久未推进算异常？
- 自动重试多少次？
- 人工补偿需要哪些上下文？
- 补偿本身是否幂等？

只有成功路径的状态机不是完整状态机。

## 第五阶段：Vue 2 客户端先治理再升级

Vue 2 大型项目的问题通常不是 `Options API` 本身，而是全局注册、路由巨石、隐式状态和请求逻辑扩散。

### 收敛应用入口

`main.js` 只负责装配根能力：路由、状态、国际化、错误监控和少量全局样式。业务弹窗、页面专用组件和领域服务不应在应用启动时全部注册。

可以建立注册预算：新增全局组件必须说明为什么所有业务模块都需要它，以及它对首屏体积的影响。

### 路由按领域拆分

大路由表先按领域拆文件，不改变 URL。每个路由元信息使用统一 schema，例如：

```ts
type RoutePolicy = {
  title: string
  permission?: string
  cache?: boolean
  layout: 'admin' | 'mobile' | 'blank'
}
```

路由守卫只负责身份、权限和导航级策略；页面数据加载留在页面或领域服务，不把所有逻辑放入全局守卫。

### 组件库按场景划边界

PC 端以桌面组件库为默认，移动端以移动组件库为默认。混用时通过业务组件封装，而不是让页面直接依赖多个库的弹窗、表单和消息 API。

```text
页面
  ▼
领域组件（CustomerPicker / MoneyInput）
  ▼
设计适配器（DesktopDialog / MobileSheet）
  ▼
具体 UI 组件库
```

这样升级组件库或统一交互时，变化集中在适配层。

### 先升级可独立验证的工具

推荐顺序通常是：

1. 建立依赖和构建基线；
2. 替换已停止维护且有安全风险的小工具；
3. 升级 lint、测试和类型检查等开发工具；
4. 替换原生编译依赖；
5. 升级打包器和加载器；
6. 最后评估框架主版本迁移。

不要在同一个提交里同时升级 Node、Webpack、Vue、UI 组件库和 CSS 预处理器。失败时将无法定位是哪一层改变了行为。

## 第六阶段：原生小程序减少复制，不强求一套代码

多个原生小程序常有相似的登录、请求、上传、空态和弹窗。直接复制最省开始时间，却会让安全修复和协议调整需要逐项目重复。

先区分三层：

```text
纯逻辑核心：金额、日期、状态转换、校验规则
运行时适配：request、storage、login、upload、analytics
品牌与页面：主题、路由、内容、具体交互
```

纯逻辑核心可以通过本地包、构建复制或生成方式共享；运行时适配保持薄；品牌页面保留独立。不要为了共享，把所有项目变成一个充满条件判断的超级小程序。

共享代码必须有版本和变更记录。复制脚本如果没有来源标记和一致性检查，只是把手工复制自动化，仍然会漂移。

## 第七阶段：把测试放在边界上

遗留系统不适合一开始追求高单元测试覆盖率。优先测试高风险边界：

| 测试类型 | 首要对象 |
| --- | --- |
| 特征测试 | 旧接口当前行为、边缘输入、错误映射 |
| 契约测试 | 多客户端共享的请求、响应和错误 |
| 单元测试 | 状态机、金额、权限、时间窗口等纯规则 |
| 集成测试 | 事务、锁、仓储、outbox、幂等表 |
| 端到端冒烟 | 登录与少量核心垂直切片 |
| 失败注入 | 超时、重复回调、进程中断、任务重试 |

测试数量不是目标。目标是让下一次改变边界时能尽快得到可信反馈。

## 功能开关和双轨运行

迁移路径应允许按租户、渠道或稳定哈希逐步启用新实现：

```php
if ($flags->enabled('new_submit_flow', $context->tenantId)) {
    return $this->newFlow->execute($command, $context);
}

return $this->legacyFlow->execute($command, $context);
```

开关需要：

- 默认值和失效行为；
- 谁可以修改；
- 修改审计；
- 新旧路径指标对比；
- 删除日期。

不要长期保留无主开关。每个开关都是一个额外系统状态，会增加测试组合。

影子读取可以对比新旧查询结果，但不能让影子路径产生真实写入或第三方副作用。差异日志也要脱敏，并设置采样和保留期限。

## 数据迁移使用扩展—回填—切换—收缩

字段或表结构迁移不要依赖一次停机完成：

1. **扩展**：增加新结构，旧代码仍可运行；
2. **双读或双写**：通过单一适配层兼容，记录差异；
3. **回填**：小批量、可重入地迁移历史数据；
4. **校验**：比较数量、校验和与业务不变量；
5. **切换**：读路径转向新结构，保留回退能力；
6. **收缩**：观察稳定后删除旧路径和旧结构。

回填任务应以主键范围或游标推进，保存 checkpoint，并限制数据库压力。不要用一个超大事务迁移全部数据。

## 一个可执行的 90 天路线

### 第 1～2 周：基线

- 固化构建与部署环境；
- 建立关键流程冒烟；
- 统一请求标识和版本标识；
- 盘点客户端—能力—接口矩阵；
- 选定一个试点切片。

### 第 3～5 周：边缘收敛

- 客户端统一请求与错误适配；
- 服务端统一响应与上下文解析；
- 第三方调用增加窄网关；
- 对旧协议分支增加使用量监控；
- 为试点补特征与契约测试。

### 第 6～9 周：业务切片

- 提取应用用例和输入对象；
- 明确事务与状态机；
- 为外部副作用增加 outbox 或可恢复任务；
- 在功能开关下灰度新路径；
- 演练关闭开关和数据补偿。

### 第 10～12 周：复制方法

- 复盘试点的周期、缺陷和回滚成本；
- 把依赖规则、模板和检查加入 CI；
- 选择第二个相似切片复用方法；
- 删除已无流量的兼容逻辑；
- 制定工具链升级的独立计划。

这个路线的产出不是“一个新架构目录”，而是一条已经验证的低风险迁移路径。

## 风险登记表

每个治理项都应记录风险与缓解措施：

| 风险 | 早期信号 | 缓解措施 | 回退方式 |
| --- | --- | --- | --- |
| 新旧结果不一致 | 影子对比差异上升 | 暂停扩大灰度，分析固定样本 | 关闭功能开关 |
| 构建升级导致兼容问题 | 旧浏览器错误率上升 | 浏览器矩阵与产物对比 | 恢复旧构建产物 |
| 双写产生数据漂移 | 校验任务出现不变量失败 | 单点写入、补偿任务 | 读回旧结构 |
| 登录适配形成循环 | 401 与跳转次数激增 | 单航班恢复和最大尝试次数 | 使用旧身份路径 |
| 任务重试产生重复副作用 | 同一 operationId 多次成功 | 幂等键与结果查询 | 停止消费者并人工核对 |

## 哪些“现代化”做法容易适得其反

### 只搬目录，不改变依赖

把长控制器内容复制到 `service` 文件，不会自动形成服务边界。判断标准是新服务能否只通过明确输入输出测试，以及它是否仍读取全局请求或随意写多张表。

### 先建一个万能公共包

没有所有权和版本边界的公共包会把所有客户端绑在一起。先共享稳定语义和纯函数，不共享业务页面与运行时细节。

### 用微服务解决代码混乱

如果数据所有权、事务和错误语义尚未厘清，拆成网络服务只会把函数调用问题变成超时、重试和分布式一致性问题。

### 把所有升级塞进一次发布

大批依赖同时升级会把行为变化、构建变化和 UI 变化混在一起。每次升级应有单一目的、可比较产物和独立回滚点。

### 兼容代码只加不删

兼容是迁移工具，不是永久架构。没有指标、owner 和退出条件的兼容分支会让每次新变化都更难。

## 完成定义

一项现代化工作只有同时满足下面条件才算完成：

- [ ] 新旧行为差异被记录并验证；
- [ ] 新路径有日志、指标和错误分类；
- [ ] 发布可以分阶段进行；
- [ ] 回滚不会破坏已经写入的数据；
- [ ] 兼容代码有明确删除条件；
- [ ] 运维和开发文档已经更新；
- [ ] 团队能用同样方法迁移下一个切片。

## 结语

遗留系统的价值恰恰在于它已经解决了大量真实问题。治理不应该抹掉这些知识，而应把隐藏在控制器、页面、脚本和人工流程里的规则提取到稳定边界中。

先保护行为，再统一边缘；先迁移一条垂直切片，再复制方法；先让变化可观察、可回滚，再升级框架。现代化不是一次换新，而是把系统训练成能够持续改变的过程。
