# WITH 查询为什么返回空数据：重新定义 SQL 批处理结果

同一段 SQL 在数据库工具里有结果，放进报表系统却返回空数组。问题不一定在 SQL；也可能是数据库封装先看了第一个关键字，把它分到了不读取结果的路径。

本文依据一个遗留 PHP 报表服务和配套 PC 页面近期改动整理，核对日期为 **2026-10-23**。只做本地源码分析，没有连接数据库或执行任何 SQL。下面示例使用合成内容，验证项均指隔离测试环境。

## “不是 SELECT 开头”不等于“不返回表格”

旧封装根据首个关键字区分读写。它遇到 `WITH`、声明语句、前置注释或多语句批处理时，可能执行了 SQL，却没有按结果集读取。

这个最小示例就足以说明问题：

```sql
WITH sample AS (
  SELECT 7 AS value
)
SELECT value FROM sample;
```

为首词判断再加一个 `WITH` 分支，只能解决一种形式。近期修复增加了专门的批处理执行路径，不依赖首词决定是否取数，而是交由驱动结果描述来判断。

## 批处理的第一个结果不一定有列

一次执行可能先返回受影响行数，然后才返回带列的表格。近期实现约定：跳过无列结果，返回遇到的第一个有列结果集。

```text
执行批处理
   ↓
当前结果有列？ ── 是 → 读取行并返回
   │ 否
   ↓
激活下一个结果
   ├─ 还有结果 → 继续检查
   ├─ 已结束   → 无表格结果
   └─ 出错     → 失败
```

SQL Server PHP 驱动的 `sqlsrv_next_result()` 有三个不同返回值：`true` 表示成功切到下一结果，`null` 表示没有更多结果，`false` 表示切换出错。不能把后二者无条件混为一谈。[Microsoft 驱动说明](https://learn.microsoft.com/en-us/sql/connect/php/sqlsrv-next-result?view=sql-server-ver17)

PDO 也有跨行集读取能力，但应依据对应驱动及错误模式处理失败，而不是直接套用另一驱动的返回值语义。[PDOStatement::nextRowset](https://www.php.net/manual/en/pdostatement.nextrowset.php)

## “第一个有列”是协议，需要明确取舍

| 执行结果 | 按当前约定应如何理解 |
| --- | --- |
| 先出现受影响行数，再出现表格 | 跳过前者，读取表格 |
| 第一个表格有列但没有行 | 这是有效空结果，不应继续寻找非空表格 |
| 连续返回两张表格 | 只返回第一张，不能默认是最后一张 |
| 执行成功但没有任何表格 | 无表格结果，与执行失败不同 |

因此，报表 SQL 中不应随手增加调试用的前置查询，否则它可能成为被展示的第一张表。需要多张结果表时，应扩展明确的返回协议，而不是依赖开发者猜测驱动行为。

## 失败不能总被包装成空数组

近期控制器开始把初始执行返回的 `false` 转成失败响应，避免把执行错误显示为“暂无数据”。这是有价值的进步，但还不是完整错误契约。

当前驱动适配仍有把结果集切换失败或捕获到的异常转为空数组的分支。因此文章不能宣称“所有数据库错误都已经正确上报”。建议继续把下面三种结果分开：

```ts
type ReportOutcome =
  | { kind: 'table'; columns: string[]; rows: unknown[][] }
  | { kind: 'no-table' }
  | { kind: 'failure'; incidentId: string };
```

这是建议的教学模型，并非当前接口。空表属于 `table`，它与无结果集、执行失败分别表达不同事实。

服务端内部错误可以用于排障，但对用户返回原始数据库错误可能暴露表名、结构或执行细节。建议在受控日志中保留原因，对外提供可关联的错误标识；日志本身也不要无差别记录完整参数与结果数据。

## 支持 CTE 不等于允许任意 SQL

批处理读取能力只解决返回值问题，不会自动提供只读权限、租户隔离、超时限制或参数安全。前置语句仍可能有副作用，不能因最后返回了表格就把整段 SQL 当成只读查询。

对于允许维护报表 SQL 的系统，应独立核对：谁能修改语句、使用什么数据库权限、输入如何绑定、执行资源如何限制、审计如何脱敏。这些需要真实配置证据，不能靠此次兼容修复推出“已经安全”。

## 页面每页更多，不等于服务端更快

配套前端近期还调大了报表默认每页条数。它改变用户一次看到多少行，却不改变上述封装一次读取整个首个结果集的事实。

因此要分别度量数据库执行、服务端取数、网络响应大小与浏览器渲染。数据规模增大时，可以评估服务端分页或游标，但不能把 UI 分页设置当作已经实现了这些能力。

## 建议验证

- [ ] 普通查询、前置注释和 CTE 都能返回预期列与行。
- [ ] 声明、受影响行数之后的表格能够被正确读取。
- [ ] 第一张空表不会被第二张非空表替代。
- [ ] 语法错误、权限错误、超时及读取中断都不会误报成功空表。
- [ ] 多驱动部署分别验证，不假定 PDO 与 SQLSRV 行为完全一样。
- [ ] 大结果集检查内存、耗时和前端渲染，而不只看每页条数。
