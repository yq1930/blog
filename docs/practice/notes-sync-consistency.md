# 快照同步与并发冲突：怎样避免旧窗口覆盖新内容

两个常见又难查的问题：

- 在两个窗口打开同一份笔记。窗口甲改了标题并保存；窗口乙还拿着旧标题，几分钟后只修改了分类，却把整份旧快照提交了上去——甲的新标题就这样消失了。
- 甲删除了一篇笔记，乙的离线快照里还有它。网络恢复后，这篇笔记又出现在了列表里。

可靠的同步需要同时回答三个问题：**这次保存是基于哪一版？哪些操作必须一起完成？删除状态能不能被普通的保存改变？**

::: info 关于本文的“当前实现”
本文的“当前实现”来自本地源码梳理，不代表已通过线上并发验证。示例从零重写，仅表达通用方法；验证步骤是落地建议。
:::

::: tip 读完这篇你会
- 分清事务锁、版本检查和幂等重试各自能保护什么
- 理解为什么“检查版本”和“写入”必须在同一个事务里
- 把删除当作独立的业务动作，防止被旧快照复活
- 设计冲突时的用户体验，而不是无限重试
:::

## 1. 原理：合同的版本号

想象两个人在修改同一份合同的复印件。提交修改时，办事员会先问一句：“你是在第几版上改的？”如果你是在第 3 版上改的，而现在已经是第 4 版了，说明在你修改期间，别人已经改过，你的修改可能会覆盖掉别人的成果。这时办事员会拒绝你，让你先看看最新的第 4 版。

此外，办事员在核对版本号、登记修改的整个过程中，会**关上窗口**，不接待其他人，免得两个人同时核对通过、先后登记。

这就是并发控制的两个核心工具：

| 机制 | 回答的问题 | 单独使用时的局限 |
| --- | --- | --- |
| 数据库事务与锁（关上窗口） | 这一组读写怎样作为一个整体执行 | 不能自动识别客户端拿的是旧内容 |
| 版本检查（核对版本号） | 客户端的编辑基线是否已经过期 | 检查和写入分开执行时，中间仍然可能被插队 |
| 幂等或状态比较 | 重试同一个操作，应该得到什么结果 | 不能代替不同操作之间的冲突处理 |

## 2. 坑一：用了事务，还是覆盖了别人的修改

**现象**：保存接口用了数据库事务，但开头的“旧窗口覆盖新标题”问题依然存在。

**原因**：事务只保证“这次写入要么全部成功，要么全部失败”。旧快照的覆盖也可以被**完整地**提交——数据库里没有半成品，但用户的新内容丢了。事务不会去判断“你提交的内容是不是基于过期的版本”。

**修复**：在事务里加上版本检查。

## 3. 坑二：检查了版本，还是偶尔被覆盖

**现象**：加了版本号检查后，大部分情况都正常，但并发很高时偶尔还是会覆盖。

**原因**：版本检查和写入是**分开执行**的。检查通过后、写入之前，另一个请求也检查通过了，两者先后写入。

**修复**：当前实现中，普通笔记的快照覆盖和单条修改，都先获取同一账号的数据库行锁，再执行业务操作。**快照版本检查、内容变更和版本推进在同一个事务里完成。** 读取快照时也使用相同的保护，让返回的内容和版本属于同一次一致的读取，而不是分别查询后拼在一起。

```text
读取快照及其版本
        ↓
客户端编辑并携带基线版本
        ↓
开启事务 → 获取账号锁 → 比较当前版本
                          ├─ 不一致 → 回滚并返回冲突
                          └─ 一致 → 写内容、推进版本 → 提交
```

MySQL 的锁定读用于在事务中保护后续操作所依据的行，相关的锁在提交或回滚时释放。这里引用的是机制说明，并不意味着取材系统使用的正是文档对应的数据库版本。[MySQL 锁定读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

下面是教学伪代码，省略了认证、输入校验和数据库适配：

```ts
async function replaceSnapshot(owner, request) {
  return transaction(async (tx) => {
    const current = await tx.lockWorkspace(owner)
    if (current.epoch !== request.expectedEpoch) {
      throw new StaleSnapshot(current.epoch)
    }

    await tx.replaceVisibleItems(owner, request.items)
    await tx.advanceEpoch(owner)
  })
}
```

真正重要的是**三个动作共享同一个事务**，而不是函数叫什么。快照里每个对象的归属、引用是否合法，仍需另外校验。

当前实现还对全局唯一标识的归属做了写入前后的检查，避免“先查到这个 ID 没被占用，插入时却已经被其他账号占用了”的空隙变成越权更新。

### 取舍：账号锁简单，但同一账号的操作会排队

账号级别的串行化容易理解，也让整库覆盖和单条写入遵守同一个顺序。代价是：一个很大的快照会占用较长的事务时间，让这个账号的其他写操作等待。它不等于所有账号共用一把全局锁，但数据库容量、热点和索引仍然会影响整体的吞吐。

**建议**：先观察快照的体积、事务的耗时和锁等待时间，再决定是否引入增量同步。直接把锁拆得更细，可能让整库操作失去原本依赖的一致性。

## 4. 坑三：移动了目录，文档却跑到了“最近编辑”的最前面

**现象**：用户只是把文档挪到了另一个文件夹，它却出现在“最近编辑”列表的第一位。

**原因**：如果只用“最近修改时间”作为版本，移动目录就必须更新这个时间，于是排序也跟着变了。

**修复**：知识库条目还有父级、目录位置和排序，当前实现把两个概念分开：

- **内容时间**：只在标题、正文或内容类型变化时推进；
- **状态标识**：同时反映内容时间和目录位置等字段；
- 保存时携带读到的状态标识，服务端据此判断基线是否仍然有效。

状态标识由字段摘要派生，**不是正文的哈希，也不是单调递增的修订号**。正文的变化通过内容时间的推进反映到摘要中，这条写入约束不能遗漏。如果状态经历了甲 → 乙 → 甲，摘要可能回到原值：它回答的是“当前状态是否和基线相同”，不负责记录中间发生过几次操作。

当前实现还保留了旧客户端的兼容入口，版本参数并非所有请求都强制提供。因此不能把“支持冲突检测”说成“任何客户端都已经受到完整保护”。

## 5. 坑四：保存其实成功了，重试却被判为冲突

**现象**：甲的保存在服务端已经成功，但响应在回来的路上丢了。甲重试时，携带的还是旧的状态标识，于是被判为冲突，用户看到一个莫名其妙的冲突提示。

**修复**：区分“相同结果的重试”和“真正的过期覆盖”。当前的条目更新是这样处理的：

| 请求情况 | 当前条目更新的处理 |
| --- | --- |
| 版本一致，字段有变化 | 执行更新 |
| 版本过期，但提交的值已经等于当前的值 | 视为相同结果的重试，允许成功 |
| 版本过期，且提交的值会改变当前状态 | 返回冲突和最新内容 |

这条规则**不能直接套用到整库快照**上：整库保存成功后已经推进了全局版本，用旧版本重试时，当前实现仍然会要求重新读取并处理冲突。

冲突界面应该让用户能够：保留自己的修改、比较最新的内容、另存为副本，或者明确选择覆盖。把旧请求无限重发，既不能恢复丢失的基线，也不能替用户决定谁的修改优先。编辑器怎样保留未保存的输入，见 [编辑会话与本地草稿](/practice/notes-save-lifecycle)。

## 6. 坑五：删除的笔记被旧快照“复活”

**现象**：就是开头的第二个场景，已删除的内容在另一端同步后又出现了。

**修复**：**删除必须是独立的业务动作**，普通保存不能改变删除状态。当前的快照同步会保留服务端的删除状态：旧快照里仍然出现的已删除笔记，不会被普通保存恢复。服务端还会把这次跳过的对象告诉客户端，让客户端处理残留的修改。

这个返回值很重要。否则用户看到“保存成功”，实际上有一部分内容根本没有写入。

```text
旧快照包含已删除内容
        ↓
保存时检查持久删除状态
        ↓
保留删除状态 + 返回跳过清单
        ↓
客户端提示、保留副本或引导专门恢复
```

彻底删除和恢复都需要有自己的权限和范围检查。不能为了让同步方便，就让任何一次普通保存顺带恢复回收站里的内容。

## 7. 坑六：删除文件夹时，漏掉了刚新增的子项

**现象**：客户端删除一个文件夹时，把它“知道的”子节点都一起删了。但在这之前，另一个窗口刚在这个文件夹下新建了一篇文档。结果这篇文档成了没有父级的“孤儿”，在界面上找不到，又一直占着数据。

**原因**：客户端手里的子节点列表可能已经过期。

**修复**：当前实现由**服务端读取现有的关系**，展开全部后代，并用同一个批次记录删除。恢复批次时，如果原来的父级已经不存在，相关的顶层条目会回到可见的根级，避免出现“接口说恢复成功，页面上却找不到”的情况。

## 8. 不同数据，“成功”的含义不同

当前实现在真实的自动保存链路中归档旧内容，而不只在手动保存入口做历史记录。归档按时间间隔节流并限制保留数量，防止每次输入停顿都产生一份完整的正文。

**“节流归档”不等于“每一次修改都可以恢复”**。知识库在间隔内会抑制新增历史，但在明确恢复旧版本之前，会强制保留当前的内容。

界面偏好使用另一套存储，不推进正文的快照版本。偏好更新使用按键合并的方式，避免只上传了局部状态时抹掉其他设备保存的键；同一个键仍然可能后写者生效。

| 数据 | “成功”的含义 |
| --- | --- |
| 正文快照 | 对应版本的数据已被确认 |
| 历史版本 | 某个恢复点已经保留 |
| 回收站 | 删除状态已经持久化，可以按规则恢复 |
| 界面偏好 | 提交的偏好键已经合并 |

这些含义不同，不宜统一显示成一句“全部已备份”。

## 验证建议

下面是建议在隔离环境中验证的场景，不是本次已经执行过的业务测试。

| 场景 | 应该观察到的结果 |
| --- | --- |
| 两个窗口以同一快照版本提交不同的修改 | 后提交者收到冲突，已确认的内容不被静默覆盖 |
| 内容提交成功但响应丢失 | 条目重试按实际字段判断；快照重试按自己的版本规则处理 |
| 一端删除，另一端保存旧快照 | 删除不被撤销，跳过的内容有明确反馈 |
| 客户端删除整支时遗漏了刚新增的子项 | 服务端按当前的树处理，不留下隐藏的孤儿 |
| 恢复前原父级已被彻底删除 | 恢复的结果仍然出现在可见的位置 |
| 事务中途抛出错误 | 内容和版本一起回滚，不能只推进其中一项 |
| 只改变了侧栏偏好 | 不触发正文的版本冲突 |

验证冲突时，要检查**最终持久化的状态**，并确认客户端仍然保留着未提交的内容。只断言 HTTP 状态码，无法证明用户的工作没有丢失。

## 检查清单

- [ ] 版本检查、内容写入和版本推进在同一个事务里
- [ ] 读取快照时，内容和版本来自同一次一致的读取
- [ ] 内容时间和目录状态分开，移动目录不打乱“最近编辑”
- [ ] 相同结果的重试不被误判为冲突，冲突时给用户可选的处理方式
- [ ] 删除是独立的业务动作，普通保存不能恢复已删除的内容
- [ ] 整支删除由服务端按当前关系展开
- [ ] 不同数据的“成功”提示各自准确
