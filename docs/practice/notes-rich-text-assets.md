# 富文本、Markdown 和附件怎样一起保存

编辑器相关的 bug 往往看起来很“小”，却很影响信任：

- 粘贴一段代码，里面的 `user_name_id` 被渲染成了斜体，下划线不见了；
- 选择上传一个文件后又继续打字，文件卡片插到了刚输入的句子中间；
- 上传期间切换到另一篇文档，附件被插进了那篇文档；
- 文档里的附件过几天就打不开了，因为正文里存的是一个会过期的地址。

要把这些能力做稳，需要分别回答三个问题：**正文用什么格式保存？异步返回的结果还能插到哪里？附件走到哪一步才算真正可用？**

本文取材于一套笔记系统的源码。代码示例重新编写，省略了真实的业务名称和接口；“已有实现”和“建议改进”分别说明，文末的场景是建议的验证清单。

::: tip 读完这篇你会
- 分清输入格式、编辑器内部模型和保存格式
- 正确处理 Markdown 粘贴，避免误伤代码和标识符
- 让异步上传的结果插到正确的位置、正确的文档
- 用“附件 ID + 按需获取访问地址”管理附件，并分清上传、登记、保存三步
:::

## 1. 先决定正文用什么格式保存

现有编辑器支持粘贴 Markdown，但内部更新时输出 HTML，正文也以 HTML 保存。**Markdown 在这里只是一种输入方式**，不是存储格式。

```text
纯文本 / Markdown / 网页 HTML
            ↓ 按来源解析
        编辑器文档模型
            ↓ 序列化
         HTML 正文
```

理清这条链，就能理解为什么附件卡片、图片尺寸和表格需要各自的序列化规则，也能避免把“支持粘贴 Markdown”误说成“任何内容都能无损导出成 Markdown”。

现有的兼容层还会把历史上的纯文本包装成段落，再交给编辑器加载。这降低了迁移成本，但“这段内容是纯文本还是 HTML”的判断仍然依赖启发式的猜测。

**建议改进**：逐步加入明确的“内容格式”和“格式版本”字段。以后调整节点结构时，可以按版本迁移，而不必不断增加字符串猜测规则。保存确认和本地草稿的关系，见 [编辑会话与本地草稿](/practice/notes-save-lifecycle)。

## 2. 坑一：粘贴代码，下划线变成了斜体

**现象**：粘贴 `user_name_id`、文件路径或者一段代码，编辑器把其中的下划线、星号当成了 Markdown 语法，渲染成了斜体或粗体，原始字符丢失了。

**原因**：编辑器看到下划线、星号就按 Markdown 改写。可是代码、路径和标识符里也经常出现这些字符。

**修复**：现有实现关闭了通用的粘贴规则，按下面的顺序分流：

| 输入情况 | 已有处理 |
| --- | --- |
| 用户使用纯文本粘贴快捷键 | 按字面字符插入，保留换行 |
| 剪贴板包含图片文件 | 进入图片处理流程 |
| 当前位于代码块中 | 交给编辑器的默认处理 |
| 剪贴板带有 HTML | 保留默认的 HTML 解析流程 |
| 只有文本，且命中 Markdown 特征 | 交给 Markdown 解析器 |
| 其余普通文本 | 不主动转换为 Markdown |

关键在于**顺序**：从网页复制的内容通常同时提供 HTML 和纯文本，优先使用 HTML 可以保留表格和行内格式；而用户按下纯文本粘贴快捷键，就表示他已经明确选择“不要任何格式”。

Markdown 特征的识别仍然可能误判。保留纯文本粘贴的入口，就是给用户一个可预期的退出方式，而不是不断堆砌更多的正则表达式。

## 3. 自定义节点：保存的内容和显示的界面是两回事

附件在编辑器里显示为一张卡片，有文件名、大小、下载和删除按钮。但这些按钮只是交互界面，不需要全部存进正文。

现有实现把附件定义为一个独立的节点：HTML 属性中保存稳定的 ID 和展示用的元数据，节点视图负责交互。重新打开正文时，再从 HTML 恢复出节点。

Tiptap 的节点定义可以配置 HTML 的解析和序列化，这部分决定了内容怎样保存、怎样被重新识别。具体见 [官方 Node API](https://tiptap.dev/docs/editor/extensions/custom-extensions/create-new/node)。

下面是重新设计的存储示意，只表达“引用和文件本身分开存放”，不对应项目中的实际字段：

```json
{
  "kind": "file-reference",
  "resourceId": "sample-file-a",
  "label": "演示资料.pdf"
}
```

### 坑二：HTML 能恢复节点，不代表 Markdown 也能

HTML 能恢复自定义节点，并不意味着 Markdown 也能完整地恢复它。Markdown 的解析和输出需要单独定义转换规则，参见 [官方扩展集成说明](https://tiptap.dev/docs/editor/markdown/guides/integrate-markdown-in-your-extension)。

现有附件节点实现了 HTML 的读写和交互视图；本文没有把“自定义节点的 Markdown 往返转换”当作已完成的能力。如果要增加 Markdown 导出，应该先明确：附件是转成链接、保留扩展语法，还是把文件一起打包导出。

## 4. 坑三：上传期间继续打字，附件插错了位置

**现象**：选择文件后，在上传过程中又输入了几行字。上传完成后，附件卡片插在了新输入的句子中间。

**原因**：上传开始前记下了一个固定的位置数字（比如“第 120 个字符”）。之后用户的输入让文档发生了变化，原来的第 120 个字符已经不是原来那个位置了。

**修复**：现有实现使用编辑器的**选区书签**，并在每一次文档变更后映射书签的位置。上传完成后解析书签，在更新后的文档中找到正确的插入点。

```text
选择文件 → 记录选区书签 → 开始上传
                         ↓
继续编辑 → 文档发生事务 → 映射书签位置
                         ↓
上传结束 → 检查会话有效 → 在当前位置插入节点
```

可以把书签想成夹在书里的书签：不管你在前面插入了多少页，书签始终夹在原来那一页。

## 5. 坑四：切换文档后，迟到的上传结果插进了别的文档

**现象**：在文档 A 上传附件，等待期间切换到了文档 B，上传完成后附件出现在了 B 里。

**修复**：位置正确只是一个条件。已有代码在插入前还会检查：编辑器是否还存在、是否可编辑、是否仍属于同一个账号会话；图片处理另外有内容代次的检查，切换正文后会作废旧的图片结果。

这也说明了“取消请求”和“拒绝过期结果”的区别：请求可能已经完成了，但它的结果不应该再影响当前的文档。

**建议改进**：文档附件的上传也可以绑定一个明确的内容会话标识。现有的图片代次保护不能直接视为文档上传也已经具备同等的隔离，特别要关注“复用同一个编辑器实例切换正文”的场景。同样的异步边界也出现在 [AI 编辑结果的应用](/practice/notes-ai-editing) 中。

## 6. 坑五：附件过几天就打不开了

**现象**：文档里的附件刚上传时能打开，几天后点击就报错“链接已过期”。

**原因**：正文里保存的是一个临时签名地址。签名地址带有效期，过期后就无法访问了。

**修复**：现有的文档附件节点保存**稳定的附件 ID**。用户预览或下载时，客户端用 ID 去请求一个当前可用的访问地址；旧的存储方式有读取文件内容的兼容路径。

可以把附件 ID 想成门牌号，临时签名地址想成访客门禁卡：正文里应该写门牌号，每次要进门时再去前台领一张临时门禁卡。

| 概念 | 用途 | 是否应该长期写进正文 |
| --- | --- | --- |
| 附件 ID | 找到业务系统中的附件记录 | 是 |
| 展示元数据 | 显示名称、大小和类型 | 可以，但不能代替权限判断 |
| 临时签名地址 | 在有效期内读取文件 | 不应该作为永久引用 |

图片和文档的策略不同：图片可以使用公开的资源地址，文档则按附件 ID 获取访问地址。不能把“图片能直接显示”的经验推广成“所有文档都应该公开访问”。

预览还会占用浏览器资源。现有的 PDF 预览使用 Blob URL，关闭预览时释放；如果请求返回之前用户已经关闭了预览，就直接释放刚生成的 URL。文本文件按文本显示，办公文档保留下载入口。

## 7. 坑六：一个“上传成功”掩盖了后面的步骤

**现象**：界面提示“上传成功”，但附件在刷新后消失了。

**原因**：现有的文档附件流程有好几步：先取得上传许可，把文件直接传到对象存储，再向业务服务登记附件信息；登记成功后，编辑器才插入节点；最后正文还要保存。

```text
取得上传许可
  → 文件传输成功
  → 附件登记成功
  → 编辑器插入引用
  → 正文保存成功
```

可以类比寄快递：包裹放进了快递柜（文件传输成功），只能证明东西到了；在系统里登记了包裹（附件登记成功），业务系统才知道它的存在；把取件码写进你的收件记录（正文保存成功），这篇文档才真正“拥有”了这个附件。每一步确认的事实不同，任何一步失败，后面的都不算数。

**修复**：界面分别表达“正在上传”“文件上传失败”“附件登记失败”“正文尚未保存”，不要用一个“成功”掩盖后续的步骤。

现有的上传任务在失败重试时会保留附件 ID，这为服务端识别“同一次附件操作”提供了稳定的身份，但客户端的 ID 本身不能证明服务端已经具备幂等保证。

**建议改进**：

- 把“文件已经传好、但登记失败”作为一个可以恢复的状态保存下来，优先只重试登记。现有客户端会重新执行整个上传流程，可能再传一次文件；本文不把它描述成断点续传或“只重试登记”；
- 单独设计失效文件的清理机制：用户取消、关闭页面、登记失败都可能留下没有被任何正文引用的文件；但直接删除所有“当前未被引用”的文件，又可能误删正在编辑中的草稿引用。

这些改进需要业务服务和存储配合，不能只在上传按钮上补一个重试。更一般的确认边界见 [快照同步与并发冲突](/practice/notes-sync-consistency)。

## 8. 降级方案也要告诉用户代价

现有的图片上传失败时，可以回退为把图片内嵌在正文里，并提示这会占用更多的正文空间。这个方案保证了编辑的连续性，但不能保证大图片最终满足正文的长度限制。

文档附件只在上传服务被判定为“未配置”时，才使用旧的二进制兼容路径；直传或登记失败时，不会自动切换存储方式，而是报告失败、等待重试。两种降级服务于不同的条件，**不应该合并成“任何文件上传失败都放进正文”的策略**。

## 建议验证的失败场景

以下清单用于开发或测试环境的后续验证，不代表本文整理时已经执行过业务测试：

- [ ] 粘贴带格式的网页，表格和链接保持预期；纯文本快捷键能保留字面字符
- [ ] 粘贴带下划线的代码或标识符，不会被意外改成斜体
- [ ] 附件保存后重新打开，节点 ID 和展示信息仍能恢复
- [ ] 上传期间继续输入，附件插入位置随文档变化，不覆盖新内容
- [ ] 上传期间切换正文、进入只读模式或切换账号，迟到的结果不会进入错误的文档
- [ ] 文件上传成功但登记失败，错误能被识别，重试时不显示虚假的完成状态
- [ ] 附件已插入但正文保存失败，页面仍然明确显示未保存，并保留可恢复的内容
- [ ] 访问地址过期后重新请求；无权限的附件不会因为持有 ID 就被开放读取
- [ ] 预览关闭后请求才返回，临时资源被释放，且不会重新打开预览
- [ ] 图片回退为内嵌内容后检查大小限制，超过限制时保留修改并明确提示
