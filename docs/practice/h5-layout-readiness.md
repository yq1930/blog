# 接口成功后页面仍不对：H5 的数据、图片与布局就绪

接口已经返回，列表却滑不动；二维码已经拿到，海报里却没有；页面还在等定位，用户以为查询坏了。这些问题有一个共同点：把不同任务的“完成”当成了同一个时刻。

本文根据两个 Vue 2 移动 H5 项目近期的已提交修复整理，核对日期为 **2026-10-23**。案例和示例已脱敏；以下讨论来自源码，真机与业务回归清单是建议，并非本次执行结果。

## 一个 ready 不足以解释页面状态

至少要分清以下边界：

| 状态 | 已经发生什么 | 还不能保证什么 |
| --- | --- | --- |
| 数据就绪 | 接口返回了可用数据 | 列表节点已经出现 |
| DOM 就绪 | 框架完成本轮节点更新 | 图片、字体已加载 |
| 容器可见 | 弹层或页面已经显示 | 尺寸不再变化 |
| 资源结束 | 图片成功、失败或等待超时 | 所有必需资源都成功 |
| 布局测量完成 | 滚动组件取得当前尺寸 | 后续资源不会再次改变尺寸 |

Vue 2 的 `$nextTick()` 等待的是数据变化后的 DOM 更新队列，不会替你等待网络图片。这正是需要在 DOM 更新后继续处理图片事件的原因。[Vue 2 异步更新队列](https://v2.vuejs.org/v2/guide/reactivity.html#Async-Update-Queue)

## 滚不动，先检查有没有真正的滚动容器

一个商品列表原来只放在固定高度的页面里，内容变长后没有对应滚动区域。近期修复把列表放进项目已有的滚动组件，为容器设置完整高度，并将底部操作区留在滚动内容外。

这类问题不能只靠增加 `refresh()` 解决。应先确认：

- 外层高度是否有限且可计算；
- 内容是否真的超过容器高度；
- 使用原生滚动还是组件模拟滚动；
- 固定按钮有没有盖住最后一项；
- 有没有父层同时截获触摸或滚动。

该页面仍保留固定延时后刷新的实现。它是已有修复的一部分，不应被写成“等待若干毫秒就能保证布局完成”。

## 图片和弹层会让旧测量失效

另一个项目已经有滚动组件，失败原因是初始化时图片尚未撑开内容高度，或者弹层仍然隐藏。

近期修复分别补上了教程图加载、富文本配图事件、轮播图加载和弹层显示后的重新测量。部分图片入口同时处理 `load` 与 `error`，以免失败资源让布局长期停留在旧状态。

```text
数据写入 → DOM 更新 → 初次测量
                         ↑
图片结束 / 弹层显示 / 内容展开 → 再次测量
```

对于富文本内部动态出现的图片，当前代码在外层使用捕获阶段监听。普通 `load` 事件不会冒泡，不能把一个普通父级监听器误当成所有子图片都能触发的入口。[MDN load 事件](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/load_event)

重新测量与回到顶部是两件事。当前公告页面的图片回调只刷新滚动边界，不重置位置；否则用户读到一半，迟到的图片会把阅读位置拉回开头。

如果同一帧有很多图片完成，建议合并测量，而不是每次都重新计算。下面是教学示例，未宣称当前项目已采用：

```js
function createLayoutRefresh(nextTick, measure) {
  let frame = 0;
  let disposed = false;
  return {
    refresh() {
      nextTick(() => {
        if (disposed || frame) return;
        frame = requestAnimationFrame(() => {
          frame = 0;
          if (!disposed) measure();
        });
      });
    },
    dispose() {
      disposed = true;
      cancelAnimationFrame(frame);
    }
  };
}
```

使用时还应在组件销毁时调用 `dispose()`；隐藏页面的恢复策略由页面决定，不能靠持续测量代替生命周期管理。

## 海报：等待结束不等于资源完整

近期海报修复把资料、二维码和图片处理放到渲染前，等页面显示后再进行截图，并为接口失败提供重试入口。

这里仍有一个重要取舍：图片预加载失败也会结束等待，且整体等待有超时兜底。源码因此只能证明“等待有出口”，不能证明“生成时所有图片都完整”。

建议按业务价值给资源分类：

| 资源 | 适合的失败策略 |
| --- | --- |
| 决定海报用途的二维码 | 未加载成功时阻止导出，保留重试 |
| 主要内容图片 | 根据需求显示失败或明确占位 |
| 装饰背景 | 可降级，但不能覆盖内容 |

同时区分“数据加载失败”“图片不完整”“截图失败”和“上传失败”。一个统一 loading 或成功提示会掩盖具体卡在哪一步。

## 定位：不影响结果正确性时才允许后台补充

近期查询页改为先返回当前已有坐标，没有坐标就先查询；定位在后台继续，后续查询再使用结果。这解除了授权弹窗对首屏数据的阻塞。

当前实现按模块共享一次定位状态，并没有自动重试或位置有效期刷新。用户移动、授权失败后重新允许定位、长时间停留等场景，仍需单独设计。

这种做法只适合坐标是辅助信息的查询。如果定位决定可见数据、价格或业务资格，缺少定位时继续执行就可能改变语义，不能直接照搬。

## 兼容补丁必须放在依赖读取之前

另一个修复针对旧滚动库的触摸探测和系统版本比较：依赖在加载时确定设备能力，补丁必须早于它运行；组件注册会复制方法，针对组件定义的修正必须早于注册。

项目也修正了只同时比较主、次版本而导致高主版本被漏判的问题，并扩展到内部嵌套的滚动组件。临时补丁尊重页面显式配置，避免覆盖已有例外。

这说明兼容代码需要明确依赖版本和执行时机。它不是建议所有应用都伪造触摸属性或统一关闭动画；升级依赖后应重新确认是否仍需保留。

## 建议验证

- [ ] 缓存命中、慢图片、图片失败、无图片时，内容都能完整滚动。
- [ ] 图片在用户阅读中途加载，测量更新但位置不被重置。
- [ ] 隐藏弹层第一次显示和再次显示，都有正确边界。
- [ ] 关键海报资源失败或超时，不误报完整生成。
- [ ] 定位拒绝、超时、后来成功，查询行为符合业务约定。
- [ ] 真实目标设备验证触摸、鼠标和嵌套滚动，不能只用桌面模拟。
