# 私有项目怎么写成公开技术文章

真实项目比练习项目更有写作价值，因为它遇到过兼容性、历史数据、弱网和多人协作这些真实的问题。但直接复制源码，很容易顺带公开内部接口、业务规则甚至用户数据。

安全的写作不是把所有内容都写得模模糊糊，而是：**保留问题和解决方法，重新整理代码和数据。**

::: tip 读完这篇你会
- 判断哪些项目代码可以公开，哪些必须重新写
- 把真实代码缩成读者容易理解、又不泄露信息的示例
- 区分“项目已经做到的”和“文章推荐这样做的”
- 在发布前检查文本、图片和构建产物
:::

## 1. 原理：画一张新地图，而不是给照片打码

想分享一次徒步的经验，有两种做法：

- 把手机里的照片发出去，再把门牌号、车牌、路人的脸打上码；
- 重新画一张简单的路线示意图，只标出关键的路口、坡度和补给点。

第一种做法很容易漏：照片的角落里可能还有一块路牌，图片文件里可能还带着拍摄的定位信息。第二种做法从一开始就只包含你想分享的内容，**读者也更容易看懂**。

写技术文章也一样：**与其复制真实代码再“打码”，不如从零写一个只说明问题的最小示例**。

## 2. 哪些内容不能直接发布

| 内容 | 常见位置 | 处理方式 |
| --- | --- | --- |
| 密钥、Token、证书 | 配置文件、SDK、私钥文件 | 完全删除，不做打码展示 |
| 域名、IP、端口 | 环境配置、请求封装 | 改成 `example.test` |
| 客户和员工的数据 | 日志、接口响应、截图 | 使用全新的合成数据 |
| 内部的表名和字段 | SQL、模型、迁移脚本 | 为文章重新设计简单的模型 |
| 真实的业务常量 | 状态码、金额、角色编码 | 改成通用的状态和演示数值 |
| 本机路径 | 错误堆栈、终端、构建日志 | 改成相对路径 |
| 内部的品牌和模块名 | 类名、路由、图片 | 使用中性的名称 |

只删掉公司名是不够的。一个真实的接口路径、一段错误文案或者一张后台截图，都可能暴露系统的用途。

## 3. 把“取材”和“公开文章”分开

推荐准备两份内容：

```text
私有源码
  ↓ 只读检查
内部底稿：记录事实和本地出处，不发布
  ↓ 提炼问题与方法
公开文章：使用重新整理的代码和合成数据
```

内部底稿只需要写“哪个文件证明了什么”，不要把整个函数、配置值或真实日志复制进去。底稿必须放在站点的发布目录之外，并通过本地的忽略规则避免被提交。

## 4. 区分三种内容

**已验证的事实**——源码可以直接证明，例如：

```text
项目使用 Vue 2 和 Vue Router 3。
请求统一经过一个 Axios 实例。
小程序使用 app.json 声明分包。
```

**工程判断**——根据多处实现得出的结论，例如：

```text
全局入口注册内容过多，会增加启动依赖和维护成本。
```

**推荐做法**——文章提出的改进，不一定已经在项目里落地：

```text
可以增加 outbox，记录提交后仍需执行的外部任务。
```

### 坑一：把建议写成了现状

**现象**：文章写着“项目通过 outbox 保证了通知不会丢失”，实际上项目里根本没有 outbox，这只是作者的建议。

**风险**：读者以为这是经过实践验证的方案；知道内情的同事会认为文章不可信。

**修复**：文章里明确写“项目中已有”还是“建议增加”。本系列的文章都用“当前实现”“建议改进”这样的措辞区分，并在文中注明核对日期和核对方式（比如“只读源码，没有连接生产环境”）。

## 5. 坑二：只改了变量名，就当成示例发布

**现象**：

```text
复制原函数
→ 把 Customer 改成 User
→ 把真实 URL 改成 demo URL
→ 其他结构全部保留
```

**风险**：原来的控制流、特殊的业务规则、字段之间的关系都还在，懂行的人依然能看出原系统的很多信息。而且原函数往往很长，读者也很难抓住重点。

**修复**：只保留文章要解释的那个概念，**从空文件重新写**：

```js
const running = Object.create(null)

export function runOnce(key, task) {
  if (running[key]) return running[key]

  const clear = () => { delete running[key] }
  const promise = Promise.resolve().then(task).then(
    value => {
      clear()
      return value
    },
    error => {
      clear()
      throw error
    }
  )
  running[key] = promise
  return promise
}
```

这段代码只解释“同一个任务复用进行中的 Promise”这一件事，没有任何真实的业务模型和接口。用成功、失败两个分支分别清理，也能兼容不支持原生 `Promise.prototype.finally` 的旧 WebView。

适合展示的代码类型：框架入口和生命周期的典型结构；通用的请求、错误处理和提交锁；不含业务规则的路由拆分方式；纯函数（日期、金额、状态转换）；为文章重新编写的最小复现测试。

每段代码前说明它的来源，比如：

> 以下代码根据真实项目中的模式重新整理，已删除业务名称、接口参数和内部数据。

代码越短越好，读者应该一眼就能看出它证明了什么。

## 6. 坑三：给真实数据“打码”

**现象**：示例里放了一条“处理过”的真实记录：手机号中间四位换成了星号，名字只留了姓。

**风险**：剩下的信息组合起来仍然可能定位到具体的人；金额、时间的分布也可能暴露业务情况。

**修复**：使用**全新的合成数据**：

```json
{
  "actorId": "user_demo_17",
  "operationId": "op_demo_42",
  "status": "pending",
  "amountMinor": 12990
}
```

金额、时间、数量和状态都不要复刻真实的分布。

### 地址和配置怎么写

URL 使用专门保留用于示例的域名：

```text
https://api.example.test/v1/resources
```

路径使用相对目录：

```text
src/modules/example/
server/Application/Example/
```

环境变量只展示名称和无效的占位符：

```dotenv
APP_ENV=development
API_BASE_URL=https://api.example.test
SESSION_SECRET=<provided-by-deployment-platform>
```

不要为了“示例能直接运行”而放一个固定的测试密钥，它很容易被复制到真实项目里。

## 7. 坑四：截图泄露了信息

**现象**：文章里的一张截图，地址栏露出了内网域名；右上角显示着登录的账号；侧边栏的菜单暴露了系统的全部功能。

截图里常见的泄露点：浏览器地址栏；登录账号和通知；真实的菜单、品牌和客户信息；终端里的用户名和绝对路径；二维码、条码；图片文件本身携带的元数据（拍摄时间、设备、定位）。

**修复**：最安全的方法是用合成数据**重新画一张简图**：

```text
页面 → 请求适配层 → 业务服务 → 数据库
                     └──────▶ 外部服务
```

如果必须截图，使用专门的演示环境，并检查裁剪后的**原始文件**，而不是只看网页上的缩略图。

## 8. 坑五：只检查了 Markdown，没检查构建产物

**现象**：文章本身没问题，但网站的搜索索引里包含了内部底稿的内容；或者 Source Map 里带着作者电脑上的绝对路径。

**修复**：发布前做两种扫描，并检查构建产物。

**敏感特征扫描**：在本地搜索真实的项目名、域名、IP、绝对路径和密钥特征：

```bash
rg -n -i \
  'private-project|internal\.example|PRIVATE KEY|API_SECRET' \
  docs/
```

真实的敏感词清单保存在本地，不要为了扫描又把它提交到公开仓库里。

**和源码做长片段比对**：把文章里的长代码行或连续多行，和私有源码做本地的精确比对。有命中的话，确认它是否真的是可以公开的通用代码。扫描报告只输出文章的行号和来源文件，不要再次打印敏感的原文。

**检查构建产物**：搜索索引是否包含内部底稿；Source Map 是否带着本机路径；打包后的环境变量是否含有真实地址；图片附件是否带有元数据；页面和导航是否存在死链。

```text
扫描源文件
  → 本地构建
  → 检查构建日志
  → 扫描 dist
  → 打开关键页面
  → 查看 Git 待提交文件
```

## 9. 一篇文章的生产流程

1. 先确定一个通用的问题，比如“弱网下怎样防止重复提交”；
2. 只读检查直接相关的入口、工具和测试；
3. 在内部底稿记录事实和来源；
4. 提炼一个可以跨项目使用的规律；
5. 从空文件重新写最小的代码；
6. 使用合成数据和中性的名称；
7. 第一轮检查技术是否正确；
8. 第二轮**只**检查信息安全；
9. 构建并扫描最终的产物；
10. 只提交公开文章和必要的导航改动。

## 检查清单

- [ ] 文章在讲通用的问题，而不是介绍私有的目录结构
- [ ] 项目事实和推荐方案已经区分清楚
- [ ] 代码片段足够短，是重新编写的，没有业务参数
- [ ] 示例数据完全由作者生成
- [ ] 没有真实的域名、IP、账号和绝对路径
- [ ] 图片、二维码和附件已经检查过原始文件
- [ ] 内部底稿不在发布目录里，也不在 Git 暂存区
- [ ] 源文件和构建产物的敏感扫描都通过
- [ ] 站点构建和导航检查通过

公开技术文章真正应该分享的是：**问题、约束、失败的原因、解决的方法和验证的方式**。真实代码为文章提供证据，但不需要把整个真实实现搬到网上。示例越聚焦，文章越容易理解，也越安全。
