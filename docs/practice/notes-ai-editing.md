# AI 编辑的可靠性边界：生成、预览、采纳和保存

在编辑器里接入 AI 改写、续写功能，最常见的两类失败是：

- 用户选中一段文字让 AI 改写，等了一会儿关掉弹窗，继续编辑另一段。旧请求随后返回，如果直接写回编辑器，用户刚输入的内容就被覆盖了；
- AI 的结果已经完整生成，预览里也能正常显示，但插入正文后超过了保存容量。用户点了“采纳”，最后却怎么也存不下来。

这两类问题都不是换一个提示词能解决的。**生成成功、结果仍然适用、用户采纳、持久保存，是四次不同的确认。**

::: info 关于本文
本文总结当前源码能证明的行为，示例均为通用重写；建议方案会单独标明，没有把本次只读检查写成业务测试结果。

**2026-10-23 更新**：近期已提交的前后端改动补齐了主动取消、编辑目标校验和进程内并发准入。下文按新实现说明，不再把“关闭弹窗只是忽略结果”当作当前状态。
:::

::: tip 读完这篇你会
- 把 AI 编辑拆成生成、预览、采纳、保存四个阶段，各自给出准确的提示
- 让过期的结果失效，并把取消一路传递到服务端
- 分清 HTTP 字节、保存容量、模型 token 等不同的长度单位
- 拒绝“截断后假装成功”，在采纳前检查整篇文档能否保存
:::

## 1. 原理：装修方案不等于已经装修好

请设计师出一份装修方案：

1. 设计师交来方案（**生成完成**）——但方案不一定适合你家；
2. 你看了效果图（**预览**）——房子还一点没动；
3. 你决定采用这份方案（**采纳**）——施工队开工，房子变了，但还没验收；
4. 验收签字（**保存**）——这次的改动才算正式完成。

如果设计期间你又把客厅改了格局，旧方案就可能不再适用。AI 编辑也是这样：

```text
用户选择操作与内容
        ↓
提交生成任务 → 失败、超时或取消
        ↓
校验并展示候选结果
        ↓
用户采纳 → 修改编辑器、成为未保存内容
        ↓
按原有保存流程提交 → 持久化成功或冲突
```

当前 AI 服务端只返回候选结果，**不直接写正文**。选区编辑和辅助写作在用户采纳后修改编辑器，之后仍然经过页面原有的保存流程。这样用户可以放弃一次生成，保存冲突也继续由已有的机制处理。**不能因为内容来自 AI，就绕开编辑会话，或者省略保存失败的提示。**

| 阶段 | 可以告诉用户什么 | 还不能承诺什么 |
| --- | --- | --- |
| 生成完成 | 已经得到候选结果 | 内容一定正确，或者适用于当前文档 |
| 预览完成 | 可以比较、复制或采纳 | 正文已经改动 |
| 采纳完成 | 当前编辑器已经更新 | 服务端已经保存 |
| 保存完成 | 本次提交已被服务端确认 | 用户之后新增的输入也已保存 |

最后一种边界和普通编辑相同，详见 [编辑会话与本地草稿](/practice/notes-save-lifecycle)。

## 2. 坑一：旧的生成结果覆盖了新的内容

**现象**：用户关闭了改写弹窗、继续编辑，几秒后旧的改写结果突然出现，覆盖了刚输入的内容；或者连续点了两次“重新生成”，先发出的那次反而最后显示。

**修复**：前端为选区编辑和辅助写作分别维护请求序号。重新生成或关闭弹窗时，旧序号失效；响应返回后先核对序号，过期的结果不进入预览。这解决的是“这个响应还属于当前的交互吗”，而不是判断模型的答案好不好。

下面是重新编写的最小示例，只演示结果失效的机制：

```ts
function createPreviewTask(generate, show) {
  let active = null

  return {
    async run(input) {
      const ticket = Symbol('preview')
      active = ticket
      const result = await generate(input)
      if (active === ticket) show(result)
    },
    dismiss() {
      active = null
    },
  }
}
```

这不是完整的任务管理器：错误展示、加载状态清理、网络取消和组件卸载都需要额外处理。它刻意只说明一件事：**过期的结果不能更新当前界面**。

近期编辑器入口还会记录编辑器实例、文档快照、账号会话代次和原始选区。结果返回时、用户采纳时，都会再次核对目标：编辑器已销毁、账号变了、正文变了，旧结果就不再应用。

这是一种比较保守的策略：哪怕用户只改了文档的另一处，也可能让旧候选失效。它没有实现“自动重新定位”或“把 AI 结果合并到变化后的文档”；如果需要更宽松的交互，还要设计位置映射和冲突处理。

## 3. 坑二：关了弹窗，服务端还在等模型

**现象**：用户关闭了弹窗，界面上一切正常，但服务端仍然在等待模型返回，继续占用资源、产生费用。

**原因**：“界面不再显示结果”和“请求真正被取消”是两件事。

**修复**：当前编辑器在生成过程中关闭弹窗时，会作废请求序号，并调用 `AbortController.abort()`；取消信号经过 AI 服务的封装传给公共请求层，最终进入 fetch。页面离开、断网、会话失效和作用域清理时，也有相应的取消或失效处理。

服务端另有取消机制：客户端的响应连接异常关闭时，向上游请求传播取消信号。它监听的是**响应连接**，避免把“请求体读取结束”这种正常情况误判为任务取消。

| 取消的层级 | 目的 |
| --- | --- |
| 界面失效 | 不再展示或采纳这次的结果 |
| 客户端请求中止 | 结束本次网络等待 |
| 服务端传播取消信号 | 尽量不再继续等待上游 |
| 上游实际停止 | 取决于上游的协议和执行状态 |

所以，源码现在能追踪到“界面取消 → 客户端请求中止 → 响应连接断开时服务端传播取消”的链路。至于反向代理是否及时传递断连、上游是否立即停止计算和计费，还需要部署环境和供应商协议的证据，不能只凭本地代码保证。

`AbortController.abort()` 可以中止 fetch 及其响应体的读取，但不保证远端业务事务回滚，那是必须另外设计的协议边界。[MDN AbortController.abort](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort)

当前实现**同时保留**网络取消和结果归属校验。取消和响应可能几乎同时发生，任何一层都不能单独替代另一层。

## 4. 坑三：设置了超时，请求还是挂了很久

**现象**：给模型调用设置了 10 秒超时，但有的请求挂了好几分钟才失败。

**原因**：只给“建立连接”设置了超时。连接很快建立了，但模型迟迟不返回内容，或者响应体一直传不完，这些都不在超时的范围内。

**修复**：当前的模型调用集中在一个公共模块里，调用方负责构造任务内容；连接错误、超时和部分上游错误在共同的出口处理。

- **总超时要覆盖整段等待**：连接、等待响应、读取响应体都算在内；
- **每个出口都要清理**：结束时清理计时器和取消监听器，否则旧任务的计时器可能干扰后续工作，长期存在的监听器也会增加排查难度；
- **错误要分类**：区分用户主动取消、超时和上游失败，分别给出提示。

等待上限是项目自己的运行选择，不等于模型供应商对推理时长的承诺。浏览器、服务端和代理各自的超时限制需要协调一致。

## 5. 并发数和调用频率要分开管理

近期服务端把几种生成动作统一接入了一个准入模块，在完成内容校验、准备调用上游时占用资源：

| 限制 | 解决什么问题 | 什么时候释放 |
| --- | --- | --- |
| 单账号在途任务数 | 同一个用户重复提交长任务 | 本次调用结束 |
| 单进程在途任务数 | 多个用户同时把运行资源占满 | 本次调用结束 |
| 时间窗口内的调用次数 | 连续发起、取消造成高频调用 | 等待时间窗口自然过去 |

当前对超额的请求直接拒绝，不在进程里无限排队；错误信息提供可以区分的原因和建议的重试等待时间。上游即使返回了网关的 HTML 页面，“繁忙”和“限流”也有独立的处理路径，不会全部变成“响应解析失败”。

占用的资源通过 `finally` 释放，释放函数本身是幂等的，防止重复清理把计数减错。**已经发出的请求即使被取消，仍然计入时间窗口的调用次数**：归还执行槽位，不代表抹去已经发生过的调用。

这些计数还在单进程的内存里。多进程或多实例部署时会各自计数，不能说成全站共享的配额。共享限额、持久化的任务队列和跨实例的公平性，仍然是后续的设计项。

## 6. 坑四：长度单位混乱，前后端各算各的

**现象**：前端提示“内容长度合法”，后端却报“超出限制”；或者按字数估算没问题，模型却报上下文超限。

**原因**：“内容不能超过某个长度”如果不说明单位，前后端很容易各写出一种理解。至少有四种不同的单位：

| 边界 | 常见单位 | 检查的对象 |
| --- | --- | --- |
| HTTP 请求体 | 字节 | 编码后的整个请求 |
| 编辑器保存容量 | 字符串计数或字节 | 最终保存的正文，包括标记和嵌入内容 |
| 模型上下文 | tokens | 提示词、用户内容、输出预算等 |
| 文件上传 | 字节 | 文件本身 |

JavaScript 的 `string.length` 计算的是 UTF-16 码元，既不等于 UTF-8 的字节数，也不等于人眼看到的字符数，更不能当作 token 数。

**修复**：每个限制都写明单位和检查对象。当前实现把“应用的 HTML 容量”和“已识别模型的容量配置”分开：请求的原始 HTML 先受应用限制，模型端负责判断实际上下文是否超限，返回的结果清洗后再检查应用容量。这里的模型配置只代表项目读到的能力假设，适配新模型时要重新核对参数含义和完成原因。

## 7. 坑五：截断后假装成功

**现象**：长文档的改写结果缺了最后几段，或者在一个句子中间戛然而止，但界面显示“生成完成”。

**原因**：截取输入的尾部，可能丢掉用户最重要的背景；截取输出的前半段，可能留下没闭合的结构或没写完的结论。如果把这样的结果当成功返回，用户很难发现问题。

**修复**：当前对已识别的模型，写作上下文不再按旧的字符阈值静默截尾；支持思考模式的模型调用路径会识别“长度耗尽”的结束原因，**拒绝把已知不完整的结果作为成功返回**。应用容量超限时，当前路径会明确失败，而不是把清洗后的 HTML 截取一段返回；上游明确报告上下文超限时，提示用户缩小内容或拆分文档。

这个保护有明确的适用范围：未知的模型仍然保留原有的兼容限制，不能说所有供应商、所有模型都具备了同样的截断检测。

**建议**：把“缩短范围后重试”作为一个明确的用户动作。需要自动分块时，要设计段落边界、上下文衔接和结果校验，而不是藏在字符串截断里。

## 8. 坑六：候选片段没问题，追加后整篇存不下

**现象**：AI 生成的段落单独看完全合法，但插入正文后，整篇文档超过了保存容量。用户点了采纳，保存时才失败。

**原因**：一段候选结果单独不超限，不代表追加后仍然能保存；替换选区时，还要考虑被删除的内容和新内容的差额。

**建议的检查流程**：

```text
当前文档 + 本次替换或插入操作
        ↓
在临时文档上应用变更
        ↓
按持久格式序列化并检查容量
        ├─ 超限 → 保留候选结果，提示缩小范围
        └─ 合法 → 允许采纳，再走正常保存
```

这是进一步加强采纳体验的建议，**不表示当前每个采纳入口都已经实现了临时文档的预检查**。服务端的保存校验仍然是最后一道关卡，不能只依赖按钮的状态。

另外，**模型输出不是可信的 HTML**。当前结果会经过白名单清洗，但清洗不能证明事实正确，也不能代替编辑器自己的内容约束。格式和附件身份怎样保存，见 [富文本与附件生命周期](/practice/notes-rich-text-assets)。

## 验证建议

下面的场景适合在隔离环境中配合可控的响应来验证。本次整理没有调用真实模型执行这些测试。

| 场景 | 应该观察到的结果 |
| --- | --- |
| 先发甲请求、再发乙请求，甲最后返回 | 甲不能覆盖乙的预览 |
| 生成期间关闭弹窗 | 正文不变，迟到的结果不会重新打开旧预览 |
| 页面连接断开 | 服务端停止等待，计时器和监听器被清理 |
| 同一账号或进程并发超过限制 | 明确拒绝，不无限排队；已有任务不受误释放影响 |
| 请求取消后立刻再发 | 在途资源可以释放，时间窗口的调用记录仍然保留 |
| 上游明确返回“长度耗尽” | 对支持识别的路径，不显示为完整成功 |
| 返回的 HTML 含有不允许的结构 | 清洗后再检查展示内容和容量 |
| 候选片段合法，追加后全文超限 | 保留用户原文和候选结果，明确说明无法保存 |
| 采纳后发生保存冲突 | 走正常的冲突流程，不绕过版本校验 |
| 代理先于应用超时 | 错误可见，不能把“没有响应”当作“已保存” |

验证时同时观察界面状态、编辑器内容和持久化的数据。只看“AI 请求返回成功”，不足以证明这次编辑真正可靠地完成了。

## 检查清单

- [ ] 生成、预览、采纳、保存四个阶段的提示各自准确
- [ ] 过期结果通过序号和目标快照失效，采纳时再次核对
- [ ] 取消从界面传递到客户端请求和服务端
- [ ] 总超时覆盖整段等待，每个出口都清理计时器和监听器
- [ ] 并发数和调用频率分开限制，释放操作幂等
- [ ] 每个长度限制都写明单位和检查对象
- [ ] 不完整的结果不作为成功返回
- [ ] 模型输出经过白名单清洗，保存仍由服务端校验
