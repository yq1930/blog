# 笔记应用开发实践：从编辑器到可靠保存

笔记应用对用户最重要的承诺只有一句：**写下的内容能保存、能找回，切换页面和设备后也不会悄悄变回旧版本。**

听起来简单，做起来却贯穿整个系统：编辑器要分清“正在输入的内容”和“已经保存的快照”；请求层要识别出过期的会话；数据库要拒绝过期的写入；发布流程还要照顾那些一直没关闭的浏览器标签页。

本系列来自一个 Vue 3 PC 客户端及其 Express、MySQL 服务端的本地源码梳理，整理日期为 **2026-10-22**。前端使用 TypeScript、Pinia、Vue Router、Vite 和 Tiptap，通过 pnpm workspace 复用数据层；后端独立维护，通过 HTTP 与客户端通信。

::: info 怎样理解文中的“当前实现”
“当前实现”指本次所读源码能证明的行为，不代表已在生产环境验证。示例为重新编写的教学片段，目录、接口、数据与配置均做了通用化处理。验证清单是给读者落地时的建议。

## 1. 整体结构：共享数据能力，界面留给客户端

当前前端没有把所有逻辑塞进 PC 页面。类型定义、请求、认证、普通笔记和知识库的 store 放在共享包里；PC 包负责页面、编辑器、浏览器交互和自己的界面状态。

```text
PC 页面、组件与路由
        │
编辑会话、离开保护、上传交互
        │
共享 store、同步协调器、请求与会话
        │ HTTP
路由与身份检查
        │
业务存储、事务与版本检查
        │
MySQL / 对象存储 / 模型服务
```

### 共享层只“发通知”，不决定“怎么提示”

共享包需要告诉界面“同步失败了”，但它不应该决定 PC 端显示哪种提示条。当前的实现是：客户端在入口处把“显示加载状态”“显示同步状态”的回调函数注入给共享层，共享层只负责调用。

这样数据逻辑可以在不同客户端复用，共享层也不会为了显示一个提示而反过来依赖某个端的组件。

这个设计有一个前提：**每个运行环境只装配自己的一套处理函数**。如果以后需要在同一个页面里运行多个应用实例，建议把模块级的回调改成按实例传入；本次源码不能据此说明已经支持多实例隔离。

## 2. 原理：按状态的“寿命”划边界

“这个变量应该放在组件里还是 Pinia 里？”这个问题常常让人纠结。换一个更具体的问法就清楚了：**它什么时候产生、什么时候失效、谁有资格修改它？**

可以把状态想成家里的物品：便利贴上的临时记录、抽屉里的日常物品、保险柜里的重要文件，放在不同的地方，是因为它们的“保质期”和重要程度不同。

| 状态 | 当前由谁负责 | 寿命 |
| --- | --- | --- |
| 当前账号与会话代次 | 认证与会话层 | 登录、退出、失效或换号 |
| 已确认的目录与条目 | 共享 store | 数据加载、更新、会话重置 |
| 标题、正文、尚未保存的父级选择 | 编辑会话 | 从打开某一条内容到离开 |
| 尚未提交的草稿 | 本机存储 | 按账号和内容范围保留 |
| 当前弹窗、侧栏、加载状态 | PC 界面层 | 当前页面或客户端实例 |
| 用户数据的版本与删除状态 | 服务端存储 | 以事务确认的持久状态 |

当前的编辑会话集中处理表单、加载、保存快照和草稿；页面只保留“要不要离开、要不要覆盖、要不要放弃”这些需要用户决定的事情。这样的拆分，比把一个大页面机械地拆成十个文件更有意义。

Vue 官方把组合式函数定义为“封装和复用有状态逻辑的函数”，但其中的副作用仍然需要对应的清理。**把代码放进组合式函数，本身并不会自动消除竞态问题。**[Vue Composables](https://vuejs.org/guide/reusability/composables.html)

## 3. 坑：给所有操作都显示“保存成功”

**现象**：看板里拖动了一张卡片，界面提示“已保存”，刷新后卡片却回到了原来的位置。

**原因**：系统里有几类看起来很像、但“保存”含义完全不同的操作：

| 操作 | 当前实现 | “成功”意味着什么 |
| --- | --- | --- |
| 普通笔记编辑 | 本地更新后进入自动同步 | 服务端确认了对应的快照 |
| 知识库文档编辑 | 手动保存，另有防抖的本地草稿 | 本次提交的内容保存成功 |
| 看板内拖动卡片或列 | 修改的是条目正文里的结构化内容 | 仍然需要保存这条看板 |
| 知识库目录移动 | 针对条目单独提交位置变化 | 服务端确认了目录变化 |
| AI 生成 | 先得到一份可预览的结果 | 还没有被采纳，更没有被保存 |

**修复**：不要给所有模块套用同一个“自动保存成功”的提示。提示文案应该能回答：**保存在了这台设备上，还是已经上传？保存的是哪一版？之后是否还有新的修改？**

## 4. 后端：入口负责装配，事务负责一致性

当前后端把“构造应用”和“启动应用”拆开了：前者组装中间件、路由和错误处理，后者负责加载环境、初始化数据库和开始监听。公共路由负责认证和输入边界，存储层组织数据库操作。

这个拆分方便在受控环境里构造应用做测试，但**不能把“导入了应用模块”等同于“数据库和外部服务已经隔离”**。自动化测试仍然需要确认依赖的配置和注入方式，不能用开发入口直接连到一个不确定的环境。

普通笔记使用账号级别的快照版本；知识库条目使用覆盖“内容时间”和“目录位置”的状态版本。两者解决的冲突粒度不同，详见 [快照同步与并发冲突](/practice/notes-sync-consistency)。

## 5. 把失败路径当成正常的产品流程

这些实现里反复出现的一个模式是：**失败之后，保留用户继续操作所需要的上下文**。

- 保存失败：保留待提交的内容，下一次可以重试；
- 读取的响应已经过期：丢弃结果，避免回填到别的文档里；
- 版本冲突：带回服务端当前的状态，让用户处理差异；
- 内容已被删除：不被旧快照自动恢复，未同步的修改可以另存为副本；
- 页面资源加载失败：保留目标地址，让用户决定是否重新加载。

这些并不等于已经实现了实时协作、任意离线操作或者无损的自动合并。当前的模式主要解决单人多窗口、多设备和弱网下的可靠性；如果要支持多人逐字协作，需要另外设计操作合并、权限和历史模型。

## 开发一个功能时的检查顺序

1. 写出用户动作和期望的状态，比如“移动目录后，继续保存正文”；
2. 画清楚它会改变表单、共享缓存，还是服务端数据；
3. 标出每一次异步操作开始时的账号、内容标识和版本；
4. 规定失败后保留什么，用户怎样重试或放弃；
5. 在受控环境里验证**交错的执行顺序**，而不只是检查一次成功的请求；
6. 最后核对发布和旧客户端的兼容，避免代码是对的、资源却加载不到。

## 检查清单

- [ ] 共享层不依赖任何一个客户端的界面组件
- [ ] 每个状态都能说清它的寿命和唯一的修改者
- [ ] 不同类型操作的“保存”提示，准确说明保存到了哪里、是哪一版
- [ ] 异步操作记录了开始时的账号、内容和版本
- [ ] 失败后保留用户继续操作所需的上下文
- [ ] 测试覆盖了交错的执行顺序，而不只是成功路径
