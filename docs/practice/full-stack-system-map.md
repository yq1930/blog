# 多端业务系统全景图：从仓库清单到能力地图

当一个服务端同时支撑 PC 管理端、员工 H5、用户 H5 和小程序时，最危险的误解是把它看成“几个前端调用一个后端”。仓库只是代码的存放方式，真正决定改动风险的是业务能力、身份上下文、数据所有权、外部副作用和发布节奏。

本文给出一套适用于长期演进系统的建模方法。目标不是画一张看起来完整的架构图，而是让团队能够回答三个具体问题：一次请求如何穿过系统、一个需求会影响哪些端、某个失败应该由哪一层处理。

> 文中的模块名、接口、字段和代码均为独立设计的示例，不对应任何具体项目。

## 为什么“仓库列表”不是架构

下面这种清单只能说明代码放在哪里：

```text
server/
admin-web/
staff-h5/
consumer-h5/
mini-program/
```

它无法告诉我们：

- “创建预约”是否在四个客户端有四套不同规则；
- 登录后的组织、门店和角色由谁决定；
- 服务端的共享模型是否已变成所有模块都能随意修改的公共区域；
- 支付成功但本地状态更新失败时由谁恢复；
- 某个接口字段调整后，哪些旧版本客户端仍在线上。

因此，系统文档至少需要五个互相校验的视图。

## 第一张图：部署视图

部署视图只画可独立发布、可独立失败的单元，不画每一个代码目录。

```text
                         ┌────────────────────┐
                         │   外部身份与支付方   │
                         └─────────┬──────────┘
                                   │
┌────────────┐                     ▼
│ PC 管理端   │ ───────┐   ┌──────────────────┐
└────────────┘         │   │                  │
┌────────────┐         ├──▶│ 多入口业务服务端  │──▶ 数据库 / 缓存
│ 员工 H5     │ ───────┤   │                  │
└────────────┘         │   └─────────┬────────┘
┌────────────┐         │             │
│ 用户 H5     │ ───────┤             ▼
└────────────┘         │       队列 / 定时任务
┌────────────┐         │
│ 原生小程序  │ ────────┘
└────────────┘
```

这张图要标注四类信息：

| 信息 | 要回答的问题 |
| --- | --- |
| 发布单元 | 哪些部分能独立构建、部署和回滚？ |
| 网络边界 | 哪些调用可能超时、重试或被网关改写？ |
| 状态单元 | 会话、缓存、任务状态分别保存在哪里？ |
| 外部依赖 | 哪些能力不由团队控制，需要降级或补偿？ |

部署视图不应该包含控制器和组件名称。那些是实现细节，可能频繁变化；发布和故障边界才是它要长期表达的事实。

## 第二张图：能力视图

能力视图按“用户要完成什么”组织，而不是按端组织。以一个通用服务型系统为例：

| 业务能力 | PC 管理端 | 员工 H5 | 用户 H5 | 小程序 | 服务端所有者 |
| --- | --- | --- | --- | --- | --- |
| 账户与身份 | 配置角色 | 员工登录 | 用户授权 | 平台登录 | 身份模块 |
| 预约 | 配置资源 | 确认服务 | 创建预约 | 创建预约 | 预约模块 |
| 订单 | 查询与调整 | 创建草稿 | 查看状态 | 支付 | 订单模块 |
| 权益 | 配置规则 | 查询可用项 | 查看与使用 | 展示卡包 | 权益模块 |
| 通知 | 模板管理 | 接收待办 | 接收结果 | 订阅消息 | 通知模块 |

这张表的价值在于暴露重复规则。如果“可预约时段”的计算同时存在于 H5、小程序和服务端，团队就应明确：客户端只能做体验性预校验，最终规则必须由服务端裁决。

能力视图还应记录能力的主数据来源。例如订单状态只能由订单模块修改，报表模块可以读取但不能反向修正。没有所有权的共享数据，最终会变成任何模块都能写的隐形耦合点。

## 第三张图：一次请求的旅程

选择一条高频、跨层、可产生副作用的流程，画出完整路径。下面以“提交预约”为例：

```text
用户点击提交
  │
  ├─ 客户端生成 requestId，并锁定提交按钮
  │
  ▼
渠道入口解析平台登录凭证
  │
  ├─ 身份适配：externalIdentity → actorId
  ├─ 上下文装配：tenantId / locationId / roles
  ├─ 输入校验：日期、项目、资源标识
  │
  ▼
应用服务执行用例
  │
  ├─ 读取规则与现有占用
  ├─ 在事务内再次验证并写入
  ├─ 记录待发送事件
  │
  ▼
返回稳定业务结果
  │
  └─ 后台任务发送通知；失败可重试
```

画请求旅程时，不要只写“调用接口”。至少把下面几个边界标出来：

1. **输入边界**：字符串、空值和旧版本字段何时转成领域可理解的类型。
2. **身份边界**：平台身份、系统账号、组织和角色何时合并成可信上下文。
3. **一致性边界**：哪些检查必须和写入处于同一个事务。
4. **外部边界**：支付、消息、文件等不可纳入本地事务的调用如何重试。
5. **响应边界**：内部异常如何变成各端都能稳定理解的错误。

## 第四张图：身份与租户上下文

多端系统常见的不一致不是业务规则，而是“当前用户是谁”。PC 可能使用账号会话，H5 依赖容器授权，小程序先获得一次性凭证；它们最后都应收敛成同一种内部上下文。

```ts
type RequestContext = {
  actorId: string
  tenantId: string
  locationId?: string
  roles: string[]
  channel: 'admin-web' | 'staff-h5' | 'consumer-h5' | 'mini-program'
  requestId: string
}
```

业务服务只接收 `RequestContext`，不直接解析 Cookie、查询参数或平台临时码。这样可以得到两个好处：

- 渠道登录方式改变时，只修改入口适配层；
- 单元测试可以直接构造上下文，不需要模拟浏览器或平台 SDK。

可信上下文必须由服务端从会话或身份映射中恢复。客户端传来的 `tenantId`、`locationId` 和角色只能作为选择意图，不能直接当作授权结论。

## 第五张图：数据与副作用

一次写操作通常同时包含本地数据和外部副作用。先把它们分开，才能讨论失败恢复。

```text
同一数据库事务
┌─────────────────────────────────────┐
│ 创建业务记录                         │
│ 写状态历史                           │
│ 写 outbox 事件                       │
└─────────────────────────────────────┘
                     │ 提交后异步派发
                     ▼
             短信 / 平台消息 / 外部同步
```

“数据库提交后立即调用第三方”看起来简单，却存在进程在两步之间退出的窗口。把待处理事件和业务数据放在同一事务中，再由后台任务发送，可以让失败变得可发现、可重试。

不是所有流程都需要消息队列。判断标准不是技术偏好，而是：外部动作能否与本地事务原子提交、失败后是否允许丢失、用户是否必须同步等待结果。

## 用垂直切片描述一个需求

有了五张图，再为具体需求建立垂直切片。一个切片从用户入口一直走到数据和观测，不以仓库为边界。

```text
切片：取消预约

交互        二次确认、提交锁、结果页
协议        POST /appointments/{id}/cancel
身份        actorId + tenantId + channel
应用用例    CancelAppointment
领域规则    状态是否允许取消、是否超过时限
持久化      主记录 + 状态历史 + outbox
副作用      释放资源、退款请求、发送通知
观测        requestId、业务编号、旧/新状态、失败阶段
回归        PC 查询、H5 详情、小程序列表状态一致
```

这种描述方式能直接变成开发清单和测试清单，也能暴露“只改了当前页面，忘了其他端”的风险。

## 入口层、应用层与基础设施层怎么分

多应用服务端最容易出现两种极端：所有入口重复实现业务规则，或者所有代码都塞进一个巨大的共享目录。更稳定的依赖方向是：

```text
渠道控制器 / 命令入口
          │
          ▼
      应用用例
          │
          ▼
领域规则与端口（repository / gateway 接口）
          ▲
          │
数据库、缓存、支付、消息等适配器
```

一个简化的 PHP 示例：

```php
final class CancelAppointment
{
    public function __construct(
        private AppointmentRepository $appointments,
        private EventOutbox $outbox,
        private TransactionManager $transactions
    ) {}

    public function execute(CancelCommand $command, RequestContext $context): void
    {
        $this->transactions->run(function () use ($command, $context): void {
            $appointment = $this->appointments->getForUpdate(
                $context->tenantId,
                $command->appointmentId
            );

            $appointment->cancelBy($context->actorId, $command->reason);
            $this->appointments->save($appointment);
            $this->outbox->append($appointment->releaseEvents());
        });
    }
}
```

示例没有出现 HTTP、Cookie、SQL 或第三方 SDK。仓储写入与 outbox 追加由同一个 `TransactionManager` 包住，避免正文所说的原子性只停留在图里；渠道入口只负责把请求转换成 `CancelCommand`。

## 客户端共享什么，不共享什么

PC、H5 和小程序运行时不同，强行共享 UI 组件通常收益不高。更值得共享的是语义：

| 适合共享 | 不宜强行共享 |
| --- | --- |
| 错误码含义 | PC 表格和小程序列表组件 |
| 状态枚举与转换规则 | 路由生命周期实现 |
| 请求和响应 schema | 平台授权 API 调用 |
| 金额、时间的序列化约定 | 交互反馈组件 |
| 埋点事件名称 | 构建工具专有配置 |

如果无法建立跨仓库共享包，也可以生成同源类型或用契约测试保证一致。最重要的是共享“定义来源”，而不是复制一份看起来相同的常量。

## 发布视图：不同步上线也要兼容

多端系统无法假设所有客户端和服务端同时发布。小程序可能等待审核，H5 可能被旧页面缓存，PC 用户可能长时间不刷新。因此每个契约变更都要经过四个问题：

1. 旧客户端调用新服务端是否仍能工作？
2. 新客户端在服务端尚未发布时会怎样？
3. 中间状态持续一天而不是十分钟时是否安全？
4. 回滚任一端后，数据格式是否仍然可读？

新增字段通常向后兼容，改变字段语义通常不兼容。不要因为 JSON 结构没有变化，就认为协议没有变化。

## 把可观测性放进系统图

一条跨端请求至少需要三个关联标识：

- `requestId`：一次网络请求，可由客户端生成并由网关校验；
- `operationId`：一次可能跨重试的用户操作；
- `entityId`：订单、预约等业务对象标识。

日志不要记录完整请求体、登录凭证和个人信息。推荐记录结构化最小集合：

```json
{
  "event": "appointment.cancelled",
  "requestId": "req_demo_42",
  "operationId": "op_demo_17",
  "channel": "mini-program",
  "result": "accepted",
  "durationMs": 86
}
```

错误监控按失败阶段聚合比按异常文本聚合更有用，例如 `identity_resolution`、`validation`、`transaction`、`external_delivery`。这样告警能够直接指向责任边界。

## 一次需求的标准变更流程

### 1. 先写行为差异

用 Given / When / Then 写出新旧行为，不急着列要改的文件。

```text
Given 记录处于可取消状态且当前用户有权限
When 用户以同一 operationId 重复提交两次取消请求
Then 只发生一次状态变更，并返回同一个最终结果
```

### 2. 标记垂直切片

依次检查交互、协议、身份、规则、存储、副作用、观测与回滚。任何“无影响”都应有理由，不能留空。

### 3. 先扩展，再切换，最后清理

跨端字段迁移使用三阶段：服务端先兼容新旧格式；客户端切换并观察；确认旧版本退出后再删除旧格式。不要把新增、切换、删除放进同一次发布。

### 4. 以风险决定验证深度

纯展示改动可以组件测试加冒烟；身份、金额、库存、支付、状态机改动需要契约测试、并发测试、失败注入和回滚演练。

## 应长期维护的最小文档集

系统文档不需要很多，但下面五份应当可被持续更新：

1. **能力—客户端矩阵**：一个能力在哪些端有入口，服务端所有者是谁。
2. **身份上下文说明**：每种渠道如何映射为统一内部身份。
3. **契约目录**：请求、响应、错误、幂等和兼容窗口。
4. **关键状态机**：允许的状态转换、操作者和副作用。
5. **发布与回滚手册**：顺序、开关、验证指标和回退条件。

文档中的可执行部分尽量交给测试守护。例如 schema 用契约测试验证，依赖方向用静态检查验证，链接用站点构建验证。

## 架构体检清单

### 系统边界

- [ ] 能否说清每个可独立部署单元的职责和故障影响？
- [ ] 能否从一个业务能力反查所有客户端入口？
- [ ] 共享目录是否有明确所有者和准入规则？
- [ ] 外部依赖是否都有超时、重试、幂等和降级说明？

### 请求与身份

- [ ] 业务服务是否只依赖统一上下文，而不解析渠道凭证？
- [ ] 组织与角色是否由服务端恢复并校验？
- [ ] 错误结果是否能被各端稳定映射，而不是依赖文本匹配？
- [ ] 写操作是否有 operationId 或等价幂等机制？

### 数据与发布

- [ ] 主数据的唯一写入者是否明确？
- [ ] 本地事务和外部副作用是否被显式区分？
- [ ] 协议变更是否考虑客户端不同步发布？
- [ ] 回滚后，新写入的数据是否仍能被旧版本读取？

## 结语

多端系统真正需要共享的不是一个“大而全”的代码库，而是一套对边界的共同认识。部署图说明哪里会独立失败，能力图说明谁拥有规则，请求图说明一次操作如何完成，身份图说明谁在行动，数据图说明失败后怎样恢复。

当这五张图能互相对上，仓库再多也仍然可理解；当它们彼此矛盾，即使所有代码都在一个仓库里，系统也会在每次跨端改动时暴露意外成本。
