# 多端业务系统全景图：一次需求到底要改哪里

一套业务系统同时有 PC 后台、员工 H5、用户 H5 和微信小程序时，最常见的困扰不是“代码放在哪”，而是：**改一个功能，到底有哪些地方会受影响？**

只盯着当前页面改，常常会出现这样的结果：小程序上的“取消”按钮按规则隐藏了，PC 后台却还能取消；员工 H5 显示的状态还是旧的；通知发了两遍；发布后旧版本的小程序调用新接口报错……

本文来自一组长期维护的真实项目。示例代码保留了项目里的典型写法，但已经删除业务名称、接口地址、内部参数和用户数据。

::: tip 读完这篇你会
- 接到需求后，快速判断要检查哪些仓库和模块
- 说清一条请求怎样从页面走到数据库，再回到页面
- 避免只改当前页面而漏掉其他客户端
- 为多人协作准备一份简单的影响范围清单
:::

## 1. 原理：像追踪一个快递包裹

一个快递包裹从寄出到签收，要经过揽收、分拣、运输、派送多个站点。哪一站出了问题，包裹都到不了。排查时，最有效的办法是查物流轨迹：它停在了哪一站？

一次业务请求也是一样：

```text
PC 管理后台 ─────┐
员工移动 H5 ─────┤
用户移动 H5 ─────┼──▶ PHP / Yaf 服务端 ──▶ 数据库、缓存、外部服务
微信小程序 ──────┘
```

四个客户端的界面和运行环境不同，但最终都依赖同一批业务规则，比如“是否允许取消”“当前用户能否操作”“金额怎么计算”。这些都应该由服务端做最终判断：**客户端可以提前提示，但不能当最后的裁判。**

## 2. 不要按仓库理解需求，要按业务动作理解

假设需求是“用户可以取消预约”。如果只看小程序页面，很容易漏掉这些问题：

| 层次 | 要确认的问题 |
| --- | --- |
| 小程序或 H5 | 按钮什么时候显示？重复点击怎么办？ |
| API | 请求需要哪些参数？重复请求会怎样？ |
| 身份与权限 | 谁能取消？能不能取消别人的记录？ |
| 业务规则 | 哪些状态允许取消？有没有时间限制？ |
| 数据 | 是否要释放占用的资源、记录状态历史？ |
| 外部动作 | 是否要退款或发通知？失败了怎么办？ |
| 其他客户端 | PC 后台和另一个 H5 是否也要显示新状态？ |

这种做法叫**垂直切片**：从用户点击开始，一路检查到数据和外部结果，而不是只看自己负责的那一层。

## 3. 一条请求的完整旅程

```text
用户点击提交
  ↓
客户端校验并锁定按钮
  ↓
请求层附带登录信息和 requestId
  ↓
服务端入口解析参数与当前用户
  ↓
业务服务检查权限和状态
  ↓
事务内写入数据
  ↓
提交后异步发送通知
  ↓
客户端刷新最终状态
```

能把一个需求画成这条链，开发、测试和排查问题都会容易很多。

### 服务端入口：只负责启动

服务端使用 Yaf，不同的客户端对应不同的入口，但入口的核心动作很简单：加载配置、选择应用目录、启动应用。根据项目代码缩短后的示例：

```php
<?php

$application = new Yaf_Application($configFile);
$application
    ->bootstrap()
    ->run();
```

入口里不适合写具体业务。否则同一条规则会在多个入口中复制，修改时很难保证一致。更合适的分工是：

```text
入口：启动哪个应用
控制器：接收什么请求
业务服务：这次操作能不能做
模型或仓储：数据怎样读写
基础设施：缓存、消息、支付等怎样调用
```

### 客户端请求层：让页面拿到统一的结果

PC 项目使用独立的请求封装，再由 API 模块调用。简化后类似：

```js
import axios from 'axios'

const request = axios.create({
  baseURL: process.env.BASE_API,
  timeout: 15000
})

request.interceptors.response.use(
  response => response.data,
  error => Promise.reject(normalizeError(error))
)
```

移动 H5 和小程序底层用的 API 不同，但页面最好拿到同样的结果：

```js
async function cancelAppointment(id) {
  try {
    const data = await api.cancelAppointment({ id })
    showSuccess(data)
  } catch (error) {
    showFailure(error)
  }
}
```

页面不应该关心底层用的是 Axios、`XMLHttpRequest` 还是 `wx.request`。

### 身份信息：在服务端重新确认

不同客户端的登录方式不同：

```text
PC：账号会话
H5：网页授权或 Cookie
小程序：平台登录码换业务会话
```

进入业务服务前，应该统一成类似的上下文：

```php
final class RequestContext
{
    public $actorId;
    public $tenantId;
    public $roles;
    public $channel;
    public $requestId;

    public function __construct($actorId, $tenantId, array $roles, $channel, $requestId)
    {
        $this->actorId = $actorId;
        $this->tenantId = $tenantId;
        $this->roles = $roles;
        $this->channel = $channel;
        $this->requestId = $requestId;
    }
}
```

这里用的是 PHP 7.3 也能解析的显式属性写法，便于旧的 Yaf 项目直接理解；如果运行环境已经统一到 PHP 8.2 以上，可以再使用构造器属性提升和 `readonly`。

客户端传来的用户 ID、组织 ID 或角色，都不能直接当作可信的结果。服务端必须从有效的会话中恢复身份，并再次校验权限（原因见 [认证、授权与会话](/backend/authentication) 中的越权问题）。

## 4. 用一张表记录功能覆盖范围

项目大了以后，最实用的架构文档往往不是一张大图，而是这样一张表：

| 业务能力 | PC | 员工 H5 | 用户 H5 | 小程序 | 服务端模块 |
| --- | --- | --- | --- | --- | --- |
| 登录 | 管理账号 | 员工身份 | 用户授权 | 平台登录 | 身份模块 |
| 预约 | 查询和调整 | 确认 | 创建 | 创建 | 预约模块 |
| 订单 | 管理 | 创建 | 查询 | 支付 | 订单模块 |
| 通知 | 配置 | 接收 | 接收 | 订阅消息 | 通知模块 |

每次需求评审，先更新这张表，再确定要修改的文件。它能直接暴露“某个端没有考虑到”。

## 5. 坑一：只改了看得见的页面

**现象**：小程序上已经按新规则隐藏了“取消”按钮，但 PC 后台、另一个 H5，甚至直接调接口，依然可以取消不该取消的预约。

**原因**：按钮消失只是界面层面的限制，接口本身没有加规则。

**修复**：权限和状态规则必须在服务端执行；客户端隐藏按钮只是为了体验。

**怎么避免再犯**：需求评审时对照第 4 节的覆盖表，逐个确认每个端和服务端的改动。

## 6. 坑二：公共参数散落在每个接口里

**现象**：新增了一个接口，忘了带上渠道标识或追踪 ID，导致服务端统计错误、问题无法追踪。

**修复**：登录信息、渠道、版本号、追踪标识统一由请求层添加，页面和 API 模块不手动拼接。手工拼接迟早会漏。

## 7. 坑三：数据提交后，直接调用外部服务

**现象**：数据库里的预约已经取消成功，但调用退款或通知服务时失败了。因为没有任何记录，事后既不知道哪些没处理，也没法重试。

**修复**：重要的外部动作，在数据提交时留下一条可以重试的任务记录，由后台任务执行和重试。详细做法见 [事务、幂等与补偿](/practice/transactional-business-workflow)。

## 8. 坑四：假设所有客户端会同时上线

**现象**：接口改了返回字段，H5 和 PC 同步更新了，但小程序新版本还在审核中，旧版小程序的用户全部报错。

**原因**：H5 可能被浏览器缓存，小程序需要审核，PC 用户可能很久不刷新页面。不同客户端的新版本，不会在同一时刻生效。

**修复**：接口变更要允许新旧版本在一段时间内共存：先新增字段、保留旧字段，等所有客户端都升级后再清理。具体方法见 [API 版本管理](/backend/api-versioning)。

## 9. 一个需求的开发清单

以“取消预约”为例：

```text
[ ] 哪些客户端有取消入口
[ ] 哪些状态允许取消
[ ] 当前用户是否有权操作
[ ] 同一个请求到达两次会怎样
[ ] 数据库需要同时修改哪些事实
[ ] 通知或退款失败后怎样恢复
[ ] 其他客户端怎样看到最新状态
[ ] 新旧客户端同时在线是否兼容
[ ] 出问题时怎样关闭或回滚
```

这份清单比“前端改页面、后端加接口”更接近真实的工作。

## 排查思路：先找请求停在了哪一站

收到“页面点了没反应”的反馈时，按顺序检查：

1. 页面有没有真的发出请求；
2. 请求有没有带上 `requestId`；
3. 服务端是否识别出了正确的用户和业务范围；
4. 业务规则在哪一步拒绝了；
5. 数据库是否已经提交；
6. 外部动作是否还在处理中；
7. 客户端是否用旧缓存覆盖了新结果。

不要一开始就在所有仓库里搜索错误文案，先确定请求停在了哪个边界。

## 长期维护需要的最小文档

- 客户端—业务能力覆盖表；
- 各种登录方式怎样转换成统一的身份；
- 关键业务状态，以及允许的状态转换；
- 发布顺序、验证步骤和回滚方法。

能用测试验证的内容，不要只靠文档提醒：错误结构用契约测试，重复提交用并发测试，站内链接用构建检查。

## 检查清单

- [ ] 需求按业务动作拆解，从点击检查到数据、外部结果和回滚
- [ ] 权限和状态规则在服务端执行
- [ ] 身份由服务端从会话恢复，不信任客户端传来的身份字段
- [ ] 公共参数由请求层统一添加
- [ ] 重要的外部动作有可重试的任务记录
- [ ] 接口变更允许新旧客户端共存
- [ ] 维护客户端—业务能力覆盖表
