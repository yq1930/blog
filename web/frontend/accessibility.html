可访问性实战 ​

可访问性（a11y）不是"为少数用户做的额外善事"，而是让页面在更多场景下都能用——用键盘的人、在强光下看不清的人、用屏幕阅读器的人、网络慢加载不完整的人。把它当作"能用的下限"来对待，而不是锦上添花。好消息是，做好少数几件事，就能覆盖大多数问题。

用对的标签就解决一半问题 ​

可访问性的第一步不是加 ARIA，而是用语义化标签。屏幕阅读器和键盘导航依赖标签的语义来理解页面结构：

html
<!-- 差：全是 div，辅助技术看不出结构 -->
<div class="header">
  <div class="nav">
    <div class="item" onclick="goHome()">首页</div>
  </div>
</div>

<!-- 好：用语义标签，结构清晰可读 -->
<header>
  <nav aria-label="主导航">
    <a href="/">首页</a>
  </nav>
</header>

几个高频要点：

场景用什么不要用什么
页面分区<header> <main> <nav> <footer>全用 <div>
标题层级<h1> 到 <h6> 按顺序用 <div class="title"> 凑样式
按钮<button><div onclick>
链接<a href><span onclick>
表单<label> 关联 <input>用占位文字代替 label

<button> 和 <a> 的区别不只是样式：按钮触发操作，链接跳转地址。用 <div onclick> 模拟按钮，会丢失键盘可聚焦、Enter/Space 触发、屏幕阅读器识别等全部能力。

键盘可达是一切的基础 ​

很多用户不用鼠标——键盘用户、读屏软件用户、某些运动障碍用户。一个基本要求：所有交互元素都能用键盘操作。

text
Tab       在可聚焦元素间移动，顺序应符合视觉顺序
Enter     激活链接或按钮
Space     激活按钮或勾选
Esc       关闭弹窗
方向键    在列表、菜单、标签页间移动

检查要点：

  • 每个可交互元素用 Tab 能到达，且有可见的焦点样式（别写 outline: none 后什么都不加）。
  • 焦点顺序与视觉阅读顺序一致，不要用 DOM 顺序和 CSS 定位搞出跳跃。
  • 自定义组件（如下拉、模态框）要实现键盘交互：模态框打开时焦点陷阱在内、Esc 关闭、返回触发它的元素。
css
/* 给焦点一个明确的样式，不要直接删掉 */
:focus-visible {
  outline: 2px solid var(--color-primary);
  outline-offset: 2px;
}

对比度与可读性 ​

文字和背景的对比度不够，在强光、老旧屏幕、视力不佳的情况下就读不清。WCAG 建议正文对比度至少 4.5:1，大字 3:1：

text
浅背景上的浅灰文字 → 对比度不足，看不清
深背景上的白色文字 → 通常达标
低对比度的占位符文字 → 常被忽略，但用户需要看清

除了对比度，可读性还受这些影响：

  • 字号别小于 14px（正文推荐 16px 起）。
  • 行高留够（1.5 左右），别让文字挤成一团。
  • 别只靠颜色传达信息——色盲用户看不出"红色表示错误"，要配文字或图标。
html
<!-- 差：只用颜色 -->
<span class="error"></span>

<!-- 好：颜色 + 文字 -->
<span class="error">必填项不能为空</span>

ARIA：该用才用 ​

ARIA（aria-* 属性和 role）能补充原生标签表达不了的语义，但有一条核心原则：No ARIA is better than bad ARIA。用错了比不用更糟，因为它给辅助技术传递了错误信息。

html
<!-- 动态更新的提示，用 aria-live 让读屏软件朗读 -->
<div aria-live="polite" id="status"></div>

<!-- 图标按钮，用 aria-label 提供文字 -->
<button aria-label="关闭">×</button>

<!-- 表单字段错误，用 aria-describedby 关联说明 -->
<input aria-describedby="email-error" aria-invalid="true" />
<span id="email-error">邮箱格式不正确</span>

常用且安全的 ARIA：

属性用途
aria-label给没有可见文字的元素提供名称（图标按钮）
aria-live标记动态更新的区域，让读屏软件播报
aria-describedby关联额外的说明或错误信息
aria-expanded / aria-hidden表达展开/折叠、可见/隐藏状态

不要用 ARIA 去伪造原生标签的能力——如果你需要按钮，直接用 <button>，而不是 <div role="button" tabindex="0"> 然后手动实现所有键盘行为。

别忘了动态内容 ​

异步加载、弹窗、路由切换后，焦点和读屏状态需要同步更新，否则辅助技术用户会"卡"在过时的页面状态：

  • 路由切换后，把焦点移到新内容区或主标题。
  • 弹窗打开时聚焦到弹窗内，关闭时焦点返回触发元素。
  • 加载完成或操作成功，用 aria-live 区域通知。

务实的检查清单 ​

  • 主要结构是否用了语义标签，而不是全 div？
  • 所有交互能否只用键盘完成？焦点是否可见？
  • 文字对比度是否达标？是否只靠颜色传递信息？
  • ARIA 是否只在原生标签不够时才用，且用对了？
  • 动态更新（加载、弹窗、路由）是否同步了焦点和通知？

可访问性不是一次性达标，而是开发习惯。每写一个交互元素就问一句"用键盘能用吗？读屏软件能理解吗？"，比事后补救成本低得多。把它当成代码质量的一部分，而不是上线前的额外检查项。
