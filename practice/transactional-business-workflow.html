高一致性业务工作流：事务、幂等、并发与补偿 ​

高一致性流程的核心不是“多写几个 rollback()”，而是先定义业务承诺，再让数据库约束、事务、幂等、状态机和补偿共同保护它。

一条可靠链路应满足：

  • 同一个业务请求无论重放多少次，只产生一次业务效果。
  • 两个并发请求不能共同消耗同一份余额、次数或库存。
  • 本地提交成功而外部调用超时后，系统不会凭感觉把它当作成功或失败。
  • 进程在任何一步崩溃后，都能依据持久化状态继续推进、重试或转人工。
  • 撤销不是删除历史，而是产生可审计、可幂等的反向业务动作。
  • 运维人员能用一个业务操作标识串起请求、事务、外部流水、回调和补偿。

本文所有类名、表名、字段、状态、流程和代码均为虚构示例，只用于解释通用方法；它们不对应任何真实系统。

示例使用较紧凑的现代 PHP 写法表达设计意图；旧运行时可改用显式属性和普通值对象，不影响事务与一致性原则。

一、先写不变量，再写流程 ​

所谓“一致”，必须能用可验证的句子表达。以“提交一份资源消费单并触发外部结算”为例，可以定义这些不变量：

不变量技术防线
同一业务请求最多生成一份有效单据幂等键唯一约束
可用资源永远不能小于允许下限条件更新或行锁
余额变化必须能由流水重建不可变账本 + 汇总校验
单据、资源变化和待发送事件要么一起存在，要么都不存在一个本地数据库事务
外部成功回调最多推进一次状态回调收件箱唯一约束 + 条件状态迁移
撤销后原动作仍可追踪反向流水关联原操作，不物理删除

如果不变量只存在于开发者脑中，代码会自然退化成一串“先做 A，再做 B，失败就返回”。先把不变量写进设计、约束、测试和告警，才有资格讨论实现。

三类一致性不要混为一谈 ​

一致性范围能用什么保证典型问题
单条记录条件更新、唯一约束、检查约束防止重复、超扣
同一数据库内多条记录ACID 事务、锁、固定写入顺序主单、明细、账本共同提交
跨数据库或第三方幂等、状态机、消息、补偿、对账支付成功但本地响应丢失

数据库事务只能可靠覆盖它真正控制的资源。把 HTTP 调用写在事务代码块里，不会让远端一起回滚，只会让本地锁持有更久。

不同资源，共用一副一致性骨架 ​

储值、服务次数、实物库存和外部支付看起来不同，但都能套用“业务意图 → 本地原子提交 → 外部推进 → 对账收敛”的骨架。它们的差别应被明确建模，不能被一个含义模糊的 balance 字段抹平：

资源类型必须明确的语义特别容易踩的坑
储值或积分单位、币种/类型、入账与消费流水、退款来源浮点误差，直接覆盖余额，退款按新规则重算
服务次数批次、有效期、扣减顺序、部分使用返还到错误批次，过期资源被重新激活
实物库存可售、预占、实扣、释放、仓位把下单即实扣和支付后实扣混在一起
外部支付本地意图、第三方事实、回调、退款超时当失败，重试时更换外部幂等键

对次数和批次型资源，流水还应记录“从哪个原始批次扣了多少”，补偿时原路返还；对库存，通常先预占、在业务提交点实扣，取消或超时则释放；对外部支付，本地数据库只能记录意图和已知事实，不能替第三方宣布最终结果。

二、先确定一个“提交点” ​

复杂流程往往有多个看起来像成功的时刻：本地单据已写、外部请求已发送、第三方已受理、异步回调已到、最终对账已确认。必须明确产品语义中的提交点。

推荐把状态分成三类，而不是只用“成功/失败”：

text
本地未提交：请求可以安全重试，没有业务效果
本地已提交、外部未确定：业务效果已记录，系统负责继续推进
最终完成：本地状态与外部事实已经确认

如果调用方在“外部未确定”时只收到一个普通失败，它通常会立即重试，制造第二次副作用。更稳妥的响应是返回稳定的操作标识和 PROCESSING 状态，让调用方查询同一操作。

三、用状态机代替散落的布尔字段 ​

一个通用的高一致性工作流可以使用以下状态：

text
RECEIVED
   │ 开始处理
   ▼
PROCESSING
   ├── 确定性业务拒绝 ──▶ REJECTED
   │
   └── 本地事务提交
       ▼
LOCAL_COMMITTED ──────┐
   │ 生成外部任务      │ 本地补偿
   ▼                  ▼
EXTERNAL_PENDING   COMPENSATING
   │                  │
   ├── 外部确认成功    ├── 补偿成功 ──▶ COMPENSATED
   │                  └── 无法自动恢复 ─▶ MANUAL_REVIEW
   ▼
SUCCEEDED

PROCESSING / LOCAL_COMMITTED / EXTERNAL_PENDING / COMPENSATING
   └── 发现事实冲突或超过恢复窗口 ──▶ MANUAL_REVIEW

状态名称可以调整，但迁移规则必须集中管理：

php
final class OperationStateMachine
{
    private const ALLOWED = [
        'RECEIVED' => ['PROCESSING'],
        'PROCESSING' => ['LOCAL_COMMITTED', 'REJECTED', 'MANUAL_REVIEW'],
        'LOCAL_COMMITTED' => ['EXTERNAL_PENDING', 'COMPENSATING', 'MANUAL_REVIEW'],
        'EXTERNAL_PENDING' => ['SUCCEEDED', 'COMPENSATING', 'MANUAL_REVIEW'],
        'COMPENSATING' => ['COMPENSATED', 'MANUAL_REVIEW'],
        'REJECTED' => [],
        'SUCCEEDED' => [],
        'COMPENSATED' => [],
        'MANUAL_REVIEW' => [],
    ];

    public function assertCanMove(string $from, string $to): void
    {
        if (!in_array($to, self::ALLOWED[$from] ?? [], true)) {
            throw new StateConflict($from, $to);
        }
    }
}
当前状态允许的下一状态
RECEIVEDPROCESSING
PROCESSINGLOCAL_COMMITTED、REJECTED、MANUAL_REVIEW
LOCAL_COMMITTEDEXTERNAL_PENDING、COMPENSATING、MANUAL_REVIEW
EXTERNAL_PENDINGSUCCEEDED、COMPENSATING、MANUAL_REVIEW
COMPENSATINGCOMPENSATED、MANUAL_REVIEW
REJECTED、SUCCEEDED、COMPENSATED、MANUAL_REVIEW无，均为当前工作流终态

不要让每个控制器自行判断状态数字。示例把 REJECTED、SUCCEEDED、COMPENSATED 和 MANUAL_REVIEW 视为当前工作流的终态；人工复核后的恢复应发起一条新的、可审计命令，而不是绕过状态机直接改回中间态。状态迁移还应同时受应用层校验和数据库条件更新保护，因为并发请求可能在校验后抢先改变状态。

四、事务边界围绕一个本地业务承诺 ​

事务内应该包含什么 ​

对于“消耗资源并创建业务单据”，本地事务通常包含：

  1. 占用幂等键。
  2. 读取或原子更新资源。
  3. 创建主单与明细。
  4. 写入不可变业务流水。
  5. 写入审计事件或 outbox 消息。
  6. 保存幂等结果摘要。

事务外应该包含什么 ​

  • 调用支付、消息、文件、地图等远端服务。
  • 发送短信、推送或邮件。
  • 生成体积较大的报表和附件。
  • 等待用户操作。
  • 长时间计算或批量导出。

推荐的整体时序如下：

text
调用方        接口层        应用服务          本地数据库        异步执行器       外部系统
  │             │              │                  │                │              │
  │ 幂等请求     │              │                  │                │              │
  ├────────────▶│ 构造命令      │                  │                │              │
  │             ├─────────────▶│ 开启事务         │                │              │
  │             │              ├─ 占用幂等键 ────▶│                │              │
  │             │              ├─ 条件扣减资源 ──▶│                │              │
  │             │              ├─ 单据/流水 ─────▶│                │              │
  │             │              ├─ 写 outbox ─────▶│                │              │
  │             │              ├─ 提交事务 ───────▶│                │              │
  │ PROCESSING  ◀──────────────┤                  │                │              │
  ◀─────────────┤              │                  │                │              │
  │             │              │                  │ 领取 outbox    │              │
  │             │              │                  ◀───────────────┤              │
  │             │              │                  │                ├─ 幂等调用 ──▶│
  │             │              │                  │                ◀─ 结果/超时 ──┤
  │             │              │                  │ 更新任务状态   │              │
  │             │              │                  ◀───────────────┤              │

本地事务提交后，即使进程立刻崩溃，outbox 仍在。执行器可以稍后接管；这比“提交后直接发 HTTP，失败只打一条日志”可靠得多。

用事务闭包代替遍地手工回滚 ​

在多个分支里手动 rollback() 再 return，很容易漏掉异常分支，也容易发生“事务尚未开始却回滚”或“某分支忘记提交”。把控制权交给统一事务管理器：

php
final class TransactionManager
{
    public function __construct(private DatabaseConnection $database) {}

    public function runOrThrow(callable $work): mixed
    {
        $this->database->begin();

        try {
            $result = $work();
            $this->database->commit();
            return $result;
        } catch (Throwable $error) {
            if ($this->database->inTransaction()) {
                $this->database->rollBack();
            }
            throw $error;
        }
    }
}

这个示例采用明确的“成功才返回”约定：业务拒绝必须抛出业务异常，基础设施失败必须抛出对应异常；事务回调只要正常返回就会提交。不要从回调正常返回 Failure 对象，否则管理器无法区分它与成功值，仍会提交。如果团队统一使用 Result 类型，就应另写一个能识别 isFailure() 并在失败时回滚的事务适配器，不能混用两种约定。

数据库连接在提交时断开，还可能形成“提交结果未知”：服务端无法仅凭异常断定数据库已经回滚。上层应使用同一个幂等键重新查询权威结果，不能换新键盲目重做整条业务动作。

还要定义嵌套事务策略：禁止嵌套、使用保存点，或让内层复用外层事务。最危险的是底层方法悄悄提交了调用方创建的事务。

五、一个完整的本地事务示例 ​

下面的代码演示资源扣减、单据、流水和待发送事件在同一事务中提交。所有命名均为虚构：

php
final class CommitUsageOperation
{
    public function __construct(
        private TransactionManager $transactions,
        private IdempotencyRepository $idempotency,
        private ResourceRepository $resources,
        private OperationRepository $operations,
        private LedgerRepository $ledger,
        private EventOutbox $outbox,
        private Clock $clock,
    ) {}

    public function execute(UsageCommand $command): OperationView
    {
        return $this->transactions->runOrThrow(function () use ($command) {
            $claim = $this->idempotency->claim(
                $command->scope(),
                $command->idempotencyKey(),
                $command->fingerprint()
            );

            if ($claim->hasCompletedResult()) {
                return $claim->completedResult();
            }

            $changed = $this->resources->decreaseIfAvailable(
                $command->resourceId(),
                $command->quantity()
            );

            if (!$changed) {
                throw new InsufficientResource();
            }

            $operation = UsageOperation::start(
                OperationId::new(),
                $command,
                $this->clock->now()
            );

            $this->operations->insert($operation);
            $this->ledger->append(LedgerEntry::forUsage($operation));
            $this->outbox->append(OperationCommitted::from($operation));

            $view = OperationView::from($operation);
            $this->idempotency->complete($claim, $view);

            return $view;
        });
    }
}

这段代码的关键不是类的数量，而是四个约束：

  • 幂等键的占用和业务写入处于同一事务。
  • 资源扣减使用原子条件，不采用“先查余额、再无条件更新”。
  • 账本只追加，不覆盖旧记录。
  • 外部动作只写成待处理事件，不在事务里直接调用。

六、幂等：防重不是“先查一下有没有” ​

幂等键必须有作用域 ​

单独一个客户端生成的字符串不够。合理的唯一范围通常是：

text
(租户或业务范围, 操作类型, 幂等键)

同一个键还要保存请求指纹。若调用方复用了键但改变了资源、数量或其他关键参数，服务端应返回“幂等键冲突”，不能悄悄返回第一次结果。

php
final readonly class RequestFingerprint
{
    private function __construct(private string $sha256) {}

    public static function from(UsageCommand $command): self
    {
        $canonical = json_encode([
            'resource' => $command->resourceId()->toString(),
            'quantity' => $command->quantity()->toCanonicalString(),
            'intent' => $command->intent()->value,
        ], JSON_THROW_ON_ERROR);

        return new self(hash('sha256', $canonical));
    }

    public function sameAs(self $other): bool
    {
        return hash_equals($this->sha256, $other->sha256);
    }

    public function toString(): string
    {
        return $this->sha256;
    }
}

只把影响业务效果的字段纳入指纹，并使用稳定字段顺序与规范化格式。时间戳、追踪标识等每次都变的字段不应破坏重放。

唯一约束是最后一道防线 ​

错误方式：

text
请求 A 查询：不存在
请求 B 查询：不存在
请求 A 插入：成功
请求 B 插入：也成功

正确方式是数据库唯一约束配合“尝试插入”：

sql
CREATE UNIQUE INDEX uq_demo_idempotency_scope
ON demo_idempotency(scope_key, operation_kind, idempotency_key);

表名和字段名是演示用。应用层捕获唯一冲突后读取已有记录，并处理三种情况：

已有记录状态返回策略
已完成，指纹相同原样返回第一次的稳定结果
处理中，指纹相同返回 PROCESSING 与同一操作标识
任意状态，指纹不同返回幂等键冲突

哪些结果应该缓存 ​

  • 已成功提交：必须缓存稳定结果。
  • 确定性的业务拒绝：可以缓存，避免同一请求不断冲击数据库。
  • 事务前的临时基础设施失败：通常不占用或释放幂等键，允许安全重试。
  • 外部结果未知：保留 PROCESSING，不能标成失败。

HTTP 超时不等于业务失败。客户端超时后应使用同一幂等键查询或重试，服务端返回同一个业务结果。

七、并发控制：判断与修改必须是同一个原子动作 ​

方案一：单条条件更新 ​

对于单资源扣减，优先使用数据库原子条件：

sql
UPDATE demo_resource_account
SET available_units = available_units - :units,
    revision = revision + 1
WHERE resource_id = :resource_id
  AND available_units >= :units;

受影响行数为零，表示资源不存在、资源不足或状态不允许。应用可以再查询一次用于生成准确提示，但不能把查询结果当成扣减是否成功的依据。

这种方式临界区短、吞吐高，适合单行约束。

方案二：悲观行锁 ​

如果规则需要读取同一聚合内多条记录后计算，可在事务里锁定它们：

sql
SELECT resource_id, available_units, state
FROM demo_resource_account
WHERE resource_id IN (:resource_ids)
ORDER BY resource_id
FOR UPDATE;

所有代码必须按稳定顺序加锁，减少死锁。事务里不能调用外部服务或做大计算。

方案三：乐观锁 ​

读多写少、冲突可以让用户重试时，带版本更新：

sql
UPDATE demo_operation
SET state = :next_state,
    revision = revision + 1
WHERE operation_id = :operation_id
  AND state = :expected_state
  AND revision = :expected_revision;

受影响行数为零就是冲突，不能继续假装成功。对于自动重试，必须重新读取并重新执行规则，而不是无限重放旧 SQL。

如何选择 ​

场景优先策略
单一余额、次数或库存扣减条件更新
多行共同满足复杂不变量固定顺序行锁
管理编辑、低冲突状态更新乐观锁
“只能存在一条有效记录”唯一约束
跨进程任务只允许一个执行者数据库领取或带租约的分布式锁

分布式锁不是数据库约束的替代品。锁可能过期、网络可能分区、进程可能暂停；关键唯一性和非负约束仍应在数据层兜底。

八、锁的三个隐藏问题 ​

1. 锁键必须与不变量一致 ​

如果不变量是“同一资源不能被同时扣减”，锁键应由资源标识构成；如果锁在用户标识上，但多个用户共享同一库存，仍会超卖。

2. 租约过期不等于旧执行者已停止 ​

使用带过期时间的分布式锁时，执行时间超过租约，第二个执行者可能获得锁。需要续租或 fencing token：每次获锁取得递增令牌，写入时只接受更新令牌。

text
执行者 A 获得 token-old，发生长暂停
执行者 B 获得 token-new，完成写入
执行者 A 恢复，携带 token-old 写入
数据库拒绝旧 token，避免覆盖新结果

3. 死锁是可预期的运行结果 ​

即使锁顺序统一，数据库仍可能因其他查询路径发生死锁。事务管理器应只对明确的死锁/序列化失败做有限、带抖动的重试。外部副作用绝不能包含在可自动重试的事务闭包内。

九、金额与数量：不要把精度问题留给运行时 ​

金额应使用整数最小单位或定点十进制值对象，不能用二进制浮点直接累加和比较。数量也要明确是否允许小数、精度和舍入规则。

php
final readonly class Money
{
    public function __construct(
        private int $minorUnits,
        private Currency $currency,
    ) {}

    public function add(self $other): self
    {
        $this->assertSameCurrency($other);
        return new self($this->minorUnits + $other->minorUnits, $this->currency);
    }
}

还应明确：

  • 折扣、税费、分摊分别在哪一步舍入。
  • 明细之和如何与主单总额对齐。
  • 冲正使用原交易金额还是按当前规则重算。
  • 币种、单位和精度是否作为类型的一部分。

冲正必须引用原始结果，不能重新执行今天已经变化的价格规则。

十、外部副作用：超时后的事实是“未知” ​

调用外部系统可能得到三类结果：

  1. 明确成功。
  2. 明确拒绝，且不会产生副作用。
  3. 超时、断连或响应无法验证，结果未知。

第三类最危险。请求可能已经到达远端，只是响应丢失。此时直接重试一个没有幂等键的“扣款”动作，可能造成重复扣款；直接回滚本地，也可能让外部成功而本地没有记录。

正确策略通常是：

text
外部调用超时
  ↓
保持 EXTERNAL_PENDING
  ↓
使用同一外部幂等键查询结果
  ├── 明确成功：推进 SUCCEEDED
  ├── 明确失败：进入补偿或业务拒绝
  └── 仍未知：退避重试，超过窗口转人工

外部幂等键应稳定映射到本地操作 ​

不要每次重试都生成新的外部请求号。可以从本地 operation_id 派生一个固定键，同时保存第三方返回的交易标识。任何回调都先通过这两个标识关联本地操作，再校验金额、币种、商户范围和签名。

不要在数据库事务里等待外部响应 ​

下面是典型反例：

php
$database->begin();
$repository->decreaseResource($command);
$remoteResult = $remoteClient->charge($command); // 网络等待期间一直持锁
$repository->saveRemoteResult($remoteResult);
$database->commit();

即使远端调用成功，随后本地提交失败也无法让远端自动撤销。更合理的是本地先提交操作意图和 outbox，由异步执行器调用；若产品必须同步等待，也应在本地事务提交后等待，并允许返回 PROCESSING。

十一、Transactional Outbox：让本地写入与“需要发送”原子化 ​

outbox 解决的是：业务数据提交了，但进程在消息发送前崩溃。它不保证远端只处理一次，因此消费者仍必须幂等。

一个演示结构：

sql
CREATE TABLE demo_outbox (
  event_id VARCHAR(128) PRIMARY KEY,
  aggregate_id VARCHAR(128) NOT NULL,
  event_type VARCHAR(128) NOT NULL,
  payload_json TEXT NOT NULL,
  status VARCHAR(32) NOT NULL,
  available_at TIMESTAMP NOT NULL,
  claimed_until TIMESTAMP NULL,
  attempt_count INTEGER NOT NULL,
  created_at TIMESTAMP NOT NULL
);

执行器领取任务时需要避免多实例重复处理：

text
选择到期且未被领取的任务
  ↓ 在短事务中设置领取租约
提交
  ↓ 事务外调用远端
按结果在新事务中标记成功、重试或人工处理

不要在持有任务行锁时发网络请求。执行器崩溃后，领取租约到期，其他实例可以继续。

重试策略至少包含：

  • 仅重试明确可重试的错误。
  • 指数退避并加入随机抖动。
  • 设置最大恢复窗口，而不只是固定次数。
  • 每次重试复用相同幂等键。
  • 超过窗口进入死信或人工队列，并产生告警。

十二、回调收件箱：先去重，再推进状态 ​

第三方回调通常会重复、乱序，甚至在同步响应之前到达。验签和基础格式校验可以在事务前完成，但 inbox 去重记录、业务状态推进、审计以及 inbox 处理状态必须在同一个本地数据库事务中提交：

text
验证来源、签名、时间窗口和载荷完整性
  ↓
开始本地事务
  ↓
原子尝试插入 inbox(RECEIVED)，唯一键为“来源 + 外部事件标识”
  ├── 已存在：读取原处理状态，本事务不重复业务效果
  └── 新事件：加载操作并核对关键事实
          ├── 当前可应用：条件状态迁移 + 审计 + inbox(APPLIED)
          ├── 暂时乱序：记录延后任务 + inbox(DEFERRED)
          └── 事实冲突：记录审计 + inbox(REVIEW_REQUIRED)
  ↓
提交本地事务
  ↓
返回协议要求的确认响应

原子尝试插入可以使用目标数据库支持的“冲突时不插入”语义，避免唯一冲突让整笔事务进入不可继续状态。若进程在提交前崩溃，收件箱和业务推进会一起回滚，第三方重发即可重新处理；若提交后确认响应丢失，重复回调会读到已有处理状态并安全确认。DEFERRED 必须由可领取、可重试的本地任务继续推进，不能只是一个无人消费的标记。

只有当 inbox 与业务数据位于同一可事务提交的数据库时，才能使用上面的原子方案。若二者跨库，应先把回调持久化为带领取状态的可靠任务，再由消费者幂等推进业务，不能用“先插收件箱、再另起事务改业务”的双写冒充原子性。

回调处理必须验证的不是只有签名，还包括：

  • 回调所指本地操作确实存在。
  • 外部商户或业务范围与本地操作一致。
  • 金额、币种或数量与本地意图一致。
  • 当前状态允许该事件推进。
  • 同一外部交易没有绑定到另一操作。

若回调内容与本地事实冲突，不要自动“修正成能成功的样子”，应保存脱敏证据并转人工核对。

十三、补偿：撤销一个承诺，不是删除历史 ​

为什么物理删除很危险 ​

高风险业务往往同时影响主单、明细、余额、库存、支付流水、业绩或审计信息。直接删除原记录会失去：

  • 谁在何时执行了原动作。
  • 当时使用了什么规则和金额。
  • 哪一步已对外产生副作用。
  • 补偿是否被重复执行。
  • 对账差异来自哪里。

更稳妥的方式是追加一份反向操作：

text
原操作：OP-A
  ├── 资源流水：DECREASE
  └── 外部结算：CONFIRMED

补偿操作：OP-B
  ├── compensates = OP-A
  ├── 资源流水：INCREASE（引用原流水）
  └── 外部退款：PENDING / CONFIRMED

原操作状态可以变成 COMPENSATED，但原流水保持不可变。

补偿本身也必须幂等 ​

补偿键可以由“原操作 + 补偿类型”构成唯一约束。第二次请求应返回第一次补偿结果，而不是再次返还资源。

补偿前还要检查后续依赖。例如一份已获得的资源可能已经部分使用，不能简单恢复整个原动作。此时有三种选择：

  • 只补偿仍可逆的部分，并记录差额。
  • 创建需要审批的人工处理任务。
  • 按业务规则拒绝自动补偿，保留明确原因。

补偿顺序通常与正向顺序相反，但不是机械回放 ​

正向流程可能是“占用资源 → 生成单据 → 外部结算”。补偿往往先确认外部是否可撤销，再恢复本地资源。若先恢复本地、外部退款最终失败，可能形成双重损失。

补偿方案必须在正向功能上线前定义，至少回答：

  • 每一步是否可逆？可逆窗口多长？
  • 补偿需要什么原始证据？
  • 外部补偿结果未知时如何查询？
  • 谁能发起、谁能审批、谁能强制终结？
  • 最终无法自动一致时，人工怎样处理并留下审计？

十四、对账器是跨系统一致性的最后防线 ​

幂等和重试仍可能因长期故障、人工操作或历史缺陷留下差异。对账器定期比较本地意图、本地结果和外部事实：

text
选择处于处理中、未知或超时状态的操作
  ↓
按稳定外部键查询第三方事实
  ↓
比较：状态、金额/数量、业务范围、时间
  ├── 一致：推进或确认终态
  ├── 可自动修复：发出幂等补偿命令
  └── 不可自动判断：创建人工核对项并告警

对账不是一条“大 SQL + 批量改状态”。每次修复都应走与在线操作相同的状态机、权限和审计路径。

演示伪代码：

php
final class ReconcilePendingOperations
{
    public function run(ReconcileWindow $window): void
    {
        foreach ($this->operations->pendingIn($window) as $operation) {
            $fact = $this->externalStatus->query(
                $operation->stableExternalKey()
            );

            $decision = $this->policy->decide($operation, $fact);
            $this->commands->dispatch($decision->toIdempotentCommand());
        }
    }
}

查询外部事实也要限流、退避和分页，避免故障恢复时同时压垮自身数据库与第三方。

十五、审计流水与当前快照要各司其职 ​

高一致性系统通常同时维护：

  • 当前快照：用于快速回答“现在还剩多少”“当前是什么状态”。
  • 不可变流水：用于回答“为什么变成这样”“能否重建和对账”。

两者在同一事务里更新。可定期执行不变量校验：

text
期初快照 + 流水变化合计 = 当前快照
有效主单汇总 = 对应资源流水汇总
本地确认的外部结果 = 外部对账事实

发现不一致时先冻结自动修复范围，保存证据，再通过专门的修复命令追加调整流水。直接编辑历史流水会让审计链失效。

十六、错误分类决定能不能重试 ​

错误类别示例处理策略
输入错误格式、单位或必填项无效不重试，返回稳定错误
业务拒绝资源不足、状态不允许不自动重试，可缓存幂等结果
并发冲突版本已变化、死锁在安全边界内重新读取后有限重试
瞬时依赖错误连接暂不可用、限流退避重试，保留相同操作标识
外部结果未知超时、断连查询状态，不直接重复副作用
永久外部拒绝参数或账户状态被明确拒绝进入补偿或业务失败
数据事实冲突本地与外部关键数据不一致停止自动推进，转人工
编程错误未预期异常、类型错误回滚、告警，不盲目重试

“捕获所有异常然后重试”是危险设计。编程错误会被放大，非幂等动作会被重复执行，真正的故障原因则被重试日志淹没。

十七、可观测性：用一个操作标识串起整条链 ​

日志字段 ​

每次状态变化应记录结构化、安全的上下文：

json
{
  "request_id": "generated-request-id",
  "operation_id": "generated-operation-id",
  "idempotency_key_hash": "non-reversible-hash",
  "event": "operation.state_changed",
  "from_state": "EXTERNAL_PENDING",
  "to_state": "SUCCEEDED",
  "external_reference_hash": "non-reversible-hash",
  "attempt": "measured-at-runtime",
  "duration_ms": "measured-at-runtime",
  "result": "success"
}

不要记录完整凭证、签名原文、支付码、隐私字段或未经筛选的回调体。若必须留取争议证据，应加密存储、限制权限并设置保留期限，不进入普通应用日志。

关键指标 ​

  • 操作提交成功率与业务拒绝率。
  • 幂等重放次数与指纹冲突次数。
  • 条件更新失败率、锁等待和死锁次数。
  • 各状态停留时长，尤其是 PROCESSING 与 EXTERNAL_PENDING。
  • outbox 积压量、最老任务年龄和重试分布。
  • 回调重复率、验签失败率和事实冲突数。
  • 自动补偿成功率、人工核对积压和对账差异。

只监控接口错误率不够。接口可能已经返回 PROCESSING，真正的故障发生在数小时后仍未完成。

告警必须能行动 ​

一个有用的告警需要包含：

  • 受影响操作范围和状态，而不是敏感业务数据。
  • 首次和最近发生时间。
  • 是否仍在增长。
  • 推荐查询入口与处理手册。
  • 哪些自动恢复已经尝试过。
  • 是否允许重试、补偿或只能人工核对。

十八、故障矩阵：在开发阶段决定崩溃后怎么办 ​

故障点持久化事实正确恢复方式
占用幂等键前崩溃无记录同键重试正常执行
幂等键与业务写入所在事务回滚均不存在同键重试正常执行
本地提交后、响应前崩溃操作和结果已存在同键重试返回原结果
本地提交后、发送事件前崩溃outbox 已存在执行器重新领取
外部已成功、响应丢失本地仍为未知用稳定外部键查询，不直接重做
回调处理一半进程崩溃回调事务回滚第三方重发或收件箱任务重试
状态更新成功、确认响应丢失收件箱与状态已提交重复回调命中幂等并确认
补偿外部成功、本地更新失败补偿状态未知查询外部补偿事实后推进
对账发现关键事实冲突差异记录存在冻结自动动作，转人工审计

把这张表变成故障注入测试，比在事故后临时猜测可靠得多。

十九、测试策略：正常路径只是最小的一部分 ​

1. 领域规则单元测试 ​

覆盖：

  • 状态机允许和禁止的每条迁移。
  • 金额、数量、舍入和分摊不变量。
  • 补偿是否引用原始结果。
  • 不同权限和业务状态的拒绝原因。

纯规则测试不依赖 Yaf、数据库、系统时间或真实 SDK。

2. 数据库集成测试 ​

使用与部署环境语义一致的数据库验证：

  • 幂等唯一约束确实生效。
  • 条件更新不会产生负资源。
  • 任意一步抛错后所有本地写入共同回滚。
  • outbox 与业务记录共同提交。
  • 状态迁移的条件更新能拒绝旧状态。
  • 死锁或序列化失败的重试范围正确。

3. 并发测试 ​

不要简单启动两个“可能同时”的请求。用屏障控制它们在关键点相遇：

text
请求 A 读取准备完成 ─┐
                      ├── 测试屏障同时释放 ──▶ 竞争同一资源
请求 B 读取准备完成 ─┘

断言最终业务效果只有一次、资源不变量成立、失败方得到可解释冲突。多轮随机并发可以发现锁顺序和低概率竞态。

4. 幂等重放测试 ​

同一个键覆盖：

  • 请求成功后立即重放。
  • 第一次仍在处理时重放。
  • 响应丢失后重放。
  • 改变关键参数后复用同一个键。
  • 多个进程同时提交同一个键。

5. 外部契约测试 ​

使用测试环境或可控的契约替身验证：

  • 请求中的外部幂等键稳定。
  • 明确拒绝、超时、格式异常都能正确分类。
  • 回调签名、乱序、重复和未知事件被安全处理。
  • 状态查询与副作用请求使用不同接口语义。

测试替身必须能模拟“远端已成功但本地看到超时”，这才是最重要的失败场景。

6. 崩溃点测试 ​

在以下边界注入进程终止或异常：

  • 本地提交前。
  • 本地提交后、返回前。
  • outbox 领取后、远端调用前。
  • 远端调用后、本地更新前。
  • 回调登记后、状态迁移前。
  • 补偿完成后、确认前。

重启执行器后，断言系统能从持久化状态继续，并且不会重复业务效果。

7. 属性测试与模型测试 ​

对账本和状态机可以生成随机命令序列，持续验证：

  • 资源不会越过业务下限。
  • 终态不能返回处理中状态。
  • 每个补偿都关联一个可补偿的原操作。
  • 相同幂等键至多对应一个业务效果。
  • 快照等于初始值与流水合计。

这种测试比手写少量案例更容易发现意外组合。

8. 迁移与回归测试 ​

从旧流程迁移时，先做“影子计算”：新规则读取同一份脱敏测试数据，只比较决策，不写生产结果。记录差异原因，完成规则对齐后再分批切换写入。

禁止为了验证新逻辑而把私有业务数据上传到外部测试服务。使用本地构造、脱敏夹具或合成数据。

二十、常见反例与为什么会失败 ​

反例一：查到不存在后再插入 ​

两个并发请求都可能查到不存在。应用层检查用于友好提示，数据库唯一约束才负责正确性。

反例二：先读余额，再写计算后的余额 ​

并发请求会覆盖彼此结果。使用条件更新、版本条件或行锁，把判断与修改放进一个原子边界。

反例三：每个失败分支手动回滚并返回 ​

异常、早退和未来新增分支很容易漏。统一事务闭包只在正常返回时提交，其余路径全部抛出并回滚。

反例四：事务中直接调用第三方 ​

远端不受本地事务控制，同时延长锁时间。使用本地意图 + outbox；同步场景也应先提交再等待，并支持处理中状态。

反例五：超时就当失败并重新发起 ​

超时代表未知。先使用同一外部键查询事实，只有明确失败且协议保证无副作用时才能重新发起。

反例六：回调只验签、不去重 ​

验签只能证明来源，不能保证事件只来一次。用收件箱唯一约束去重，用条件状态迁移抵抗乱序。

反例七：撤销时删除原记录或重算金额 ​

删除会破坏审计，重算会使用已经变化的规则。追加关联原操作的反向流水，金额和数量来自原始已确认结果。

反例八：有分布式锁就不需要数据库约束 ​

锁会过期、丢失或被错误释放。数据库条件和唯一约束仍应保护最终不变量。

反例九：所有错误都自动重试 ​

业务拒绝不会因为重试变成功，编程错误会被放大，未知外部结果可能造成重复副作用。先分类，再决定拒绝、查询、重试、补偿或转人工。

反例十：只记录“操作失败” ​

没有操作标识、状态迁移、外部引用和错误分类，无法判断是否可以重试。结构化日志应能重建一次工作流的决策过程，但必须排除敏感数据。

二十一、上线前检查清单 ​

不变量与数据模型 ​

  • [ ] 每条关键不变量都能用一句话表达，并有数据库或测试防线。
  • [ ] 主单、明细、资源快照和流水之间的关系明确。
  • [ ] 账本只追加，修复和冲正不覆盖历史。
  • [ ] 金额和数量的单位、精度、舍入与分摊规则明确。
  • [ ] 关键唯一性由数据库约束兜底。

事务 ​

  • [ ] 事务只覆盖同一本地数据库可原子提交的写入。
  • [ ] 外部请求、文件生成和通知不在事务内执行。
  • [ ] 统一事务管理器覆盖异常、早退和嵌套策略。
  • [ ] 事务内所有关键读取使用一致的写连接。
  • [ ] 加锁顺序稳定，死锁只在安全边界内有限重试。

幂等与并发 ​

  • [ ] 每个高风险写接口要求有作用域的幂等键。
  • [ ] 保存请求指纹，拒绝同键不同参数。
  • [ ] 首次稳定结果可被原样重放。
  • [ ] 判断与资源修改通过条件更新、版本或锁原子完成。
  • [ ] 分布式锁之外仍有数据库不变量保护。

外部副作用 ​

  • [ ] 本地操作标识稳定映射为外部幂等键。
  • [ ] 成功、明确失败、未知三类结果有不同处理。
  • [ ] 外部结果未知时先查询，不直接重做副作用。
  • [ ] outbox 领取有租约、退避、死信和告警。
  • [ ] 回调有验签、收件箱去重、事实核对和乱序保护。

补偿与对账 ​

  • [ ] 正向上线前已经定义每一步的可逆性和补偿窗口。
  • [ ] 补偿命令自身幂等，并关联原操作与原流水。
  • [ ] 无法自动判断时有人工核对状态和处理权限。
  • [ ] 对账器通过状态机发命令，不直接批量改终态。
  • [ ] 人工修复同样生成审计和调整流水。

观测与测试 ​

  • [ ] 请求、业务操作、外部引用和补偿可以安全关联。
  • [ ] 能看到处理中状态年龄、队列积压和对账差异。
  • [ ] 日志不包含凭证、签名原文、隐私数据和完整请求体。
  • [ ] 集成测试使用与目标数据库一致的事务和锁语义。
  • [ ] 并发、重放、乱序回调、响应丢失和进程崩溃均有测试。

二十二、一条适合遗留系统的渐进改造路线 ​

无需一次引入所有模式。可以沿风险最低的顺序推进：

text
第一步：为高风险入口增加稳定 operation_id、结构化日志和状态查询
   ↓
第二步：统一事务闭包，补齐数据库唯一约束与条件更新
   ↓
第三步：引入有请求指纹的幂等记录，客户端重试复用同一键
   ↓
第四步：把通知等非关键副作用迁到本地 outbox
   ↓
第五步：把支付等外部流程改为显式状态机与结果未知处理
   ↓
第六步：增加回调 inbox、自动对账、幂等补偿和人工处理台

每一步都应先挑一个垂直业务切片，保留旧入口契约，并用指标比较迁移前后的重复率、失败率和恢复时间。不要同时重写数据库、接口和所有客户端，否则无法判断改造是否真正提高可靠性。

结语 ​

高一致性系统无法消灭失败，它能做的是把失败从“不可知的异常”变成“可恢复的状态”。本地事务负责一个明确的数据库承诺；幂等和并发控制保证同一资源只被正确改变一次；状态机表达尚未完成的事实；outbox 与收件箱跨越进程和网络断点；补偿与对账让已经发生的外部事实最终可收敛；可观测性则让人知道系统现在卡在哪里、下一步能做什么。

真正可靠的流程不是从不进入异常，而是无论在哪一步中断，都能回答三个问题：已经发生了什么、下一步允许做什么、怎样证明最终恢复正确。
