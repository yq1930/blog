从私有源码提炼公开技术文章：一套可执行的脱敏流程 ​

真实项目最有文章价值，也最容易泄密。简单删除公司名并不等于脱敏：目录结构、接口路径、错误文案、状态编码、截图元数据和一段看似普通的 SQL，都可能让读者反推出业务、部署方式或客户信息。

安全写作的目标不是把文章写得模糊，而是把“真实证据”和“公开表达”分成两层：内部底稿保存可追溯的事实，公开正文只保留可以迁移到其他项目的方法，并用从零设计的示例重新证明它。

先定义什么绝不发布 ​

在阅读源码前建立禁止清单，避免写完后才凭感觉删内容。

类别常见载体公开处理
凭据密钥、证书、Cookie、Token、连接串不读取、不复制、不进入草稿
网络拓扑域名、IP、端口、网关与分流规则改为 example.test，不描述真实映射
身份信息用户、员工、客户、设备、平台账号使用完全合成的标识与数据
数据模型内部表名、字段名、SQL、索引命名从问题重新设计教学模型
业务规则真实费率、额度、状态码、角色编码用通用不变量和虚构数值表达
项目结构私有仓库名、内部模块名、绝对路径只描述技术层和职责
运行记录日志、HAR、截图、Source Map不直接使用；必要时手写演示记录
组织信息客户名、品牌、人员、邮件、提交记录删除或改为“渠道 A”等中性称呼

禁止清单要比“源码不能贴”更具体。很多泄露来自源码之外：终端提示符会显示用户名和路径，浏览器标签会显示后台名称，二维码和图片 EXIF 也可能带出信息。

建立双层文档，而不是边看边写 ​

推荐把工作分为两个完全不同的产物。

text
私有源码
   │ 只读审计
   ▼
内部证据底稿 ──── 记录事实等级与本地出处，不发布
   │ 抽象问题、约束、不变量
   ▼
公开文章 ──────── 原创示例、通用名称、公开资料

内部底稿用于防止作者凭记忆夸大事实；公开文章用于传播方法。两者不要混成一份再期待发布前“一键清洗”，因为路径和标识很容易藏在代码块、链接、图片和注释中。

内部底稿也要遵守最小化原则：只记录“哪个文件证明了什么”，不要复制私钥、配置值、完整函数或生产数据。它应被本地排除，不进入站点目录、版本提交和构建产物。

给每条结论标事实等级 ​

从源码看到一个工具类，不代表全系统都正确使用它；看到事务 API，不代表所有关键流程都有完整事务。底稿可以使用三种等级：

  • 已验证事实：依赖清单、入口或实现可以直接证明；
  • 综合判断：多个事实共同指向一种工程含义；
  • 推荐做法：作者基于问题提出的目标方案，不宣称已经落地。

公开文章中应通过措辞体现边界：

text
不严谨：系统通过分布式锁保证了所有写操作安全。
严谨：项目中存在锁基础设施；对于竞争写入，还应配合数据库约束、状态机与幂等验证。

这不仅是保密要求，也是技术准确性的要求。

不从文件目录出发，要从问题出发 ​

直接按源码目录写文章，很容易变成项目说明书：

text
入口文件做了什么
工具目录有哪些函数
某个控制器调用了哪些模型

更安全、更有用的结构是：

text
问题：弱网下同一写操作可能到达多次
约束：客户端可重试，服务端可能多实例，外部结果可能未知
不变量：一个业务意图只能产生一次有效状态变化
方案：交互锁 + 幂等键 + 唯一约束 + 结果查询 + 副作用去重
验证：并发、超时、崩溃点与重复回调测试

当文章围绕问题和不变量组织时，真实类名、路由和表结构自然不再重要。

示例代码必须从零重写 ​

脱敏不是变量重命名。保留原函数结构、分支顺序和特殊常量，只替换名字，仍可能暴露实现，也可能构成对私有源码的实质复刻。

安全示例应遵循四条规则：

  1. 从文章要证明的最小概念重新设计；
  2. 使用与真实领域不同的中性模型；
  3. 改变结构，而不只是改标识符；
  4. 删除与论点无关的历史兼容和业务分支。

例如要解释幂等，可以独立设计一个任务提交接口：

ts
type OperationRecord = {
  key: string
  fingerprint: string
  status: 'processing' | 'succeeded' | 'failed'
  result?: unknown
}

async function runOnce<T>(
  key: string,
  fingerprint: string,
  action: () => Promise<T>
): Promise<T> {
  const existing = await operationStore.find(key)

  if (existing && existing.fingerprint !== fingerprint) {
    throw new Error('IDEMPOTENCY_KEY_REUSED')
  }
  if (existing?.status === 'succeeded') {
    return existing.result as T
  }

  return operationStore.claimAndRun(key, fingerprint, action)
}

它只表达“键、请求指纹、状态、首次结果”四个概念，不需要借用真实订单类型、数据库模型或错误文案。

示例数据要合成，不要只打码 ​

把手机号中间四位替换为星号仍然保留了真实记录的其他关联特征。更安全的方法是完全合成：

json
{
  "actorId": "user_demo_17",
  "operationId": "op_demo_42",
  "amountMinor": 12990,
  "status": "pending"
}

合成数据还要避免复刻真实分布。金额、门店数量、角色层级、状态长度和时间窗口都可能构成业务指纹。教学示例只保留证明论点所需的最小数据。

用中性词汇替代内部领域语言 ​

内部术语往往比项目名更能识别业务。建立统一映射表可以降低遗漏：

内部概念类型公开表达
品牌或组织租户、组织 A
具体经营单元网点、地点、门店示例
内部岗位操作者、审核者、授权角色
特定产品资源、权益、服务项
真实单据订单、任务、预约等通用聚合
内部编码resource_demo_01

不要让一个真实术语在正文里被替换，却又留在代码注释、文件名、图片 alt、URL slug 或 Git diff 中。

路径、接口和配置的替换规则 ​

URL ​

统一使用保留用途域名：

text
https://api.example.test/v1/resources

不要使用一个看起来虚构、实际上可被注册或已经属于他人的域名。文章也不应描述真实服务如何按租户、设备或地区选择主机。

文件路径 ​

示例使用相对路径：

text
src/modules/example/
server/Application/Example/

不要展示 /Users/name/...、盘符目录、共享盘或部署脚本中的绝对路径。

环境变量 ​

只展示变量名称与占位符，不展示任何可用值：

dotenv
APP_ENV=development
API_BASE_URL=https://api.example.test
SESSION_SECRET=<set-by-deployment-platform>

即便是“测试密钥”也不应提交到文章示例。读者容易复制它，未来也难判断它是否真的只用于测试。

图表也要重新画 ​

从内部文档截图后打码风险很高：画布边缘、悬浮提示、文件名、浏览器地址栏和图片元数据都可能泄露信息。更安全的是根据抽象模型重新画最小图：

text
客户端
  │
  ▼
渠道适配层 ──▶ 统一身份上下文
  │
  ▼
应用用例 ───▶ 数据端口 / 外部网关

图里只出现文章已经定义的通用概念。截图无法避免时，应使用专门的演示环境和合成数据，并检查裁剪后的原文件，而不是只看页面预览。

代码泄露扫描要覆盖“精确匹配”和“特征匹配” ​

发布前至少做两类扫描。

特征匹配 ​

搜索：

  • 私有项目名和品牌词；
  • 生产域名、IP、端口和内部路径；
  • 邮箱、手机号、身份证、坐标等数据模式；
  • secret、token、private key、连接串等凭据特征；
  • 真实表名、字段名、角色和状态编码；
  • 绝对路径与内部仓库地址。

示意命令：

bash
rg -n -i \
  'internal-project|private\.example|/Users/|BEGIN .*PRIVATE KEY' \
  docs/

真实扫描词库保存在本地安全位置，不应把生产标识清单反向提交到公开仓库。

长行精确匹配 ​

把公开文章中足够长的代码行和源码做本地精确比对，可以发现“只改了几个变量”的伪重写。扫描报告只输出文章行号与来源文件，不回显命中的敏感原文。

精确匹配无法发现经过轻微改写的整段结构，因此仍需要人工检查：示例的控制流、特殊数字、注释顺序和异常分支是否过于接近来源。

构建产物必须再扫描一次 ​

源码干净不代表产物干净。静态站点构建可能包含：

  • Markdown 注释或未预期的 frontmatter；
  • Source Map 中的本地路径；
  • 打包进客户端的环境变量；
  • 图片和附件元数据；
  • 搜索索引里的隐藏正文；
  • 死链错误输出里的内部文件路径。

推荐流程：

text
扫描源文件
  → 本地构建
  → 检查构建日志与死链
  → 扫描 dist 文本和 Source Map
  → 随机打开关键页面
  → 查看 Git diff 与待提交文件清单

站点构建通过只证明语法和链接大致正确，不证明内容安全。

图片、音视频和附件的额外风险 ​

文本扫描看不到媒体中的信息。发布前检查：

  • 截图中的地址栏、标签页、账号、通知和任务栏；
  • 图片 EXIF、创建软件、作者和地理信息；
  • 视频每一帧可能出现的弹窗和通知；
  • 音频中被顺带说出的客户或环境信息；
  • PDF、Office 文件的作者、批注、修订记录和隐藏工作表；
  • 二维码、条码是否能解析出真实链接或标识。

最稳妥的文章配图仍是使用合成数据重新制作。

Git 是最后一道边界 ​

发布前不要只看工作目录，要看真正将进入版本历史的内容：

bash
git status --short
git diff --check
git diff -- docs/
git diff --cached -- docs/

确认研究底稿、AI 配置、日志、临时文件和构建产物都不在待提交列表中。被删除的敏感文件如果曾经提交过，普通删除并不会从 Git 历史移除，需要单独制定历史清理和凭据轮换方案。

一篇文章的完整生产流程 ​

1. 明确公开问题 ​

先写一句不含项目背景的问题，例如：“多个客户端不同步发布时，怎样安全演进同一 API？”

2. 只读采集证据 ​

只看与问题直接相关的入口、依赖、调用边界和测试。跳过配置值、运行日志和数据导出。

3. 写内部事实表 ​

每条记录包含：事实、等级、本地来源、可公开程度和需要替换的标识。

4. 提炼不变量 ​

把文件事实转成工程命题，例如：“同一业务意图无论到达几次，只产生一次有效结果。”

5. 重新设计示例 ​

选择通用领域，从空文件开始写最小示例；不打开来源函数逐行改写。

6. 标记建议与现状 ​

没有证据证明已经落地的内容，明确写成“推荐”“可采用”或“目标结构”。

7. 两轮审校 ​

第一轮只看技术正确性和文章结构；第二轮只看信息安全，不被内容流畅度分散注意力。

8. 本地验证 ​

运行敏感词、长行匹配、死链、构建和产物扫描，并人工打开首页和新文章。

9. 最小化提交 ​

只提交公开文章与必要导航修改，不提交底稿、脚本输出、截图原件和本地配置。

发布前检查清单 ​

内容边界 ​

  • [ ] 文章围绕通用问题，而不是按真实目录讲解？
  • [ ] 每个事实、判断和建议是否被清楚区分？
  • [ ] 是否删除了真实项目名、品牌、角色、路由和状态编码？
  • [ ] 是否没有暗示当前系统已经完成未验证的治理？

示例与数据 ​

  • [ ] 示例是否从零设计，而不是对私有源码重命名？
  • [ ] 数据是否完全合成，并避免复刻真实分布？
  • [ ] 域名是否使用 example.test，路径是否为相对路径？
  • [ ] 错误文本、注释和测试名是否也已泛化？

文件与媒体 ​

  • [ ] 是否没有绝对路径、私有仓库链接和内部提交信息？
  • [ ] 图片、视频、音频和附件是否检查了内容与元数据？
  • [ ] Source Map、搜索索引和构建产物是否重新扫描？
  • [ ] 内部底稿是否位于发布目录之外并被本地排除？

工程验证 ​

  • [ ] 敏感特征扫描是否无命中或已逐条解释？
  • [ ] 与来源代码的长行匹配是否无可疑结果？
  • [ ] 站点构建、死链检查和页面冒烟是否通过？
  • [ ] git status 是否只包含预期公开文件？

结语 ​

从私有项目写公开文章，最重要的能力不是“打码”，而是抽象：把真实代码背后的约束、不变量、失败模型和取舍提炼出来，再用一个全新的最小系统讲明白。

证据底稿保证文章没有凭空想象，原创示例保证实现不被带出，自动扫描与人工复核守住最后边界。做到这三层，公开分享不仅更安全，文章也会比项目说明书更经得起时间和技术栈变化。
